## 二、代码模式库

### 2.1 配置架构模式

```
config.json ← 全局配置
     ↓
_conf_schema.json ← 定义可覆盖字段(group_overrides hint是设计契约)
     ↓
get_group_setting() ← 按群覆盖实现

读取路径原则：
- 全局配置：self.config.get(key)
- 群组覆盖：get_group_setting(group_id, key)
- ASR/语音相关：倾向全局配置(路由一致性优先)
```

### 2.2 缓存结构模式

```
统一使用 deque(maxlen=N)
由常量控制容量
设计契约：记录是否独立于功能开关需明确确认
```

### 2.3 权限模型模式

```
三层架构：_is_authorized() → 各类admin检查函数
多层权限：全局配置(插件管理员) → 群配置(群管理员) → 具体请求(用户)
```

### 2.4 类型注解模式

```
混合风格问题：定义处用 Dict[str, deque]，部分处用类名
→ 代码演进历史痕迹，应在审查中要求统一
```

## 五、经验教训库

### 5.1 审查类教训

**PR描述≠代码变更**
审查摘要与PR描述出现严重不一致时，应：
- 在审查报告中明确标注"PR描述未涵盖以下变更"
- 暂定"全部变更"为审查范围边界
- 要求PR作者补充描述或解释

**缓存写入位置取决于设计意图**
- 若"记录"独立于"功能开关" → 置于enabled检查之前
- 若"记录"是"功能"的一部分 → 置于enabled检查之后
- **审查者需先确认设计意图再提出建议**

**配置读取路径变更风险**
- 从`get_group_setting`改为`self.config.get`后
- 群组配置中残留的旧值既不生效也不会被清除
- 需考虑迁移路径和回退逻辑

**Schema hint是设计契约**
- `_conf_schema.json`的`group_overrides`定义能力边界
- 变更schema hint也属于重要变更，需验证同步性

### 5.2 Issue分析类教训

**命令名引用必须验证**
- 违反规范：凭记忆引用`/设加群审核`/`/取加群审核`
- 正确做法：先grep命令注册代码，验证实际命名pattern

**API调用声称需代码位置**
- 声称"API已存在"但未grep验证是违规操作
- 必须提供file:line格式的具体位置

**配置类Issue关注副作用**
- 开关关闭时的功能依赖是重要风险点
- 特别关注对已有功能(#57等)的影响

**标签置信度需校准**
- `api`标签对配置层功能置信度偏高(0.75→0.5-0.6)
- `permissions`/`security`标签易被遗漏
- `breaking-change`标签对语义变更不可忽略

### 5.3 通用规范

**"消息不丢失"是假设而非事实**
并非所有功能都需要"记录先行"，建议需基于功能设计而非通用安全原则。

**Quick策略的局限性**
- 仅聚焦核心代码逻辑
- 应主动核对PR描述与变更文件的一致性
- 建议明确列出"已验证的同步变更文件"清单

## 六、项目特有规范要点

| 场景 | 规范要点 |
|------|----------|
| 配置读取路径变更 | 必须同步更新schema hint和README说明 |
| 全局vs群组配置 | 明确标注支持或不支持按群覆盖 |
| ASR/语音相关配置 | 倾向于全局配置(路由一致性优先) |
| 加群审核功能 | 涉及多层权限(全局→群组→用户) |
| 本地缓存新增 | 必须定义容量上限和清理机制 |
| OneBot协议相关 | message_id vs message_seq语义区分 |
