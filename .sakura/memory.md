## 仓库背景

仓库 `mjy1113451/astrbot_plugin_gm` 是 AstrBot 群管理类插件，Issue 常涉及命令解析、群管理权限、按群配置、配置 schema 与 README 同步。

## Issue 分析经验

### 1. 分类与优先级

- 明确运行时报错、命令参数类型错误、用户反馈“更新后仍存在”时，主分类应为 `bug`；若属于命令参数解析，可辅助考虑 `command`、`parser`、`compatibility`、`needs info`。
- 权限/配置粒度调整，如“头衔、管理、踢人权限按群独立配置”，应归为 `enhancement`，不是 `other`。可辅助考虑 `configuration`、`permission`、`group-management`、`needs-discussion`。
- `medium` 通常适用于：核心命令局部不可用、权限配置影响多群使用但非阻断。若错误导致插件启动/加载失败，应考虑升为 `high`；若只是单群体验优化，可保持 `medium`。
- 标题中 `[bug][medium]`、`[enhancement][medium]` 是重要信号，但必须结合正文和代码验证，不能机械照抄。

### 2. AstrBot 命令参数问题

- 对 `@filter.command(...)` 命令，必须区分错误发生在框架解析阶段还是业务函数阶段。若 AstrBot 根据函数注解提前转换参数，函数体内 `try/except int(count)` 无法兜底。
- 遇到 `参数 count 类型错误`、`count(int)=0` 等报错，应优先检查命令函数签名、类型注解和默认值，如 `count: int = 0`、`count: int = 1`。
- 修复方向通常是命令入口用 `str`/可选原始参数接收，在函数内部统一转换、校验并返回友好提示，同时保留无参默认语义。
- 不要只修复单一入口；应全局搜索相同模式，如 `count: int`、`: int =`、`filter.command`，检查 `/撤回`、`/撤回用户` 等复制粘贴式问题。
- 测试需覆盖：无参数、正常数字、非法字符串、空字符串、负数、过大数值、引用消息、@用户+数量、不同 AstrBot 版本。

### 3. 权限与按群配置需求

- “按群独立配置”通常不只是新增配置项，而是权限模型调整。需区分：功能权限、配置权限、插件管理权限。
- 本仓库相关关键点包括：`group_overrides`、`get_group_setting`、`title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`，以及 `has_title_admin_rights`、`has_kick_admin_rights` 等权限函数。
- 可行性评估应检查：是否已有全局配置项、是否已有按群覆盖读取路径、权限函数是否统一使用该读取逻辑、命令是否操作正确层级、`_conf_schema.json` 和 README 是否同步。
- 风险重点：旧配置迁移、删除旧“按群插件管理”的兼容性、空列表是覆盖为空还是回退全局、超级管理员/群管理员继承规则、多群隔离、安全误授权。
- 对权限类改动必须建议测试：全局配置生效、按群覆盖、未配置回退、空列表覆盖、多群隔离、普通用户不得获得踢人/管理/头衔权限。

### 4. 标签、标题与重复检测

- 标签推荐应优先贴合仓库现有标签；未知标签体系时也应给出通用候选并注明需映射，不能因不确定而留空。
- 标题为空或无意义（如“。”）时必须改写；标题应保留原始错误片段或具体对象。示例：`修复 count(int)=0 导致的命令参数类型错误`、`支持按群独立配置头衔、管理和踢人权限`。
- 避免把推断写成事实。若 Issue 未明确命令来源，可写“疑似撤回命令/需确认”，并要求补充完整日志、触发命令、AstrBot 版本、插件版本、是否启动即报错。
- 重复检测不能只依赖标题。参数错误需搜：`count(int)=0`、`参数 count 类型错误`、`撤回`、`filter.command`；按群权限需搜：`按群配置`、`群独立`、`权限`、`踢人`、`管理`、`头衔`、`group_overrides`。

### 5. 流程注意

- 不应因结构化输出字段（如 milestone 必须单行）校验失败，就把分类降为 `other`、标签置空、可行性写“无法评估”。字段失败应局部降级，保留可判断的信息。
- 对信息不足的 Issue，仍应给出有条件的可行性判断：说明需要补充哪些证据，以及在常见代码结构下的预估工作量与风险。
