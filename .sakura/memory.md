# 代码审查经验总结

> 累计反思 133 次

---

## 一、增量审查规范

### 1.1 Quick策略边界

| 原则 | 说明 |
|------|------|
| **声明优先** | PR描述提到的文件必须全部验证，不限于git diff |
| **状态变量扩展** | 涉及计数器/标志位的变更，应查看完整方法上下文 |
| **增量≠孤立** | 验证本次变更是否解决之前审查提出的问题 |

### 1.2 增量审查遗漏清单

```
□ PR描述声明的文件 ≥ 实际变更文件
□ 增量变更的完整逻辑链（尤其状态机/计数器）
□ 本次变更与历史提交的关联性
```

---

## 二、PR描述完整性校验

### 2.1 核心规则

| 规则 | 检查项 |
|------|--------|
| **声明覆盖** | 审查摘要中的变更点 ≥ PR描述中的变更点 |
| **新增项声明** | 新增功能/配置/命令必须列出 |
| **差异标注** | PR描述与代码不一致时，标注"描述缺失"而非默认"无" |

### 2.2 文档变更同步

- Quick策略下，PR明确描述的文档变更（如README/Schema）必须验证
- "删除命令未同步README"需判断：功能破坏性遗漏 vs 体验优化建议

---

## 三、并发与持久化审查

### 3.1 异步环境关注点

```
□ 计数器自增+检查+重置+保存 是否原子
□ 多协程并发调用时的竞争条件
□ 批量保存与单次保存的互斥保护
```

### 3.2 持久化策略一致性

项目存在两种模式并存：
- **即时保存**：高可靠性，高I/O（`_record_violation`等）
- **批量保存**：低I/O，低可靠性（`_increment_message_count`）

**审查要点**：若同一模块存在多种持久化策略，需追问是有意设计还是历史遗留。

### 3.3 计数器重置顺序风险

```python
# 错误顺序：save_stats()失败 → counter已重置 → 丢失计数
save_stats()
_msg_save_counter = 0

# 正确顺序：save_stats()失败 → counter仍为49 → 下次触发重试
_msg_save_counter = 0
save_stats()
```

## 四、缓存安全审查

| 检查项 | 说明 |
|--------|------|
| 容量上限 | deque(maxlen=N) 必须定义 |
| 清理机制 | TTL/容量阈值触发是否完整 |
| 内存泄漏 | 长期运行是否会导致内存增长 |

### 4.1 功能设计意图确认

配置项`enabled=false`时的预期行为：
- **"不记录"**：记录应置于enabled检查之前
- **"不执行"**：记录应置于enabled检查之后

**审查建议需基于确认的设计意图，而非通用安全原则。**

## 五、配置变更审查

### 5.1 配置迁移路径检查

| 变更类型 | 审查要点 |
|----------|----------|
| 读取路径变更 | 旧配置迁移路径、升级用户处理 |
| 覆盖能力变更 | 同步更新schema hint和文档 |
| 枚举值变更 | 边界校验 |

### 5.2 Schema Hint作为设计契约

```
_conf_schema.json 的 group_overrides 定义了「可按群覆盖」的能力边界
```

变更schema hint属于设计契约变更，需与代码变更同等重视。

### 5.3 配置变更审查清单

```
□ 新增配置 → 默认值安全性
□ 删除配置 → breaking-change和迁移路径
□ 读取路径变更 → 旧配置迁移和回退逻辑
□ 覆盖能力变更 → 同步更新schema hint和文档
□ 枚举值变更 → 边界校验
```

## 六、类型注解审查

### 6.1 一致性检查

```
# 定义处
private_message_history: DMHistoryManager = {}  # 类名？运行时是dict

# 使用处
private_message_history: Dict[str, deque] = {}
```

类型不一致暴露代码演进历史，定义处与使用处应统一。

### 6.2 OneBot协议语义

- `message_id` vs `message_seq` 语义不同，需区分使用

## 七、审查质量评分标准

| 维度 | 权重 | 关键指标 |
|------|------|----------|
| 覆盖度 | 40% | 核心逻辑、异常路径、边界条件 |
| 准确度 | 30% | 严重程度判定、决策合理性 |
| 完整性 | 30% | 架构理解、设计意图、潜在风险 |

### 7.1 评分校准参考

| 评分 | 含义 | 决策参考 |
|------|------|----------|
| 9-10 | 优秀，发现关键问题 | approve |
| 7-8 | 良好，有少量遗漏 | approve + comment |
| 5-6 | 一般，遗漏较多 | request_changes |
| <5 | 较差 | request_changes |

**文档问题与代码问题需分级**：文档同步问题通常为comment级别，除非导致功能无法使用。

---

## 八、审查效率与深度平衡

| 策略 | 适用场景 | 风险 |
|------|----------|------|
| Quick | 增量审查+无新风险+历史审查充分 | 可能遗漏上下文关联 |
| Full | 首次审查+复杂变更+涉及架构调整 | 效率较低 |

### 决策建议

- **首次审查**必须Full
- Quick仅适用于依赖已有审查结论的增量变更
- 涉及**状态机/计数器**的变更，应扩展至完整方法上下文
