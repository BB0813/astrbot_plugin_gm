# 项目记忆

累计反思 12 次

## 仓库背景

仓库 `mjy1113451/astrbot_plugin_gm` 是 AstrBot 群管理类插件，Issue 常涉及命令解析、群管理权限、按群配置、配置 schema 与 README 同步。注意 Issue 中可能出现旧插件名或相近插件名（如 `astrbot_plugin_group_admin`），分析时需确认与当前仓库/插件注册名是否一致，避免把推断写成事实。

## Issue 分析经验

### 1. 分类与优先级

- 明确运行时报错、命令参数类型错误、用户反馈“更新后仍存在”时，主分类应为 `bug`；若属于命令参数解析，可辅助考虑 `command`、`parser`、`compatibility`、`needs info`。
- 权限/配置粒度调整，如“头衔、管理、踢人权限按群独立配置”，应归为 `enhancement`，不是 `other`。可辅助考虑 `configuration`、`permission`、`group-management`、`needs-discussion`；若删除旧机制或命令，评估 `breaking-change`。
- `medium` 通常适用于：核心命令局部不可用、权限配置影响多群使用但非阻断、群管理命令提示成功但实际未生效。若错误导致插件启动/加载失败，或存在越权、误踢/误撤大量消息等高风险，应考虑升为 `high`；若只是单群体验优化，可保持 `medium`。
- 标题中 `[bug][medium]`、`[enhancement][medium]` 是重要信号，但必须结合正文和代码验证，不能机械照抄。标题为空或“。”、“，”时，仍应从正文提炼分类、优先级和标题；若系统要求标题字段，不能写“无建议”，可保留清晰原标题或轻量规范化。

### 2. AstrBot 命令参数与撤回逻辑问题

- 对 `@filter.command(...)` 命令，必须区分错误发生在启动/插件加载/命令注册阶段，还是用户调用后的业务函数阶段。若 AstrBot 根据函数注解提前转换参数，函数体内 `try/except int(count)` 无法兜底；对包含可选数量、@用户、引用消息等复杂语法的入口，优先用字符串/原始事件解析。
- 遇到 `参数 count 类型错误`、`count(int)=0` 等报错，应优先检查命令函数签名、类型注解和默认值，如 `count: int = 0`、`count: int = 1`，同时确认触发命令、完整堆栈、AstrBot 版本、插件版本/commit、是否旧缓存。
- 修复方向通常是命令入口用 `str`/可选原始参数接收，在函数内部统一转换、校验并返回友好提示，同时保留无参默认语义。需明确 `0`、空字符串、`None`、负数、过大值等边界含义。
- `/撤回 N` 的语义应按用户直觉理解为撤回“当前命令之前的 N 条消息”，不能默认优先撤回命令自身；`count=1` 是最小必测用例。应获取历史消息、排除当前 `event.message_id`、按时间顺序选择可撤回目标；历史接口不可用时应明确提示，而不是回退成撤回指令自身并误报成功。
- 撤回类问题需检查引用消息优先级、无参默认行为、`/撤回用户` 是否受影响、消息 ID 类型、历史返回正/倒序、当前命令是否包含在历史中、消息不足、撤回超时/权限不足、OneBot 适配器不支持历史接口等。
- 不要只修复单一入口；应全局搜索相同模式，如 `count: int`、`: int =`、`filter.command`，检查 `/撤回`、`/撤回用户` 等复制粘贴式问题，以及 `int`、`bool`、`float`、`At` 等可能被框架预解析的参数。
- `/撤回 @用户 N` 与 `/撤回用户 @用户 N` 要区分“功能缺失、入口未路由、参数解析失败、文档/提示不清”四种情况。若已有 `recall_user_cmd`、`_extract_at_qq` 等按用户撤回逻辑，修复宜抽取共享 helper（数量解析、历史遍历、权限校验、撤回执行），避免复制导致行为分叉。`@用户` 解析应基于消息 segment/user_id/At 对象，不要按昵称文本或空格简单 split；昵称可能含空格，多个 @、未 @、非法数量、0、负数都要有明确提示。
- 撤回命令测试要覆盖语法组合：`/撤回`、`/撤回 1`、`/撤回 @用户 1`、`/撤回用户 @用户 1`、引用撤回、无/非法/负数/0/过大数量、多个 @、非群聊、bot 权限不足、历史消息不足或接口不可用。

### 3. 权限、群管理 API 与按群配置需求

- “按群独立配置”通常不只是新增配置项，而是权限模型调整。需区分：功能权限、配置权限、插件管理权限；遵循最小权限原则，避免用泛化“插件管理员”替代具体动作授权。
- 本仓库相关关键点包括：`plugin_admins`、`group_overrides`、`get_group_setting`、`title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`，以及 `has_title_admin_rights`、`has_kick_admin_rights`、`has_group_admin_rights` 等权限函数。
- 按群配置要分三层判断：业务读取层是否统一走 `get_group_setting`；命令管理层是否能正确写入/查看/清除 `group_overrides[group_id][key]`；配置 UI/schema/README 是否清楚表达“全局默认 + 群级覆盖”。Schema/UI 问题也可能是 `bug`，不要机械归为 enhancement。
- 顶层配置项存在不一定是 bug，它可能是全局默认值。更稳妥做法是保留全局默认，在 `_conf_schema.json` 和 README 中标注可被群级覆盖；状态展示应显示“有效值 + 来源 + 全局默认值”。动态群号键若受 AstrBot UI 限制，至少需用说明和示例弥补。
- 配置边界风险：`0` 可能表示关闭且必须能覆盖全局，不能被 `dict.get`/假值判断误当缺失；空列表是覆盖为空还是回退全局，`None`、缺失 key、空字符串要区分；旧配置迁移和兼容读取不能忽略。
- 可行性评估应检查：是否已有全局配置项、是否已有按群覆盖读取路径、权限函数是否统一使用该读取逻辑、命令是否操作正确层级、状态/帮助输出是否一致、`_conf_schema.json` 和 README 是否同步。
- 删除或废弃旧“按群插件管理”时要谨慎：考虑旧配置迁移、兼容读取、deprecated 过渡、命令语义变化、用户习惯破坏。
- 群管理 API “返回成功但实际未生效”（取消头衔、设管理员、踢人/禁言、改群名片等）要按固定链路排查：命令解析 → 权限判断 → API 参数 → 适配器兼容 → API 返回值 → 状态回读 → 用户提示。OneBot/NapCat/Lagrange/go-cqhttp 可能对 `special_title=""`、`duration=-1/0/不传`、返回值和缓存刷新语义不同。
- `/取消头衔` 等命令不能仅根据 action 返回值提示成功；需考虑机器人是否管理员/群主、权限是否高于目标、目标是否群主、QQ 限制、客户端缓存/延迟。可用 `get_group_member_info` 回读确认，但要提示回读也可能受缓存和字段差异影响。
- 权限类改动必须建议测试：全局配置生效、按群覆盖、未配置回退、空列表/0 覆盖、多群隔离、普通用户不得获得踢人/管理/头衔权限、旧配置升级后行为。

### 4. 标签、标题与重复检测

- 标签推荐应优先贴合仓库现有标签；未知标签体系时也应给出通用候选并注明需映射，不能因不确定而留空。除 `bug` 外，按场景补充 `command`、`recall`、`message-history`、`compatibility`、`group-management`、`configuration`、`schema`、`documentation`、`ui/config-ui`、`needs-info` 等。
- 标题为空或无意义时必须改写；标题应保留原始错误片段或具体对象。示例：`/撤回 1 应撤回上一条消息而非指令本身`、`取消头衔命令提示成功但实际未清空群头衔`、`禁言踢出阈值按群覆盖后仍显示为全局配置`。是否保留 `[bug][medium]` 取决于仓库标题风格。
- 避免把推断写成事实。若 Issue 未明确命令来源或运行环境，可写“疑似/需确认”，并要求补充完整日志、触发命令、AstrBot 版本、插件版本、OneBot 实现、机器人群权限、是否启动即报错。
- 重复检测不能只依赖标题。参数错误需搜：`count(int)=0`、`参数 count 类型错误`、`撤回`、`recall_cmd`、`recall_user_cmd`、`filter.command`；撤回自身需搜：`/撤回 1`、`撤回指令本身`、`上一条消息`、`get_group_msg_history`、`message_id`。
- 按群权限/配置需搜：`按群配置`、`群独立`、`权限`、`踢人`、`管理`、`头衔`、`禁言阈值`、`mute_kick_threshold`、`group_overrides`、`group_admins`、`配置显示`；头衔问题需搜：`取消头衔`、`special_title`、`set_group_special_title`、`duration`、`NapCat`、`成功但没生效`。
- “未检测到重复”在缺少历史 Issue 列表时只能表述为暂未发现，需说明可能漏报；同命令/同模块但症状、触发路径、修复点不同的 Issue 应标关联而非重复。

### 5. 流程注意

- 不应因结构化输出字段（如 milestone 必须单行）校验失败，就把分类降为 `other`、标签置空、可行性写“无法评估”。字段失败应局部降级，保留可判断的信息。
- 对信息不足的 Issue，仍应给出有条件的可行性判断：说明需要补充哪些证据，以及在常见代码结构下的预估工作量与风险。
- 对“版本已更新仍存在”的问题，应追踪最近相关 commit/PR：可能是修复方向错误、覆盖入口不全、插件目录/缓存未更新，不能仅重复原修复建议。
