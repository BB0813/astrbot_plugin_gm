# AstrBot GM 插件代码审查经验总结

> 累计反思 110 次 | 最后更新：2026-08-10

---

## 一、Issue 分析规范

### 1.1 重复检测硬约束 ⚠️
- **第一行必须写"暂未发现"**
- 禁止使用"可能是 #X 的重复"等措辞
- 违规项为 P0 问题

### 1.2 标签推荐要点
| 标签 | 适用场景 |
|------|---------|
| `api`/`api-integration` | 涉及 OneBot API 调用时必加 |
| `command`/`new-command` | 新增命令时必加 |
| `parser` | 仅参数解析时使用，静态命令匹配不应给高置信度 |
| `query` | 纯查询操作 |
| `usability` | 可用性增强 |

### 1.3 工作量估算完整性
- 命令型 Issue：需考虑速率限制/冷却机制（+15-25 行）
- 配置项设计：需考虑按群覆盖、默认值安全性、滥用防护

## 二、PR 审查规范

### 2.1 审查策略选择
```
破坏性配置变更（删除默认项）→ 必须使用 full 策略
quick 策略不应用于需要评估业务影响的变更
```

### 2.2 命令移除七处同步（必检）
1. `main.py` handler
2. `_GM_COMMAND_NAMES` 元组
3. README/帮助文本
4. CHANGELOG
5. metadata.yaml
6. i18n 文件
7. **文档全文 grep 验证**

### 2.3 配置项移除评估
| 变更类型 | 风险等级 | breaking-change 建议 |
|----------|----------|---------------------|
| 删除既有配置 | 中 | 0.90-0.95，需在 CHANGELOG 明确标注 |
| 硬编码替代可配置项 | 中 | 显式评估影响范围 |

### 2.4 权限模型变更检查清单
```
□ 替代方案是否完备？
□ 旧配置迁移路径是否明确？
□ 破坏性影响是否在 PR 描述中充分说明？
□ 是否需要 changelog / 升级指引？
```

---

## 三、权限审查经验

| 变更方向 | 风险等级 | 审查重点 |
|----------|----------|----------|
| 收紧权限 | 低 | 旧配置处理、向后兼容 |
| 放宽权限 | **高** | 滥用风险、隐私合规 |
| 简化模型 | 中 | 功能完整性、文档一致性 |

---

## 四、技术审查要点

### 4.1 AstrBot 插件特有
- `_GM_COMMAND_NAMES` 是命令注册的硬约束，仅删除 handler 不足
- 命令移除必须同步更新该元组

### 4.2 OneBot API 调用类 Issue
必须检查：
1. Bot 自身权限要求
2. 目标用户权限要求
3. 官方平台限制
4. 适配器兼容性（NapCat 等）

### 4.3 撤回/删除类操作
验证完整链路：缓存写入 → 业务逻辑 → 回执

---

## 五、Quick 模式必检项
```
□ README/文档中是否提及被移除的命令/配置
□ _GM_COMMAND_NAMES 是否与实际命令同步
□ 硬编码替代可配置项时的 breaking-change 显式标注
□ 权限变更时是否涉及帮助文本/错误提示同步
□ 文档全文 grep 验证
```
