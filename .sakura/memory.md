## 1. Issue 分析核心流程

### 1.1 标准输出结构
```
分类: enhancement/bug/other
优先级: high/medium/low
可行性: A/B/C/D 四档分支 + 工作量估算
标签: 至少 8-15 个，含置信度
建议标题: 可保留/改写版
重复检测: 暂未发现 + 检索关键词 + 关联 Issue
```

### 1.2 校验失败处理原则（P0 硬约束）
- **禁止整体降级**：字段校验失败 → 仅修复字段输出格式，**不得**降级为 `other`/`无法评估`/`无建议`
- 信息不足 ≠ 无法评估，基于已知信息给出分支判断
- 回退触发计数已达 N+1 次，必须彻底根除

### 1.3 重复检测强制模板
- **第一行必须写"暂未发现"**
- 禁止使用："未检测到重复"、"无重复"、"可能是 #X 的重复"
- 主分类不同 → 重复概率上限 0.30（前置过滤）

## 3. 优先级决策路径

### 3.1 标准 5 条路径
1. 横切权限 + breaking-change → 升 high
2. owner-driven + 已标准化 → 不升 high
3. 工作量可控 + 迁移明确 → 不升 high
4. 跨适配器风险有兜底 → 维持原级
5. **默认值决策**（默认 false 维持；默认 true 升 high）+ 隐私风险降级

### 3.2 动作联动型特殊规则
- 涉及删除用户数据 → 必须评估滥用风险、合规风险
- 默认 true（自动清历史）→ 升 high
- 默认 false（用户主动启用）→ 维持 medium

---

## 4. 隐私合规强制要求

### 4.1 何时必须添加 privacy 标签
- 删除用户数据
- 修改用户信息
- 清历史/撤回他人消息
- GDPR/个人信息删除语义

### 4.2 隐私合规清单
- 审计日志（操作者、消息 ID、时间戳）
- 用户通知（被清除者私聊告知）
- 撤回通知抑制（避免群内风暴）
- 失败回滚（部分失败时回执 N/M）

## 5. 可行性分支细化标准

### 5.1 A/B/C/D 四档
- **A**：最小可行，80-150 行 / 1-2 天
- **B**：完整功能，150-250 行 / 2-3 天
- **C**：完整 + 跨适配器回读，250-400 行 / 3-5 天
- **D**：分阶段，4-6 天

### 5.2 分支 B/C 必显式标注
- 撤回时限（2 分钟时间窗）
- 通知风暴抑制
- 去重处理（set）
- 回执一致性（三类计数）
- 外部仓库验证状态
