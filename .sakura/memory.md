## 一、审查策略规范

### 1.1 策略升级触发条件

| 条件 | 建议策略 |
|------|---------|
| 配置项新增 ≥5 | standard+ |
| 代码变更 ≥200 行 | standard+ |
| 破坏性配置变更（删除默认项） | **必须 full** |
| 权限模型变更 | full |
| 多文件跨层同步变更 | standard+ |

### 1.2 Quick 模式强制检查项

```
□ README/文档中是否提及被移除的命令/配置
□ _GM_COMMAND_NAMES 是否与实际命令同步
□ 硬编码替代可配置项时的 breaking-change 显式标注
□ 权限变更时是否涉及帮助文本/错误提示同步
□ 新配置项默认值是否安全（false 优于 true）
```

## 二、AstrBot 插件特有模式

### 2.1 命令注册硬约束

AstrBot 命令注册依赖 `_GM_COMMAND_NAMES` 元组：
- 仅删除 handler **不足以** 真正移除命令
- 必须同步更新元组
- 七处同步清单：
  1. main.py（handler 删除）
  2. `_GM_COMMAND_NAMES` 元组
  3. README/帮助文本
  4. CHANGELOG
  5. metadata.yaml（如有）
  6. i18n 文件（如有）
  7. 缓存/状态文件（如有）

### 2.2 权限模型演进模式

集中权限检查趋势（#130→#132→#147 连贯演进）：
```
分散 is_plugin_admin → 统一 _is_authorized()
```

权限统一 helper 审查要点：
- 抽样所有调用点
- 验证 success/静默失败双路径
- 确认替代方案覆盖旧场景

### 2.3 权限变更风险矩阵

| 变更方向 | 风险等级 | 审查重点 |
|----------|----------|----------|
| 收紧权限 | 低 | 旧配置处理、向后兼容 |
| 放宽权限 | **高** | 滥用风险、隐私合规 |
| 简化模型 | 中 | 功能完整性、文档一致性 |

## 三、Issue 分析规范

### 3.1 原标题标记解读

**必须读取原标题标记**：
- `[bug]` → 分类为 bug，优先级参考标记
- `[enhancement]` → 功能增强
- 标记是分类/优先级的重要信号

### 3.2 Issue 分析硬约束

| 规则 | 说明 |
|------|------|
| **禁止使用** | "可能是 #X 的重复" |
| **必须使用** | "暂未发现" + 搜索说明 |
| 标签推荐 | **不能为空**，至少给出基础标签+置信度 |
| 标题改写 | 应改写，保留命令名和核心问题 |
| 可行性判断 | 不能"无法评估"，至少定位相关代码 |

### 3.3 持久化类 Issue 检查清单

```
□ 排名数据的存储位置（内存？临时文件？）
□ 是否缺少数据库/文件持久化逻辑
□ 重启后数据丢失 = 缺少 save()/load() 机制
```

### 3.4 Issue 分类准确性

- `bug`：功能缺陷，代码行为与预期不符
- `data-persistence`：数据持久化缺陷
- `command` 标签：适用于**新增命令**或**命令行为重大变更**，不适用于命令的 bug
- 持久化缺陷优先级通常为 **medium**（非核心功能失效）

## 四、Breaking Change 管理

### 4.1 配置项变更风险评估

| 变更类型 | breaking-change 评分 | 处置 |
|----------|---------------------|------|
| 删除既有配置 | 0.90-0.95 | 必须 CHANGELOG 独立章节 |
| 硬编码替代可配置项 | 视影响范围 | 需显式评估，CHANGELOG 标注 |
| 新增配置项（默认安全值） | 低 | 文档同步 |

### 4.2 硬编码常量评估

```
评估问题：
□ 是否应保留可配置性？
□ 影响范围（单群/多群）？
□ 用户迁移路径是否明确？
```

## 五、审查工具鲁棒性

### 5.1 审查失败处理

| 场景 | 当前状态 | 建议改进 |
|------|---------|---------|
| 工具输出验证失败 | 产生 None/10 评分 | 应拒绝提交，标记"审查失败" |
| 审查输出验证错误 | 无有效输出 | 自动降级为"manual review required" |
| 评分 None/10 | 产生审查决策 | 应触发告警 |

### 5.2 审查输出验证要求

- 文件 findings 必须提供 **line values**
- 禁止产生无评分的审查决策
- 增量审查需验证合并前的 PR 是否已审查

## 六、项目架构观察

### 6.1 代码模式

```
权限检查架构: _is_authorized() → _is_group_admin_or_owner()
                         ↓
            has_*_admin_rights() × 3
```

- 权限判断分散在多个方法中
- 采用短路逻辑（`or` 链）组合多种权限来源
- 删除操作涉及群管理动作（`kick` 语义隐含）

### 6.2 配置架构

```
_conf_schema.json（类型约束） + 实际 JSON（用户数据）
```

- 配置项移除是破坏性变更（旧配置被忽略）
- provider_manager 统一管理 AI 能力
- 多层级 fallback 策略（provider → active → endpoint）

## 七、常见审查遗漏清单

### 高频遗漏项

1. **文档同步** — README/文档提及被移除命令
2. **`_GM_COMMAND_NAMES` 同步** — AstrBot 插件必检
3. **硬编码常量替代配置项** — breaking-change 未标注
4. **持久化缺失** — 内存缓存缺少 save/load
5. **原 Issue 标题标记** — 被忽略的分类信号

### PR 描述质量标准

```
□ 必须包含 "breaking-change" 章节（如有）
□ 配置项新增需说明默认值安全性
□ 外部依赖需说明兼容性
□ 命令移除需提供 grep 验证结果
□ 权限变更需说明替代方案完备性
```

## 八、增量审查特殊处理

### 8.1 增量变更风险点

| 提交类型 | 审查要点 |
|---------|---------|
| 合并提交 | 需验证合并前 PR 是否已审查 |
| 配置项变更 | 需验证移除是否遗留文档引用 |
| 权限模型变更 | 需验证命令移除七处同步 |
| `chore(sakura)` | 需确认不引入功能变更 |

### 8.2 增量审查失败特征

```
Quick 策略 + 审查工具失败 = 覆盖度 0%
```

根本原因：
1. 工具无法解析 findings（缺少 line 值）
2. Quick 策略本身不强制完整检查
3. 变更量超出 quick 策略的安全边界

## 九、审查质量自检

### 评分合理性参考

| 评分 | 适用场景 |
|------|---------|
| 10/10 | 完美，无改进空间 |
| 7-8/10 | 代码正确，文档/小问题 |
| 5-6/10 | 存在需修复的问题 |
| <5/10 | 严重问题，需 request_changes |

### 决策正确性验证

- Quick 模式发现核心问题 → 决策正确
- 审查失败但 PR 本身合理 → 工具问题，PR 本身可接受
- 无法评估但给出 None 评分 → 应标记审查失败
