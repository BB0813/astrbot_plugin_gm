# 代码审查经验总结 | 累计反思 132 次

## 核心原则

1. **Quick策略不等于忽略**：增量审查时需核对PR描述声明的所有文件（含README/Schema）
2. **PR描述是承诺清单**：审查摘要中的变更点应≥PR描述中的变更点，缺失项需标注
3. **状态机/计数器变更必看完整上下文**：增量审查的"只见树木"风险
4. **设计意图先于代码建议**：先确认功能意图，再提建议，避免"消息不丢失"式假设

---

## 新增审查规则

### 规则N：PR描述完整性校验
```
□ 审查摘要中的变更点 ≥ PR描述中的变更点
□ 新增功能/配置/命令必须在PR描述中明确列出
□ 缺失项标记为"描述缺失"而非默认"无此项"
```

### 规则O：缓存安全性检查
```
□ 新增本地缓存是否定义容量上限？
□ 是否有TTL机制或显式清理函数？
□ 是否存在内存泄漏风险？
```

### 规则P：功能设计意图确认
```
□ 配置项enabled=false时的预期行为是什么？
□ "不执行" vs "执行但不提供UI" 必须明确区分
□ 审查建议需基于确认的设计意图，而非通用原则
```

### 规则T：增量上下文关联验证
```
触发条件：增量审查+关联Issue
□ 确认本次变更解决了之前提出的问题
□ 增量变更是否依赖其他未变更的代码
□ 标注"审查范围仅限于[具体行号]"
```

## Quick策略执行规范

### 文件范围确定
```
变更文件清单获取：
1. git diff --name-only（实际变更）
2. PR 描述提到的文件（声明变更）
3. 取并集，作为审查范围边界
```

### 文档同步显式确认
```
□ PR描述提到的文档变更是否与实际变更文件一致
□ 记录「已验证的同步变更文件」清单
```

### 文档问题分级
| 问题类型 | 严重度 | 处理方式 |
|----------|--------|----------|
| 功能性文档缺失（命令表） | 建议修复 | comment |
| 示例段落遗漏 | 优化建议 | comment |
| 功能破坏性遗漏 | 严重 | request_changes |

## 配置类变更审查清单

```
□ 新增配置项 → 检查默认值安全性
□ 删除配置项 → 检查 breaking-change 和迁移路径
□ 读取路径变更 → 检查旧配置迁移和回退逻辑
□ 覆盖能力变更 → 同步更新 schema hint 和文档
□ 枚举值变更 → 检查边界校验
```

### 配置读取路径变更迁移验证
```
□ 是否存在旧配置数据的迁移路径说明
□ 升级用户是否需要手动清理旧配置
□ CHANGELOG 是否说明升级步骤
```

## 架构模式识别

### 持久化策略不一致风险
```
// 即时保存（高可靠性，高I/O）
_record_violation() → save_stats()
_record_mute_and_maybe_kick() → save_stats()

// 批量保存（低I/O，低可靠性）
_increment_message_count() → [计数器=50?] → save_stats()
```
**检查项**：同一模块内存在多种持久化方法时，验证设计一致性

### 缓存结构模式
```
private_message_history: Dict[str, deque(maxlen=N)]
```
**检查项**：统一使用deque(maxlen=N)控制容量，需验证清理机制

### 配置分层架构
```
config.json ← 全局配置
     ↓
_conf_schema.json ← 定义可覆盖字段（group_overrides hint）
     ↓
get_group_setting() ← 按群覆盖实现
```
**检查项**：schema hint 是设计契约，变更 schema hint = 变更设计契约

## 代码质量信号

| 信号 | 含义 | 审查动作 |
|------|------|----------|
| "一致性"缺失 | 同模块两种实现模式 | 主动追问：有意设计还是历史遗留？ |
| 类型注解不一致 | 代码演进历史痕迹 | 要求统一到最新风格 |
| 防御性重复检查 | 可能有竞争条件 | 深入检查并发安全性 |

## 并发安全审查要点

在异步/协程环境中：
- 自增 + 检查 + 重置 + 保存 是否原子
- 批量保存与单次保存是否有互斥保护
- 计数器操作是否需要锁保护

### 计数器重置顺序风险
```python
# 错误顺序（本次修复前）
save_stats() 失败 → _msg_save_counter = 0 已执行 →
下一批从49开始 → 第50条才触发保存 → 丢失一批

# 正确顺序
save_stats() 失败 → _msg_save_counter = 0 未执行（仍为49）→
下一批49+1=50 → 立即触发保存 → 触发重试
```

## PR描述审查锚点使用

高质量PR描述应包含：
- [ ] 权限矩阵（命令级别权限定义）
- [ ] API限制说明
- [ ] 变更统计（文件数、代码行数）
- [ ] 验证命令

审查者应将PR描述作为"承诺清单"，逐项验证实现。

## 经验教训精选

1. **Quick策略与全量审查的界定**：首次审查必须为full，Quick仅适用于依赖已有审查结论的增量变更

2. **PR描述与代码变更的差异处理**：发现不一致时，明确标注"PR描述未涵盖以下变更"，暂定"全部变更"为审查范围边界

3. **建议正确性取决于功能意图**：
   - ❌ "消息不丢失"是假设而非事实
   - ✅ 需先确认功能设计意图（"记录"是否独立于"功能开关"）

4. **schema hint是设计契约**：变更需与代码变更同等重视

5. **配置迁移的隐形风险**：读取路径变更后，旧群组配置残留既不生效也不会被清除
