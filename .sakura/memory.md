# 项目记忆

累计反思 11 次

## 仓库背景

仓库 `mjy1113451/astrbot_plugin_gm` 是 AstrBot 群管理类插件，Issue 常涉及命令解析、群管理权限、按群配置、配置 schema 与 README 同步。注意 Issue 中可能出现旧插件名或相近插件名（如 `astrbot_plugin_group_admin`），分析时需确认与当前仓库/插件注册名是否一致，避免把推断写成事实。

## Issue 分析经验

### 1. 分类与优先级

- 明确运行时报错、命令参数类型错误、用户反馈“更新后仍存在”、命令期望/实际行为不一致时，主分类应为 `bug`；若属于命令参数解析，可辅助考虑 `command`、`parser`、`compatibility`、`regression/not fixed`、`needs info`。
- 权限/配置粒度调整，如“头衔、管理、踢人权限按群独立配置”，通常归为 `enhancement`；但若代码已有 `group_overrides/get_group_setting` 能力、只是 schema/UI/文档仍表现为全局配置，则可归为 `bug` + `configuration/schema/ui/documentation`。
- `medium` 通常适用于：核心命令局部不可用、权限配置影响多群使用但非阻断、配置展示误导多群管理。若启动/加载失败、安全越权、严重误撤大量消息，应考虑 `high`；若只是说明文字不清，可降为 `low-medium`。
- 标题中 `[bug][medium]`、`[enhancement][medium]` 是重要信号，但必须结合正文和代码验证。标题为空、“。”或结构化字段失败时，仍应从正文提炼分类、优先级和标题，不能降级为 `other` 或标签置空。

### 2. AstrBot 命令参数问题

- 对 `@filter.command(...)` 命令，必须区分错误发生在启动/插件加载/命令注册阶段，还是用户调用后的业务函数阶段。若 AstrBot 根据函数注解提前转换参数，函数体内 `try/except int(count)` 无法兜底。
- 遇到 `参数 count 类型错误`、`count(int)=0`、用户称“更新后仍存在”，应优先检查命令函数签名、类型注解和默认值，如 `count: int = 0`、`count: int = 1`，同时确认触发命令、完整堆栈、AstrBot 版本、插件版本/commit、是否旧缓存，并追踪最近相关 PR/commit，判断是修复方向错误还是覆盖入口不全。
- 修复方向通常是命令入口用 `str`/可选原始参数接收，在函数内部统一转换、校验并返回友好提示，同时保留无参默认语义。需明确 `0`、空字符串、`None`、负数、过大值等边界含义。
- 不要只修复单一入口；应全局搜索相同模式，如 `count: int`、`: int =`、`filter.command`，检查 `/撤回`、`/撤回用户` 等复制粘贴式问题，以及 `int`、`bool`、`float`、`At` 等可能被框架预解析的参数。
- 测试需覆盖：无参数、正常数字、非法字符串、空字符串、负数、过大数值、引用消息、@用户+数量、不同 AstrBot 版本。

### 3. 撤回命令与消息历史

- `/撤回 1` 在群管理语境中通常意味着撤回“当前命令之前的 1 条消息”，不是撤回指令自身。若用户描述“撤回了指令本身”，即使正文很短也是明确 bug，标题可改为：`/撤回 1 应撤回上一条消息而非指令本身`。
- 分析 `/撤回 N` 时检查 `recall_cmd`：是否先撤回触发命令自身、是否把当前 `event.message_id` 纳入候选、count 是否从目标消息开始计数、历史消息排序是正序还是倒序、当前指令是否出现在历史中。
- 修复建议应是先获取群消息历史并过滤当前命令 message_id，只撤回命令之前 N 条可撤回消息；历史接口不可用时返回明确提示，通常不要回退为撤回指令自身以免误报成功。
- OneBot/适配器风险：`get_group_msg_history` 可能不可用，返回顺序/字段结构/message_id 类型不同；机器人可能因权限不足、消息超时、非自身消息而无法撤回；引用撤回语义应优先且不能被破坏。
- 测试至少覆盖 `/撤回 1`、`/撤回 2/3`、无参默认、回复消息撤回、消息不足、权限不足、历史接口不可用、群聊/私聊差异。

### 4. 权限与按群配置需求

- “按群独立配置”通常不只是新增配置项，而是权限模型调整。需区分：功能权限、配置权限、插件管理权限；遵循最小权限原则，避免用泛化“插件管理员”替代具体动作授权。
- 本仓库相关关键点包括：`plugin_admins`、`group_overrides`、`get_group_setting`、`title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`，以及 `has_title_admin_rights`、`has_kick_admin_rights`、`has_group_admin_rights` 等权限函数。
- 可行性评估应检查：是否已有全局配置项、是否已有按群覆盖读取路径、权限函数是否统一使用该读取逻辑、命令是否操作正确层级、状态/帮助输出是否一致、`_conf_schema.json` 和 README 是否同步。
- 删除或废弃旧“按群插件管理”时要谨慎：考虑旧配置迁移、兼容读取、deprecated 过渡、命令语义变化、用户习惯破坏。
- 风险重点：空列表是覆盖为空还是回退全局、超级管理员/群管理员继承规则、多群隔离、安全误授权、合法管理员失效、命名混淆（如 `group_admins` 与 `group_admin_admins`）。
- 权限类改动必须建议测试：全局配置生效、按群覆盖、未配置回退、空列表覆盖、多群隔离、普通用户不得获得踢人/管理/头衔权限、旧配置升级后行为。

### 5. 配置 schema/UI 与禁言踢出阈值

- 按群配置类 Issue 要区分三层：业务读取层是否走 `get_group_setting`；命令管理层是否能写入/查看/清除 `group_overrides[group_id][key]`；配置展示/UI/schema/README 是否表达“全局默认 + 群级覆盖”。
- 对 `mute_kick_threshold`，若 `_record_mute_and_maybe_kick` 已通过 `get_group_setting(group_id, "mute_kick_threshold", 0)` 读取，则核心逻辑可能已支持群级阈值，问题更可能在 `_conf_schema.json`、AstrBot 配置 UI、`config_cmd` 或 README 示例未暴露/未解释群级覆盖。
- 不要把顶层配置项存在直接视为 bug。保留全局默认值通常合理；更稳妥做法是将 schema 描述改为“全局默认禁言踢出阈值”，说明可被群级覆盖，并在状态/配置展示中显示“有效值 + 来源（群级覆盖/全局默认）”。不宜简单删除全局项，避免迁移和兼容风险。
- 需先确认用户说的“还在插件配置设置”指 AstrBot 控制台配置 UI，还是插件内 `/配置`/状态命令；两者修复路径不同。若框架 UI 不支持动态群号键，应通过 schema 描述、群级命令和 README 示例弥补。
- 覆盖语义要特别关注 `0`、空值、缺失值：`0` 很可能表示关闭自动踢出，必须能显式覆盖全局值，不能被 `dict.get` 或假值判断误当成未配置回退。
- 测试：全局阈值、按群覆盖、未配置回退、覆盖为 0、不同群隔离、状态展示来源、旧配置兼容。

### 6. 标签、标题与重复检测

- 标签推荐应优先贴合仓库现有标签；未知标签体系时也应给出通用候选并注明需映射，不能因不确定而留空。撤回类可候选 `bug, command, recall/message-recall, group-management, onebot, message-history`；配置类可候选 `bug, configuration, schema, group-config/per-group-config, ui/config-ui, documentation`。
- 标题为空或无意义时必须改写；标题应保留原始错误片段或具体对象。示例：`修复 count(int)=0 导致的命令参数类型错误`、`/撤回 1 应撤回上一条消息而非指令本身`、`禁言踢出阈值按群覆盖后仍显示为全局配置`、`支持头衔、管理和踢人权限按群独立配置`。
- 避免把推断写成事实。若 Issue 未明确命令来源，可写“疑似撤回命令/需确认”，并要求补充完整日志、触发命令、AstrBot 版本、插件版本、是否启动即报错。
- 重复检测不能只依赖标题。同样涉及 `/撤回` 不一定重复，需区分参数解析错误、撤回自身、权限不足、数量错误、引用逻辑错误、API 不支持。只有症状、触发路径和修复点高度一致才判重复，否则标关联。
- 缺少历史 Issue 列表时，“未检测到重复”只能表述为“暂未发现”。检索关键词：`count(int)=0`、`参数 count 类型错误`、`撤回指令本身`、`/撤回 1`、`recall_cmd`、`recall_user_cmd`、`get_group_msg_history`、`禁言阈值`、`mute_kick_threshold`、`group_overrides`、`配置显示`、`按群配置`。

### 7. 流程注意

- 不应因结构化输出字段（如 milestone 必须单行、缺少 `<SUGGESTED_TITLE>`）校验失败，就把分类降为 `other`、标签置空、可行性写“无法评估”。字段失败应局部降级，保留可判断的信息。
- 对信息不足的 Issue，仍应给出有条件的可行性判断：说明需要补充哪些证据，以及在常见代码结构下的预估工作量与风险。
- 对“版本已更新仍存在”的问题，应追踪最近相关 commit/PR：可能是修复方向错误、覆盖入口不全、插件目录/缓存未更新，不能仅重复原修复建议。
