## 一、审查策略规范

### Quick 策略使用边界
| 场景 | 规范要点 |
|------|----------|
| **适用** | 简单逻辑变更、配置值调整、增量修复已有问题 |
| **不适用** | 涉及状态机/计数器、并发安全、设计意图变更 |

### Quick 策略必须验证的文件
- PR描述明确列出的文件（如 `README.md`、`_conf_schema.json`）
- 文档删除命令必须同步 README 示例段落
- **不能默认聚焦单一文件而忽略声明变更**

## 二、核心审查规则

### R1. 增量审查上下文关联验证
| 检查项 | 说明 |
|--------|------|
| 确认本次变更解决了之前提出的问题 | 检查是否引用了之前 review |
| 增量变更是否依赖其他未变更的代码 | 识别隐含依赖 |
| 标注审查范围仅限于[具体行号] | 明确边界 |

### R2. 持久化策略一致性
| 检查项 | 说明 |
|--------|------|
| 同一模块内存在多个持久化方法 | 需说明选择该模式的原因 |
| 批量保存的阈值是否经过论证 | 50条/100条是否有依据 |
| 各方法的保存时机是否一致 | 不一致时追问设计意图 |

### R3. 异步环境计数器安全
- 自增 + 检查 + 重置 + 保存 是否原子
- 批量保存与单次保存是否有互斥保护
- 多协程并发调用时的竞争条件

### R4. PR描述完整性校验
| 检查项 | 说明 |
|--------|------|
| 审查摘要中的变更点 ≥ PR描述中的变更点 | 遗漏项标记为"描述缺失" |
| 新增功能/配置/命令必须在PR描述中列出 | 缺失则要求澄清 |
| PR描述提到的文件与实际变更文件一致 | 差异原因需明确标注 |

### R5. 缓存安全性检查
| 检查项 | 说明 |
|--------|------|
| 新增本地缓存是否定义容量上限 | deque(maxlen=N) |
| 是否有TTL机制或显式清理函数 | 内存泄漏风险 |
| enabled=false时的预期行为 | "不记录" vs "记录但不提供功能" |

### R6. 配置变更全面检查
| 变更类型 | 检查项 |
|----------|--------|
| 新增配置项 | 默认值安全性 |
| 删除配置项 | breaking-change + 迁移路径 |
| 读取路径变更 | 旧配置迁移、回退逻辑 |
| 覆盖能力变更 | schema hint + 文档同步 |

## 三、代码模式库

### 3.1 持久化模式
```
// 即时保存（高可靠性，高 I/O）
_record_violation() → 修改 stats → save_stats()

// 批量保存（低 I/O，低可靠性）
_increment_message_count() → [计数器=50?] → save_stats()
```

### 3.2 配置读取模式
```
// 全局配置
self.config.get(key)

// 群组覆盖
get_group_setting(group_id, key)
```

### 3.3 计数器重置顺序（重要）
```python
# 错误：先重置后保存
save_stats()      # 失败 → 计数器已重置 → 丢一批计数
_msg_save_counter = 0

# 正确：先保存后重置
save_stats()      # 失败 → 计数器保持49 → 下次立即触发重试
_msg_save_counter = 0
```

### 3.4 缓存写入时序
```
缓存写入位置取决于功能设计意图：
- 若'记录'独立于'功能开关' → 置于 enabled 检查之前
- 若'记录'是'功能'的一部分 → 置于 enabled 检查之后
审查者需先确认设计意图再提出建议
```

## 四、架构观察要点

| 关注点 | 审查提示 |
|--------|----------|
| **一致性** | 发现同一模块内有两种实现模式时，主动追问是有意设计还是历史遗留 |
| **类型注解** | 定义处与使用处应保持一致，Dict[str, deque] vs 类名 |
| **schema hint** | `_conf_schema.json` 的 `group_overrides` 是设计契约 |
| **文档同步** | 功能变更必须同步 README，删除命令需同步示例段落 |

## 五、问题严重程度判断

| 严重度 | 适用场景 | 示例 |
|--------|----------|------|
| **Major** | 功能破坏、潜在数据丢失、安全漏洞 | 缓存写入时序错误 |
| **Minor** | 代码风格、命名语义、类型注解 | message_id vs message_seq |
| **Comment** | 文档遗漏、用户体验优化建议 | 示例段落缺失 |
| **request_changes** | 仅适用于功能性缺失，不适用于纯文档问题 | - |

## 六、经验教训精选

### 6.1 增量审查的"只见树木"风险
- 审查者若查看完整方法，可能发现增量变更的隐含依赖
- 计数器重置顺序取决于"50条阈值"设计意图——增量审查难以察觉
- **涉及状态机/计数器/标志位的变更，应扩展至完整方法上下文**

### 6.2 "消息不丢失"是假设而非事实
- `dm_history_recall=false` 可能是设计意图：用户不想被记录
- 建议需基于功能设计意图，而非通用安全原则
- 审查前必须明确确认功能设计目标

### 6.3 PR描述作为审查范围锚点
- PR描述质量极高时（权限矩阵、API限制、验证命令），充分利用其完整性
- 审查摘要应作为"承诺清单"，逐项验证实现
- 声明式变更（PR描述明确列出文件）需全部验证

### 6.4 文档问题与代码问题分级处理
| 问题类型 | 建议处理 |
|----------|----------|
| 功能性文档缺失（命令表） | `request_changes` |
| 示例段落遗漏 | `comment` 级别 |

### 6.5 防御性审查：计数器重置顺序
```python
# 重置顺序错误的潜在后果演示
save_stats() 失败 → _msg_save_counter = 0 已执行
下一批消息从 49 开始计数 → 第 50 条才触发保存
# 结果：丢失一批消息的计数
```
