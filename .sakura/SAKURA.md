# 项目概述：mjy1113451/astrbot_plugin_gm

> 累计反思 12 次

## 1. 项目简介

`astrbot_plugin_gm` 是 AstrBot 的 QQ 群管理插件，面向 QQ 群聊管理场景，提供插件管理员维护、禁言/解禁、踢人、撤回消息、群昵称、专属头衔、精华消息、官方群管理员设置等能力。

## 2. 技术栈与结构

- **语言**：Python 3.10+
- **框架**：AstrBot 插件体系
- **平台接口**：aiocqhttp / OneBot 相关 API
- **配置**：`_conf_schema.json` + `main.py` 运行时读取
- **许可证**：MIT

```text
astrbot_plugin_gm/
├── main.py              # 插件主逻辑：命令、权限、配置、OneBot API 兼容
├── metadata.yaml        # 插件元信息
├── _conf_schema.json    # AstrBot 配置 Schema
├── README.md            # 安装、配置、命令、权限说明
├── docs/                # 补充文档
└── .sakura/             # 项目记忆、规则与反思
```

主要中文命令：`/设管`、`/取管`、`/禁言`、`/解禁`、`/禁我`、`/踢`、`/头衔`、`/取消头衔`、`/设管理`、`/取消管理`、`/设精`、`/设群昵称`、`/改昵称`、`/撤回`、`/撤回用户`。

## 3. 权限与配置模型

1. **插件管理员**：由 `plugin_admins` 或 `/设管` 动态维护；群主默认具备插件管理员身份。
2. **QQ 官方权限**：禁言、踢人、撤回、设精、设置管理员、设置头衔等还依赖机器人在群内的官方权限和目标成员身份层级。
3. **专项权限/按群覆盖**：反思多次提到代码中可能存在 `title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`、`group_overrides`、`get_group_setting` 以及 `has_title_admin_rights`、`has_kick_admin_rights`、`has_group_admin_rights` 等机制。权限需求应先检查这些入口，避免只改命令层。
4. **全局默认 + 群级覆盖**：多群配置应明确缺省回退、空列表/空对象/`0` 的语义。特别是 `0` 可能是合法配置（如关闭阈值），不能被误当作缺失而回退。

常见配置项：`show_recall_notice`、`reject_re_add`、`plugin_admins`；反思中还重点出现 `mute_kick_threshold` 与 `group_overrides`。

## 4. 近期反思沉淀

### 4.1 `/撤回` count 参数解析（Issue #106）

- AstrBot 可能在调用命令函数前按类型注解转换参数；若签名是 `count: int = ...`，非法输入的错误可能发生在函数体外，内部 `try/except int(count)` 捕获不到。
- 稳健策略：复杂命令入口用 `str` 或原始消息接收，再在函数内统一解析、校验并给友好提示。
- 同类入口要一起排查：`recall_cmd`、`recall_user_cmd`、所有 `: int =`、`count: int` 命令参数。
- “版本已更新仍存在”不一定是回归；除非确认旧版本正常新版本异常，否则谨慎标 `regression`。

测试重点：`/撤回`、`/撤回 3`、`/撤回 abc`、引用撤回、带 @ 用户和数量的撤回用户场景、空字符串、负数、过大数字、中文数字等。

### 4.2 `/撤回 1` 错误撤回指令自身（Issue #109）

- 用户期望 `/撤回 1` 撤回“当前指令上方一条消息”，实际撤回了 `/撤回 1` 指令本身，应归类为 `bug`，优先级 `medium`。
- 关键逻辑风险：若实现先撤回触发命令自身，再获取历史消息，`count=1` 时会直接达到数量并返回，必然撤错目标。
- 更合理语义：先获取群历史，过滤当前命令 `message_id`，只撤回命令之前的 N 条可撤回消息。
- 历史接口不可用时应返回明确提示，不应回退成“撤回指令自身”并误报成功。
- 需保持引用撤回优先级，不能破坏 `/撤回` 引用目标消息的旧语义。
- OneBot 历史消息接口风险：可能不支持、返回顺序不同、字段结构不同、当前指令是否包含不一致、`message_id` 类型差异、消息超时或权限不足导致撤回失败。

重复检测关键词：`/撤回 1`、`撤回指令本身`、`撤回上一条消息`、`recall_cmd`、`get_group_msg_history`、`message_id`、`count`。同样涉及 `/撤回` 不一定重复，需比较症状、触发路径和修复点。

### 4.3 `/撤回 @用户 N` 未触发按用户撤回（Issue #110）

- 用户输入 `/撤回 @用户 1` 后落入普通 `/撤回` 兜底提示，未进入按用户撤回逻辑，应按 `bug` 或命令解析/UX 缺陷处理，优先级 `medium`。
- 该问题不是“按用户撤回能力完全缺失”：代码中可能已有 `/撤回用户 @用户 N`（`recall_user_cmd`）能力，核心是 `/撤回` 短命令未路由到同一逻辑，或文档/帮助提示不清。
- 修复建议优先抽共享 helper，如 `parse_recall_count`、`recall_recent_messages`、`recall_user_messages`，避免在 `recall_cmd` 与 `recall_user_cmd` 复制逻辑后行为分叉。
- `recall_user_cmd` 若仍使用 `count: int = 1`，也应改为字符串/原始参数入口，统一内部解析。
- `@用户` 不应简单按空格切分；昵称可能含空格，应优先依赖 AstrBot/OneBot at segment、user_id 或现有 `_extract_at_qq(raw)`。
- 解析顺序需避免破坏原有 `/撤回 N`、无参引用撤回和 `/撤回用户 @用户 N` 行为；多个 @、无 @、非法数量、负数、0、数量过大、非群聊、历史接口不可用、权限不足都要有明确提示。

查重关键词：`/撤回 @用户`、`/撤回用户`、`@用户 N`、`recall_cmd`、`recall_user_cmd`、`_extract_at_qq`、`count 类型错误`、`请引用一条消息后使用该指令`。

### 4.4 `/取消头衔` 提示成功但未清空（Issue #111）

- 用户执行 `/取消头衔 @某人`，机器人返回“取消头衔成功”，但实际群头衔未取消，应归类为 `bug`，优先级 `medium`；若确认在主流适配器（如 NapCat）稳定复现，可提高处理优先级。
- 关键链路：`/取消头衔` → `unset_group_title_cmd` → `_clear_group_title` → `set_group_special_title` → `special_title=""`、`duration=-1` → 根据 API 返回提示成功。
- 高风险点是 OneBot 适配器兼容：空字符串是否表示清空、`duration=-1/0/不传` 的语义、API 返回 ok 是否真实生效，不同 NapCat/Lagrange/go-cqhttp 可能不同。
- 还必须排查权限与平台限制：机器人是否为群主/管理员、目标是否群主或权限更高、是否有设置头衔权限、QQ 客户端缓存或接口延迟。
- 修复不应只改成功文案；应验证参数组合并尽量通过 `get_group_member_info` 回读 `special_title`。但回读也可能受缓存/字段差异影响，必要时使用短延迟或提示“已发送取消请求，请稍后确认”。
- 群管理类“返回成功但实际未生效”要形成固定检查链：命令解析 → 权限判断 → API 参数 → 适配器兼容 → API 返回值 → 状态回读 → 用户提示。

查重关键词：`取消头衔`、`头衔没取消`、`special_title`、`set_group_special_title`、`duration=-1`、`NapCat`、`OneBot`、`成功但没生效`。

### 4.5 禁言踢出阈值按群配置/展示（Issue #107）

- 核心通常不是禁言统计逻辑坏了，而是“配置 UI/Schema/展示”没有体现“全局默认 + 群级覆盖”。可归为 `bug`，辅以 `configuration`、`schema`、`ui/config-ui`、`documentation`、`group-config`。
- 线索：`get_group_setting`、`group_overrides`、`_record_mute_and_maybe_kick` 可能已支持按群读取 `mute_kick_threshold`，但 `_conf_schema.json` 或配置命令仍把它展示为顶层全局项。
- 不应简单删除全局 `mute_kick_threshold`；更稳妥是保留为“全局默认禁言踢出阈值”，并说明可由群级覆盖。
- 展示建议显示“有效值 + 来源”，例如“禁言踢出阈值：3，来源：当前群覆盖；全局默认：5”。显式配置 `0` 应表示关闭/覆盖，不能被当作未配置。

相关修改需同步 `_conf_schema.json`、README、帮助文本、配置查看/设置/清除命令和测试。

### 4.6 专项权限按群配置（Issue #105 经验）

- “头衔、管理、踢人等专项权限按群独立配置”更像权限模型增强，通常标 `enhancement`。
- 重点是从泛化“按群插件管理员”转向按动作授权，符合最小权限原则。
- 需兼容旧配置：如改变 `group_admins` 语义，应考虑迁移、废弃期或兼容读取。
- 若已有 `group_overrides` 和 `get_group_setting`，应复用并明确缺省、空列表、全局回退和多群隔离。
- 敏感操作（踢人、设/取消管理、头衔）必须做越权和误授权测试。

### 4.7 Issue 分析与标签经验

- 标题为“。”、“，”或信息很少时，不能依赖标题分类；应基于正文错误文本、复现命令和代码线索检索。
- 标题带 `[bug][medium]`、`[enhancement][medium]` 可作为信号，但仍需结合正文和代码验证。
- 结构化输出校验失败只应影响对应字段，不能导致已明确的 bug 被降级为 `other`、标签为空或可行性“无法评估”。
- 标签应优先匹配仓库实际标签体系；未知时给通用主标签，并列出候选标签，如 `command`、`parser`、`group-management`、`compatibility`、`needs-info`。
- 重复检测要谨慎表述“暂未发现”，并给检索关键词；同命令不等于同问题。
- 建议标题应保留核心触发条件，如 `/撤回 1`、`/撤回 @用户 N`、`/取消头衔`、`mute_kick_threshold`，不要泛化到丢失定位信息。

## 5. 开发约定与注意事项

- 插件逻辑集中在 `main.py`，修改时要全局搜索相似命令模式，避免复制粘贴式遗漏。
- 配置定义、业务逻辑、README、帮助文本和配置展示必须同步。
- 管理员 QQ 号建议按字符串处理，避免数字精度或格式问题。
- QQ 群管理操作依赖平台 API、适配器实现和机器人群权限；必须处理接口失败、权限不足、消息超时、缓存延迟和异常返回。
- 权限类改动必须覆盖：全局配置、群级覆盖、命令入口、权限判断函数、文档说明和回归测试。
- AstrBot API/命令解析兼容问题，应先确认框架版本、插件版本/commit、适配器类型、完整堆栈和最小复现命令，并区分插件启动、命令注册、命令调用、特定输入触发四个阶段。
