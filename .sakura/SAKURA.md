# 项目概述：mjy1113451/astrbot_plugin_gm

> 累计反思 6 次

## 1. 项目简介

`astrbot_plugin_gm` 是一个用于 AstrBot 的 QQ 群管理插件，提供插件管理员管理、禁言、踢人、撤回消息、设置群昵称、设置头衔、设置精华消息等常用群管能力。项目主要面向 AstrBot 机器人环境下的 QQ 群聊管理场景。

## 2. 技术栈

- **主要语言**：Python 3.10+
- **插件框架**：AstrBot 插件体系
- **QQ 平台接口**：aiocqhttp / OneBot 相关 API
- **配置方式**：`_conf_schema.json` 定义配置项，运行时由 `main.py` 读取
- **许可证**：MIT License

## 3. 核心结构

```text
astrbot_plugin_gm/
├── main.py              # 插件主逻辑：命令、权限判断、API 调用兼容
├── metadata.yaml        # AstrBot 插件元信息
├── _conf_schema.json    # 配置 Schema
├── README.md            # 安装、配置、命令和权限说明
├── docs/                # 补充文档

```

### main.py 重点能力

实现的主要中文斜杠命令包括：

- `/设管`、`/取管`：维护插件管理员
- `/禁言`、`/解禁`、`/禁我`
- `/踢`
- `/头衔`、`/取消头衔`
- `/设管理`、`/取消管理`
- `/设精`
- `/设群昵称`、`/改昵称`
- `/撤回`：引用撤回或撤回最近 N 条消息

## 4. 权限与配置模型

项目采用多层权限设计：

1. **插件管理员**
   - 由 `plugin_admins` 配置或 `/设管` 动态维护。
   - 群主默认具备插件管理员身份。
   - 可使用大部分管理命令。

2. **QQ 官方群权限**
   - 禁言、踢人、撤回、设置管理员、设置精华等操作还依赖机器人本身在 QQ 群中的官方权限。

3. **专项权限管理员（代码中已有/需关注）**
   - 反思中多次提到代码可能存在 `title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`、`group_overrides`、`get_group_setting` 以及 `has_title_admin_rights`、`has_kick_admin_rights`、`has_group_admin_rights` 等机制。
   - 后续权限需求应优先检查这些入口，避免只改命令层而遗漏权限判断函数。

4. **按群覆盖配置**
   - 多群场景下应明确全局配置与群级覆盖的关系。
   - 特别要定义：未配置时是否回退全局、空列表是否表示显式禁用/覆盖、多群之间是否完全隔离。

常见配置项：

- `show_recall_notice`：撤回后是否发送提示
- `reject_re_add`：踢人后是否拒绝重新加群
- `plugin_admins`：插件管理员 QQ 列表（建议保存为字符串数组）

## 5. 近期反思沉淀

### 5.1 AstrBot 命令参数解析问题

Issue #106 反思集中在 `/撤回` 或相关命令的 `count` 参数类型错误：

- 若命令函数签名使用 `count: int = 0`、`count: int = 1` 等注解，AstrBot 可能在调用函数前根据类型注解做参数转换。
- 如果错误发生在框架解析阶段，函数体内的 `try/except int(count)` 无法捕获。
- 修复不应只在函数体内兜底，应优先检查 `@filter.command(...)` 装饰函数的签名、默认值和注解。
- 更稳健的策略：命令入口用 `str` 或可选原始参数接收用户输入，再在函数内部统一解析、校验和返回友好提示。
- 同类问题要全局排查，不要只修一个入口；例如同时检查 `recall_cmd`、`recall_user_cmd` 以及所有 `: int =`、`count: int` 的命令参数。

测试应覆盖：

- `/撤回` 无参数
- `/撤回 3`
- `/撤回 abc`
- 引用消息撤回
- 带 @ 用户和数量的撤回用户场景
- 空字符串、负数、过大数字、中文数字等边界输入

分析此类 Issue 时需先确认错误发生阶段：插件启动、命令注册、命令调用，还是特定输入触发。若导致插件整体加载失败，优先级应高于仅影响单条命令。

### 5.2 按群专项权限配置需求

Issue #105 反思集中在“将头衔、管理、踢人等专项权限调整为按群独立配置”：

- 该类 Issue 应归为 `enhancement`，更细可标为配置/权限增强。
- 重点不是简单新增配置项，而是权限模型调整：从泛化的“按群插件管理员”转向按动作授权的专项权限，符合最小权限原则。
- 需重点关注兼容性：如果删除或改变 `group_admins` 等旧配置语义，应考虑迁移、废弃期或兼容读取，避免旧用户权限突然失效。
- 需同步修改 `_conf_schema.json`、README、帮助文本、状态展示和相关管理命令。
- 如果已有 `group_overrides` 和 `get_group_setting`，应复用现有按群覆盖机制，但要明确空列表、缺省值和全局回退语义。
- 涉及踢人、设管理、取消管理、头衔等敏感操作时，应额外做安全测试，防止越权或误授权。

建议相关标题更具体，例如：

- `支持头衔、管理、踢人等专项权限按群独立配置`
- `调整按群权限配置：移除插件管理，改为头衔/管理/踢人专项配置`

### 5.3 Issue 分析与标签经验

- 标题为“。”或信息极少时，不能依赖标题做分类、重复检测或标题保留，应基于正文错误文本和代码线索检索。
- 对带 `[bug][medium]`、`[enhancement][medium]` 的标题，可将其作为高置信度信号，但仍要结合正文和代码验证。
- 标签推荐应优先匹配仓库实际标签体系；若未知，可给通用主标签，并列出可选标签。
- `版本已更新，问题还存在` 不一定等于回归；除非确认旧版本正常、新版本异常，否则谨慎标 `regression`。
- 结构化输出某字段校验失败（如 milestone 必须单行）不应导致分类、标签、可行性等有效信息整体丢失。
- 重复检测应使用错误文本和语义关键词，例如 `count(int)=0`、`参数 count 类型错误`、`group_overrides`、`插件管理`、`踢人权限`、`按群配置`。

## 6. 开发约定与注意事项

- 插件逻辑集中在 `main.py`，适合小型插件，但修改时要全局搜索相似命令模式，避免复制粘贴式遗漏。
- 配置定义与业务逻辑需保持同步：改配置必须同步 `_conf_schema.json` 和 README。
- 管理员 QQ 号建议按字符串处理，避免数字精度或格式问题。
- QQ 操作依赖平台 API 和机器人群权限，需处理接口失败、权限不足和异常返回。
- 权限类改动必须同时覆盖：全局配置、按群配置、命令入口、权限判断函数、文档说明和回归测试。
- 对 AstrBot API/命令解析兼容问题，应优先确认框架版本、插件版本/commit、完整堆栈和最小复现命令。
