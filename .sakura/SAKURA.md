## 1. 项目简介

`astrbot_plugin_gm` 是一个用于 AstrBot 的 QQ 群管理插件，提供插件管理员管理、禁言、踢人、撤回消息、设置群昵称、设置头衔、设置精华消息、设置/取消群管理员等常用群管能力。插件面向 QQ 群聊管理场景，强调中文命令、权限控制与 AstrBot/OneBot API 兼容。

## 2. 技术栈

- **主要语言**：Python 3.10+
- **插件框架**：AstrBot 插件体系
- **QQ 平台接口**：aiocqhttp / OneBot 相关 API
- **配置方式**：`_conf_schema.json` 定义配置项，运行时由 `main.py` 读取
- **许可证**：MIT License
- **运行场景**：AstrBot 机器人环境下的 QQ 群聊管理

### main.py

实现主要群管命令与事件处理，包括：

- `/设管`、`/取管`
- `/禁言`、`/解禁`
- `/踢`
- `/头衔`、`/取消头衔`
- `/设管理`、`/取消管理`
- `/设精`
- `/设群昵称`、`/改昵称`
- `/撤回`
- `/禁我`

同时负责权限判断、配置读取、命令参数解析、平台 API 调用与异常处理。

### _conf_schema.json

定义插件配置项。README 当前公开配置包括：

- `show_recall_notice`：撤回后是否发送提示
- `reject_re_add`：踢人后是否拒绝重新加群
- `plugin_admins`：插件管理员 QQ 列表

近期反思还显示代码中可能已有或计划涉及更细粒度权限配置，如 `title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`、`group_overrides` 等；更新权限功能时必须同步 Schema、README 和默认配置。

## 4. 权限模型与配置约定

项目采用两层权限设计：

1. **插件管理员**
   - 由 `plugin_admins` 配置或 `/设管`、`/取管` 动态维护。
   - 群主默认具备插件管理员权限。
   - 可使用插件大部分管理命令。

2. **QQ 群官方权限**
   - 某些操作要求机器人本身拥有 QQ 群管理员/群主权限。
   - 例如禁言、踢人、撤回消息、设置群管理员、设置精华消息等。

配置约定：

- 管理员 QQ 号宜以字符串数组保存，避免数字精度或格式问题。
- 布尔配置应使用明确语义命名，如 `show_recall_notice`、`reject_re_add`。
- 多群场景下应优先考虑“全局默认 + 按群覆盖”的结构。
- 若使用 `group_overrides`，需要明确：未配置时是否回退全局、空列表是否表示覆盖为空、群主/超级管理员是否始终拥有权限。

## 5. 重要开发经验与近期反思

### 5.1 AstrBot 命令参数解析风险

近期 Issue #106 反复暴露 `count` 参数类型错误：用户反馈“版本已更新，问题还存在”，报错类似 `参数 count 类型错误`、`count(int)=0`。分析认为核心风险在于：

- `@filter.command(...)` 命令函数若写成 `count: int = 0`、`count: int = 1`，AstrBot 可能在进入函数体前按注解自动转换参数。
- 如果转换发生在框架解析阶段，函数体内的 `try/except int(count)` 无法捕获错误。
- 同类问题不应只修一个入口，应同时检查 `recall_cmd`、`recall_user_cmd` 以及所有相似 `count`/数字参数命令。

建议修复模式：

- 对用户输入不可靠或可选的命令参数，优先用 `str` 或原始可选参数接收，再在函数内部手动解析。
- 统一处理 `None`、空字符串、非法文本、负数、过大数字等边界值。
- 对非法输入返回友好提示，避免框架级类型错误直接暴露给用户。
- 回归测试至少覆盖：`/撤回`、`/撤回 3`、`/撤回 abc`、引用撤回、`/撤回用户 @某人 5`、空格和异常输入。

未来排查类似问题时，应优先检查：

```bash
grep -R "filter.command" .
grep -R ": int =" .
grep -R "count: int" .
```

并区分错误发生阶段：插件启动/加载、命令注册、命令调用、特定参数输入。

### 5.2 Issue #106 分析注意事项

- 分类为 `bug` 基本准确，优先级通常为 `medium`；若导致插件整体加载失败，可升为 `high`。
- 需确认报错插件名与仓库是否一致：Issue 中可能出现 `astrbot_plugin_group_admin`，当前仓库为 `astrbot_plugin_gm`，可能是改名、注册名差异、用户发错仓库或框架/依赖问题。
- 标签除 `bug` 外，可按仓库体系考虑 `needs info`、`compatibility`、`command`、`parser`；`regression` 只有在确认旧版本正常、新版本异常时再加。
- 对标题为空或无意义的 Issue，重复检测应基于错误正文关键词，如 `count(int)=0`、`参数 count 类型错误`、`撤回`、`filter.command`。

### 5.3 按群专项权限配置需求

近期 Issue #105 反复讨论“将专项权限改为按群独立配置”，涉及头衔、管理、踢人等敏感权限。该类需求应归为 `enhancement` / 功能增强，而不是 `other`。优先级 `medium` 合理，因为它影响多群管理隔离和权限安全，但通常不是阻塞性 bug。

实现关注点：

- 该需求不只是新增配置项，而是权限模型语义调整。
- 应区分三类权限：功能权限、配置权限、插件管理权限。
- 建议复用或完善 `group_overrides` 这类“按群覆盖，全局回退”机制。
- 权限函数如 `has_title_admin_rights`、`has_kick_admin_rights`、设置/取消管理相关权限判断应统一走配置读取工具，避免各命令散落读取不同配置。
- 如果用户要求“删除按群插件管理”，实现时要谨慎：更安全的方式可能是保留旧配置/命令并标记弃用，新增专项权限配置和迁移说明。
- 必须同步 `_conf_schema.json`、README、命令帮助和默认配置。

测试重点：

- 全局配置生效。
- 按群覆盖生效。
- 未配置按群项时回退全局。
- 空列表/空配置的语义明确。
- 多群互不影响。
- 普通用户不会误获踢人、头衔、设置管理等敏感权限。
- 旧配置升级后行为可预期。

推荐标题/标签经验：

- 标题宜具体，如“支持按群独立配置头衔、管理员和踢人权限”。
- 标签可考虑：`enhancement`、`configuration`、`permission`、`group-management`、`needs-discussion`；若有破坏性变更再加 `breaking-change`。

### 5.4 Issue 分析流程经验

- 不应因结构化输出字段（如 milestone）校验失败，就把分类降级为 `other` 或丢弃标签、标题、可行性判断。
- 标题中出现 `[enhancement][medium]`、`[bug][medium]` 可作为辅助信号，但必须结合正文和代码验证。
- 标题为“。”等无信息内容时，标题改写通常是必要的；重复检测应依赖正文语义和错误关键词。
- 标签推荐应优先映射仓库已有标签体系；若未知，可给通用候选并说明需对齐。
- 对权限/配置类 Issue，应主动分析兼容迁移、默认值、安全边界和文档同步。
- 对命令解析类 bug，应区分框架解析阶段与业务函数阶段，避免把函数内部兜底当成完整修复。
