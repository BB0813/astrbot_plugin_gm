# 项目概述：mjy1113451/astrbot_plugin_gm

> 累计反思 11 次

## 1. 项目简介

`astrbot_plugin_gm` 是 AstrBot 的 QQ 群管理插件，面向群聊管理场景，提供插件管理员维护、禁言/解禁、踢人、撤回消息、群昵称、头衔、精华消息、官方群管理员设置等能力。

## 2. 技术栈与结构

- **语言**：Python 3.10+
- **框架**：AstrBot 插件体系
- **平台接口**：aiocqhttp / OneBot 相关 API
- **配置**：`_conf_schema.json` + `main.py` 运行时读取
- **许可证**：MIT

```text
astrbot_plugin_gm/
├── main.py              # 插件主逻辑：命令、权限、配置、OneBot API 兼容
├── metadata.yaml        # 插件元信息
├── _conf_schema.json    # AstrBot 配置 Schema
├── README.md            # 安装、配置、命令、权限说明
├── docs/                # 补充文档
└── .sakura/             # 项目记忆、规则与反思
```

`main.py` 中主要中文命令包括：`/设管`、`/取管`、`/禁言`、`/解禁`、`/禁我`、`/踢`、`/头衔`、`/取消头衔`、`/设管理`、`/取消管理`、`/设精`、`/设群昵称`、`/改昵称`、`/撤回`。

## 3. 权限与配置模型

1. **插件管理员**：由 `plugin_admins` 或 `/设管` 动态维护；群主默认具备插件管理员身份。
2. **QQ 官方权限**：禁言、踢人、撤回、设精、设置管理员等还依赖机器人在群内的官方权限。
3. **专项权限/按群覆盖**：反思多次提到代码中可能存在 `title_admins`、`group_admin_admins`、`kick_admins`、`group_admins`、`group_overrides`、`get_group_setting` 以及 `has_title_admin_rights`、`has_kick_admin_rights`、`has_group_admin_rights` 等机制。权限需求应先检查这些入口，避免只改命令层。
4. **全局默认 + 群级覆盖**：多群配置应明确缺省回退、空列表/空对象/`0` 的语义。特别是 `0` 可能是合法配置（如关闭阈值），不能被误当作缺失而回退。

常见配置项：`show_recall_notice`、`reject_re_add`、`plugin_admins`；反思中还重点出现 `mute_kick_threshold` 与 `group_overrides`。

## 4. 近期反思沉淀

### 4.1 `/撤回` count 参数解析（Issue #106）

- 若命令函数签名使用 `count: int = 0`、`count: int = 1`，AstrBot 可能在调用函数前按类型注解转换参数。
- 若错误发生在框架解析阶段，函数体内 `try/except int(count)` 捕获不到。
- 修复应优先检查 `@filter.command(...)` 对应函数签名、默认值和注解，而不是只在函数体内兜底。
- 稳健策略：命令入口用 `str` 或可选原始参数接收，再在函数内部统一解析、校验并给友好提示。
- 同类入口要一起排查，如 `recall_cmd`、`recall_user_cmd`，以及所有 `: int =`、`count: int` 命令参数。
- “版本已更新仍存在”不一定是回归；除非确认旧版本正常新版本异常，否则谨慎标 `regression`，但要追踪近期相关 PR/commit 是否只修了函数体未修签名。

测试重点：`/撤回`、`/撤回 3`、`/撤回 abc`、引用撤回、带 @ 用户和数量的撤回用户场景、空字符串、负数、过大数字、中文数字等。

### 4.2 `/撤回 1` 错误撤回指令自身（Issue #109）

- 用户期望 `/撤回 1` 撤回“当前指令上方一条消息”，实际撤回了 `/撤回 1` 指令本身，应归类为 `bug`，优先级 `medium`。
- 关键逻辑风险：若实现先撤回触发命令自身，再获取历史消息，`count=1` 时会直接达到数量并返回，必然撤错目标。
- 更合理语义：先获取群历史，过滤当前命令 `message_id`，只撤回命令之前的 N 条可撤回消息。
- 历史接口不可用时应返回明确提示，不应回退成“撤回指令自身”并误报成功。
- 需保持引用撤回优先级，不能破坏 `/撤回` 引用目标消息的旧语义。
- OneBot 历史消息接口风险：可能不支持、返回顺序不同、字段结构不同、当前指令是否包含不一致、`message_id` 类型差异、消息超时或权限不足导致撤回失败。

重复检测关键词：`/撤回 1`、`撤回指令本身`、`撤回上一条消息`、`recall_cmd`、`get_group_msg_history`、`message_id`、`count`。同样涉及 `/撤回` 不一定重复，需比较症状、触发路径和修复点。

### 4.3 禁言踢出阈值按群配置/展示（Issue #107）

- 该类问题核心通常不是禁言统计逻辑坏了，而是“配置 UI/Schema/展示”没有体现“全局默认 + 群级覆盖”。可归为 `bug`，辅以 `configuration`、`schema`、`ui/config-ui`、`documentation`、`group-config`。
- 已有线索：`get_group_setting`、`group_overrides`、`_record_mute_and_maybe_kick` 可能已支持按群读取 `mute_kick_threshold`，但 `_conf_schema.json` 或配置命令仍把它展示为顶层全局项。
- 不应简单删除全局 `mute_kick_threshold`；更稳妥是保留为“全局默认禁言踢出阈值”，并清楚说明可由群级覆盖。
- 需区分用户说的“插件配置设置”是 AstrBot 控制台/配置 UI，还是插件内部 `/配置`/状态命令：前者可能受框架 Schema 能力限制，后者可直接改展示逻辑。
- 展示建议显示“有效值 + 来源”，例如“禁言踢出阈值：3，来源：当前群覆盖；全局默认：5”。
- 边界语义：缺失 key 回退全局；显式配置 `0` 应表示关闭/覆盖，不能被当作未配置。

相关修改需同步 `_conf_schema.json`、README、帮助文本、配置查看/设置/清除命令和测试。搜索关键词：`禁言阈值`、`禁言踢出阈值`、`mute_kick_threshold`、`group_overrides`、`按群配置`、`配置显示`、`全局配置`。

### 4.4 专项权限按群配置（Issue #105 经验）

- “头衔、管理、踢人等专项权限按群独立配置”更像权限模型增强，通常标 `enhancement`。
- 重点是从泛化“按群插件管理员”转向按动作授权，符合最小权限原则。
- 需兼容旧配置：如改变 `group_admins` 语义，应考虑迁移、废弃期或兼容读取。
- 若已有 `group_overrides` 和 `get_group_setting`，应复用并明确缺省、空列表、全局回退和多群隔离。
- 敏感操作（踢人、设/取消管理、头衔）必须做越权和误授权测试。

### 4.5 Issue 分析与标签经验

- 标题为“。”或信息很少时，不能依赖标题做分类；应基于正文错误文本、复现命令和代码线索检索。
- 标题带 `[bug][medium]`、`[enhancement][medium]` 可作为信号，但仍需结合正文和代码验证。
- 结构化输出校验失败只应影响对应字段，不能导致已明确的 bug 被降级为 `other`、标签为空或可行性“无法评估”。
- 标签应优先匹配仓库实际标签体系；未知时给通用主标签，并列出可选标签。
- 重复检测要谨慎表述“暂未发现”，并给检索关键词；同命令不等于同问题。
- 建议标题应保留核心触发条件，如 `/撤回 1`、`count 参数`、`mute_kick_threshold`，不要泛化到丢失问题定位信息。

## 5. 开发约定与注意事项

- 插件逻辑集中在 `main.py`，修改时要全局搜索相似命令模式，避免复制粘贴式遗漏。
- 配置定义、业务逻辑、README、帮助文本和配置展示必须同步。
- 管理员 QQ 号建议按字符串处理，避免数字精度或格式问题。
- QQ 操作依赖平台 API 和机器人群权限，必须处理接口失败、权限不足、消息超时和异常返回。
- 权限类改动必须覆盖：全局配置、群级覆盖、命令入口、权限判断函数、文档说明和回归测试。
- AstrBot API/命令解析兼容问题，应先确认框架版本、插件版本/commit、完整堆栈和最小复现命令，并区分插件启动、命令注册、命令调用、特定输入触发四个阶段。
