### 3. 可行性判断质量

原分析写“可行性：无法评估”，不够充分。

虽然没有直接读取代码，但根据 Issue 描述和项目记忆，仍然可以做出有条件的可行性判断：

- 当前 `/撤回 N` 很可能依赖 `get_group_msg_history` 获取群消息历史；
- 部分 OneBot 实现不支持该接口；
- 引用消息撤回已有可用路径，说明基础撤回 API 很可能可用；
- 增加兼容回退的可行方向包括：
  1. 优先使用 `get_group_msg_history`；
  2. 若接口不可用，检测适配器能力并给出更明确提示；
  3. 在插件运行期间维护最近消息缓存，作为 `/撤回 N` 的备用来源；
  4. 或支持只在引用消息场景下回退，但明确说明 `/撤回 N` 无法完全兼容；
  5. 可配置地启用本地消息缓存，避免无界内存增长。

因此，较合理的可行性评估应是：

> 可行，工作量中等。若只是优化错误提示和能力检测，工作量较小；若实现不依赖历史接口的本地消息缓存回退，需要处理缓存生命周期、群隔离、消息顺序、权限、机器人重启后缓存丢失等问题，工作量中等，并有一定边界风险。

需要识别的风险包括：

- 本地缓存只能覆盖机器人在线后收到的消息，不能撤回重启前或未缓存的消息；
- 需要排除当前 `/撤回 N` 指令本身；
- 需要按群维护缓存，避免跨群误撤；
- 需要处理撤回权限、超时、消息不足、消息 ID 类型差异；
- 不同 OneBot 实现返回错误码和“不支持接口”的方式可能不同。

所以“无法评估”过于保守，也浪费了 Issue 中已经提供的有效信息。

### 6. 经验教训

#### 6.1 不应因结构化校验失败整体降级

原分析摘要为：

> AI Issue analysis output could not be validated: expected `<SUGGESTED_TITLE>`

这说明可能是输出格式校验失败。但格式失败不应导致：

- 分类变成 `other`
- 标签为空
- 可行性变成“无法评估”
- 标题变成“无建议”

正确做法应是局部修复字段，保留能够从 Issue 中明确判断的信息。

#### 6.2 `/撤回 N` 的核心问题要区分清楚

撤回类 Issue 需要区分几类不同问题：

1. 参数解析问题，例如 `count: int` 被 AstrBot 提前转换导致报错；
2. 语义问题，例如 `/撤回 1` 是否撤回上一条消息；
3. 历史接口问题，例如 `get_group_msg_history` 不可用；
4. 引用消息撤回问题；
5. 按用户撤回问题，例如 `/撤回 @用户 N`。

本 Issue 属于第 3 类：历史接口不可用时的兼容回退。不要误判为普通 bug，也不要与参数解析问题混为一谈。

#### 6.3 兼容回退不能简单等同于“继续提示引用消息”

如果只是提示用户“请使用引用消息撤回”，那不是功能回退，只是失败提示。真正的增强方向应考虑：

- 本地缓存最近群消息；
- 能力检测；
- 明确降级策略；
- 对缓存不足、机器人重启、接口不支持等情况给出准确提示；
- 避免误撤当前命令自身。

#### 6.4 分析时应结合仓库上下文

本仓库是 AstrBot 群管理插件，撤回命令是高频群管理功能。涉及 OneBot 适配器差异时，应优先考虑 `compatibility` 标签和适配器能力差异，而不是简单归类为 `other`。

较合理的分析结果应类似：
