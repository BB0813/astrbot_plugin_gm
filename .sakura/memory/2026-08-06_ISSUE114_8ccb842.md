## 6. 经验教训

### 6.1 Python 异步语法陷阱（值得固化的通用经验）

这是非常具体且高价值的教训：
- `async def` + 函数体含 `yield` ⇒ 自动成为 **async generator**。
- async generator 中 `return <expr>` 会被 Python 解析器判为 SyntaxError（即使逻辑上等价于"产出后终止"）。
- **async 函数与 async generator 不能靠"是否真的被迭代"来切换，语法上必须在定义时确定**。

**对分析流程的启示**：
- 遇到 `async def` 函数同时出现 `yield` 和带值 `return`，应立即怀疑这是 SyntaxError 来源。
- 分析此类 Issue 时，`python -m py_compile` 是最便宜的验证手段，应在风险点中明确推荐。
- 建议仓库 CI 流程固化 `py_compile` 检查，从流程上杜绝同类问题。

### 6.2 PR 引入回归的识别模式

本次 Issue 是典型 PR 回归：
- Issue 标题点出 **PR #113** 是直接来源。
- 反思记忆里"对'版本已更新仍存在'的问题应追踪最近相关 commit/PR"——本 Issue 不属于该模式（直接是加载失败），但仍然适用**反向追溯**：从错误行号 / 函数名反查引入 commit。
- 分析中已正确建议"参考 PR #113 的 18 个命令注册处对照校对"，可进一步建议：在 PR 合并前，对包含 `async def` 的新函数做"是否含 yield"的扫描。

### 6.3 仓库特有的关注点

- 仓库 `astrbot_plugin_gm` 大量使用 async 装饰器 + 异步事件回调，async/await/yield 三者混用的边界风险较高。后续遇到该仓库的 bug 报告，应特别留意：
  - 是否含 `yield` 关键字
  - 是否在 async 函数里调用 sync helper 但 helper 内含 yield
  - 是否有"既想 yield 又想 return 值"的混写迹象
- 18 个新命令集中注册在同一 PR 是仓库近期模式（参考反思记忆里"复制粘贴式问题"），意味着**单点修复必须配合同 PR 全量扫描**，本次分析已提示。
