# Issue #131 分析反思

## 核心问题诊断

本次分析存在**严重的反模式触发**：输出摘要明确显示 "reserved tag syntax in USERNAME"——这是字段校验失败导致的输出异常，但根据项目记忆中的**明令警示**：

> "结构化输出校验失败 ≠ 信息不足"……校验失败应**局部修复**而非**整体降级**

本次却犯了**整体降级**的错误：分类退化为 `other`、可行性为"无法评估"、标签为空、标题为"无建议"——**实质性判断全部被错误地放弃了**。

## 1. 分类与优先级准确性

**❌ 严重错误**：分类 `other` 完全不正确。

根据 Issue 内容"添加 /添加群待办 命令，引用消息回复即可设为群待办"，这是**典型的功能新增请求**，原标题也明确标注了 `[enhancement][medium]`，应归为：

- **主分类**：`enhancement`（不是 `other`）
- **辅助标签候选**：`command`、`group-management`、`todo`、`onebot`/`compatibility`、`needs-discussion`（OneBot 群待办 API 跨适配器支持度待确认）

**优先级 `medium` 合理**：新增非核心命令，不涉及安全/横切重写，且涉及 OneBot 适配器差异需讨论，medium 恰当。

## 2. 标签推荐质量

**❌ 完全未给标签**——这是校验失败连带导致的失误。

按本仓库标签体系，应至少建议：

- `command`：新增命令
- `group-management`：群管理类功能
- `todo`/`group-todo`：群待办专项（若仓库未建应建议新建）
- `onebot`/`compatibility`：群待办 API（`_set_group_todo` / `set_group_whole_ban` 等）在 NapCat/Lagrange/go-cqhttp 支持度不一
- `needs-discussion`：是否复用现有 `recall_cmd` 的引用消息解析路径、是否需要权限校验等设计决策待定

## 3. 可行性判断质量

**❌"无法评估"无依据**。根据项目记忆有充分模板可参考：

- **分支A**（OneBot v11 暴露 `_set_group_todo` API + 适配器支持）：~80-150 行
- **分支B**（需依赖第三方或自实现）：不可行或 ~200+ 行 + 跨适配器兜底

应明确给出分支判定，而非直接放弃评估。

## 4. 重复检测准确性

**❌ 措辞违反强制模板**："未检测到重复" 是明令**禁用措辞**，应改为"暂未发现重复，建议检索关键词：群待办、todo、待办消息、引用消息、添加群待办"。

## 5. 标题改写适当性

**❌"无建议"是反模式**。原标题 `[enhancement][medium] 新增 /添加群待办 命令（引用消息回复即可设为群待办）` 信息密度足够清晰，应标"可保留"或给出轻量规范化版本（如去掉方括号前缀或简化为"新增 /添加群待办 命令"）。

## 6. 经验教训

### 关键教训

1. **Pre-check 必须前置**：在任何字段出现"无建议/无法评估/空/未检测到重复"前，**必须**先确认是否源于校验失败。本次摘要已明确告知是校验失败，但仍触发了整体降级——说明反思流程中存在自动化保护机制缺失。

2. **建议机制**：应在反思流程中加入"校验失败短路器"——若摘要提及字段校验错误，则：
   - 仅修复字段输出格式（如把"无法评估"改为有条件判断的评估）
   - 实质性判断（分类/可行性/标签）维持原始判断
   - 标题字段在原标题清晰时直接给"可保留"

### 本类型 Issue（群待办/引用消息类）的仓库特有模式

- **OneBot 群待办 API 跨适配器支持矩阵**：`_set_group_todo(message_id, group_id)` 在 NapCat、Lagrange、go-cqhttp 中实现差异较大，部分仅支持群公告而非"群待办"语义（QQ 客户端层面"群待办"与"群公告"是不同入口）。
- **QQ "群待办" vs "群公告" 语义区分**：QQ 群待办是 `set_group_todo`（部分实现为 `set_group_notice`），与"群公告"（`set_group_announce`）不同；插件需明确选型。
- **引用消息解析既有路径**：本仓库已有 `recall_cmd` 中"引用消息"解析经验（`_extract_at_qq` 等），新增群待办可复用现有引用解析基础设施，避免重复实现。
- **权限校验横切关注点**：群待办设置属于群管理动作，是否需群主/管理员权限？建议配置 `todo_admins` 类似 `recall_admins` 的最小权限模型。
- **必查项清单**：① OneBot 适配器是否暴露 `set_group_todo` ② 消息 ID 跨适配器识别 ③ 引用消息中的 `message_id` 提取路径 ④ 权限模型（群主/管理员/可配置）⑤ 错误反馈（如消息已过期、不是机器人发送的消息）⑥ 撤回场景下的待办撤销（七处同步清单适用？）

### 仓库特有的新增命令可行性模板补充建议

应在项目记忆中新增"**OneBot 群待办类 Issue 标准分析模板**"，作为对现有撤回/STT/头衔/权限模板的补充，覆盖 API 选型、权限模型、引用解析复用、跨适配器降级。

## 总结

本次分析是项目记忆所警示的"**结构化输出校验失败导致整体降级**"反模式的典型案例。Issue 本身信息充分、分类明确、可行性可评估，但因校验失败触发了全面退缩。建议在反思流程中固化"校验失败短路器"：**字段修复必须局部化，实质性判断不可连带退化**。
