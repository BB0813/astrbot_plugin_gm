# Issue #134 分析反思

## 1. 分类与优先级准确性

**分类 `bug` 准确**。用户明确反馈"bot 解禁了𝓒𝓪𝓷𝓬𝓮𝓻"——bot 将装饰字符字面量当作合法 QQ 号执行了实际解禁动作，这是典型的解析层 bug 而非 enhancement 或 feature request。装饰 Unicode（`𝓒𝓪𝓷𝓬𝓮𝓻` 属于 Mathematical Alphanumeric Symbols U+1D49E-U+1D4CF）在 OneBot segment 中 `qq` 字段本应是数字字符串，QQ 平台不应回传这种值，所以这几乎确定是 `_extract_at_qq` 的归一化/校验缺失。

**优先级 `medium` 合理但需校准一处措辞**。原标题用"[bug][medium]"已合理，**核心论证"误解禁比误禁言影响更严重"完全成立**——解禁是逆向操作，错误地把非用户解禁了相当于放行了一个并未被封禁的对象，但实际场景里这又分两种情况：
- 目标本来就是非禁言用户 → 仅是误操作日志、无实际副作用
- 目标本来处于禁言状态 → 等于绕过了群管的禁言决策、形成权限绕过漏洞

第二种场景如果存在才是真正的 `high`。但**单 Issue 单次证据无法证实第二种场景成立**，所以 `medium` 已是保守合理选择，无需升 `high`。原标题保留 `[medium]` 是正确判断。

**潜在误判警示**：分析中提到"高频解析类 bug"——这是基于#134自身是"装饰字符 QQ"模式第四次触发的元判断（项目记忆明确写了"已第四次触发校验失败短路"），不是误判；模板化复用是正确的。

## 3. 可行性判断质量

**显式三分支判定是 #133 沉淀的关键纪律，本 Issue 正确执行了**——分支A（输入层归一化 + 校验）、分支B（兼容 + 早期拒绝）、分支C（深度重构）三档分别给了行数和天数估算。这是好的延续，但**分支A与分支B的区分度需再审视**：

- 分支A："`_extract_at_qq`/`_extract_at_qqs` 顶部加 NFKC + `\d{5,12}` 校验"，20-40 行
- 分支B："保持现有解析路径 + `re.fullmatch` 提前返回"，10-20 行

这两分支实际上**几乎重叠**——分支B是分支A的子集（只加正则不加 NFKC）。这种"A 包含 B"的分层对决策无帮助，反而会让人困惑。建议精简为**两档**：
- **轻量**（10-20 行/0.5-1 天）：仅加 `re.fullmatch(r"\d{5,12}", qq)`，在 `_extract_at_qq`/`_extract_at_qqs` 失败时返回空串/None
- **强化**（30-60 行/1-2 天）：NFKC 归一化 + 正则强校验 + 友好错误提示 + 单元测试覆盖装饰字符场景 + 同步加固 `_parse_qq_list`

**工作量下限判断正确**：明确写"不可估为「< 1 天」"，与项目记忆"小型修复工作量下限 1 天"一致。装饰字符测试矩阵（NapCat/Lagrange/go-cqhttp × 数学字母/手写体/Emoji 风格）确实是 0.5 天的活。

**未充分识别的技术风险**：
- ❌ **未讨论 OneBot 适配器层行为**：当 OneBot v11 segment 的 `qq` 字段本身被 NapCat 填充成装饰字符时（极少见但理论可能），仅在 `_extract_at_qq` 加正则无法解决，需在 segment 源头校验
- ✅ 但项目记忆模板已写了"② OneBot 适配器是否对装饰字符 QQ 拒绝/截断"，原 Issue 摘要里没明确体现这点，建议在反思中补充到"必查项"而不是仅放在脚注

**`unmute_cmd` L1948 路径分析到位**：正确识别 `_extract_at_qq(raw) or self._parse_qq(target)` 的 fallback 链，并提醒加固 `_parse_qq_list`——这是项目记忆"症状相似 ≠ 根因相似"陷阱的反向应用（同一 bug 跨模块传播）。

## 6. 经验教训

### 本 Issue 特有的反思

1. **分支判定粒度不要过细**：分支A 与分支B 实际是包含关系，应合并为两档而非三档。下次遇到"加 X"vs"加 X+Y"的分层时，先检验是否真存在路径分叉再给三个独立分支。

2. **项目记忆模板的"必给标签"清单需严格执行**：模板写了 `at-parse`/`at-extract` + `unmute`/`mute-action`，分析结果却漏给了——下次遇到匹配模板的 Issue，应**先在脑中对照模板的"必给标签"清单逐项勾选**，不要漏。

3. **OneBot 适配器层风险应在"必查项"里显眼位置标注**：装饰字符可能在 `_extract_at_qq` 之前的 segment 构造阶段就已经被 NapCat 污染，仅在 `_extract_at_qq` 加 NFKC 可能治标不治本。这条应在"必查项"① 之前加一条"前置检查：segment['data']['qq'] 是否本身就是装饰字符"。

### 仓库模式沉淀建议

- **"装饰字符 QQ"作为独立模式已可成型标准模板**：本 Issue 是该模式首发 + 模板化复用的素材来源。下次遇到此类 Issue 时直接套用本模板的"必查项""必给标签""工作量下限 1 天"三件套，无需重新发明。
- **可行性的 `_parse_qq_list` 同步加固建议值得固化为模板**：所有装饰字符/视觉欺骗型 QQ 解析 bug，都应同时建议 `_parse_qq_list`/`_parse_qq` 路径加固，避免下游绕过。这条应加入"装饰字符 QQ"模板的"修复建议"章节。

### 反模式提醒

- **"未检测到重复"措辞违规再次出现**：这是项目记忆明确禁止的措辞模板，第四次出现（#131/#132/#133/#134），需要在反思层固化：**任何重复检测结论都必须用"暂未发现"+"建议检索关键词"或"与 #X 相似但根因不同，置信度 0.XX"模板**。
- **分支判定不要为了凑数给三个分支**：如果实际只有两条独立路径（轻量 vs 强化），不要硬凑第三个"深度重构"分支。第三个分支仅当确实存在独立技术决策点（如重写整个解析模块）时才给出。
