## 2. 发现的模式

### 代码模式
- **plain dict + setdefault 显式创建** 替代 defaultdict：作者主动避开了 §4 中沉淀的 `defaultdict 工厂误触发` 风险，说明对自身代码有较深理解。
- **falsy 判空 + 业务安全的隐式约定**：`if not group_id or not message_id or user_id is None` 把 `0` 当作缺失是 Python 常见捷径，但与"通用 helper"身份矛盾——属于"业务正确但接口不规范"的典型模式。
- **本地缓存作为兼容性回退**：典型的"当上游 API 不可用时降级到本地状态"模式，常见于 OneBot 适配层（NapCat/Lagrange/go-cqhttp 能力差异）。

### 架构观察
- **撤回功能集中在 `recall_cmd` 与 `recall_user_cmd`**，但共享了一个未抽取的"读取最近消息"helper，是 §4.2 中提到的"修复宜抽取共享 helper"的应用场景。
- **缓存按群隔离 + maxlen 限制**：典型的 LRU-by-time 模式，但缺全局 key 上限，反映出"局部资源保护"有意识、"全局资源保护"无意识的常见短板。
- **`after_message_sent` 作为辅助记录点**：把"自身消息记录"从主 `on_group_message` 钩子下沉到 `after_message_sent`，体现了对 bot 消息生命周期（已发送后才回执）的清晰理解，但审查未确认两者注册的先后顺序与去重逻辑。

## 3. 规范完善建议

### 新增规则候选

**规则：撤回类本地缓存必须满足以下条件**
- 全局 key（群组）数量上限 + LRU 淘汰策略
- 写入失败不影响主流程（try/except + debug 日志）
- 读取时排除命令消息自身（按 `event.message_id` 过滤）
- 命令描述与 README 必须明确"本地缓存仅覆盖进程启动后"的范围限制

**规则：helper 函数的判空风格应统一**
- 若 helper 是通用接口，用 `is None` 严格判空
- 若 helper 是业务快捷路径，可保留 falsy 判空但必须在 docstring 注明约定
- 审查时对 `_record_recent_message` 这种"既像通用 helper 又像业务实现"的灰色地带应主动追问

**规则：OneBot 兼容性回退必须验证提示语义**
- 当历史接口空返回时，提示语不应固定写"不支持"，应区分"接口不可用 / 临时错误 / 历史为空"
- 项目记忆 §4.4 已沉淀此原则，应升级为强制审查项（minor 而非 suggestion）

### 项目特有规范

- **撤回功能的命令描述必须显式说明本地缓存行为**：包括"仅本进程"、"窗口大小"、"可能不完整"三个要点，避免用户误以为是历史记录。
- **缓存 maxlen 与命令 N 上限的比例安全边际**：建议 maxlen ≥ 2N，避免用户撤回 N 条但缓存不足时被误报。本项目 100 vs 50 比例仅为 2:1，建议放宽到 4:1 以上。
- **README 与帮助文本同步**：项目记忆 §4.3 已沉淀，但本审查未强制要求；应升级为"涉及用户可见行为的改动必须同步文档"。

## 4. 经验教训

### 未来审查关注要点

1. **撤回类 PR 必须走完整路径**：从命令入口 → 参数解析 → 历史接口获取 → 缓存回退 → 消息撤回 → 用户反馈，缺一环都会导致修复失效。本审查的端到端覆盖偏弱。
2. **"撤回结果会附带『（来自本地缓存）』提示"是 PR 描述声明，必须在 diff 中定位确认**——本次未做，是潜在盲点。
3. **缓存类 PR 必须审视全局上限**：本次是 minor 提醒而非阻断，但下一次类似改动应升级为 major，因为长期运行稳定性是生产事故常见来源。
4. **OneBot 兼容性回退的提示语必须精准**：`get_group_msg_history` 返回空可能意味着 5 种以上情况（不支持 / retcode 非 0 / 参数不兼容 / 网络异常 / 权限不足 / 历史不足），不可一概写"不支持"。
5. **falsy 判空是常见反模式但不易被识别**：应在审查时主动检查所有 `if not x` 形式，确认是否有 `0` / 空字符串 / 空列表会被误丢的合法值。

### 技术特定经验

- **本地缓存撤回的内存模型**：每条记录至少 `{message_id, user_id}`，按 100 条/群 × 1 万群 ≈ 几 MB 元数据 + 运行时 deque 指针开销。`maxlen=100` 是消息条目上限，dict key 才是真正的内存增长源。
- **`setdefault` 与 defaultdict 的关键差异**：前者只在显式调用时创建 bucket，后者会被任何访问（包括 `in` 检查、`[key]` 读取）触发工厂函数。这是本审查触发的 `defaultdict 工厂误用风险` issue 的根因，值得作为审查范式记忆。
- **`after_message_sent` 与 `on_group_message` 的去重**：bot 自己发的消息会同时经过两个钩子吗？本次审查未确认，但 `after_message_sent` 通常只在 bot 主动发送后触发，与 `on_group_message`（接收）不冲突——但应验证没有重复记录。
