## 6. 经验教训

### 未来 Issue 分析中应关注的要点

1. **优先确认错误发生阶段**
   - 启动时报错；
   - 插件加载时报错；
   - 命令注册时报错；
   - 命令调用时报错。

2. **标题为空或无意义时，重复检测要依赖错误正文**
   - 原标题为“。”时，不能依赖标题相似度；
   - 应用错误关键词检索：`count(int)=0`、`参数 count 类型错误`、`count`。

3. **框架兼容性问题要谨慎归因**
   - 如果错误与 AstrBot 参数解析有关，需要区分插件代码问题和框架行为变化；
   - 建议同时记录 AstrBot 版本和插件版本。

4. **避免把推断写成事实**
   - “很可能来自 /撤回 命令”可以；
   - “问题就是 /撤回 命令”则需要更多证据。

5. **建议用户补充最小复现信息**
   应请求：
   - 完整报错日志；
   - 触发命令；
   - AstrBot 版本；
   - 插件版本/commit；
   - 是否启动即报错；
   - 是否使用了旧缓存或旧插件目录。

### 对此类 Issue 的分析经验

此类“参数类型错误”通常有几个高频根因：

1. 命令框架不支持类型注解参数；
2. 默认值和注解类型组合不被支持；
3. 可选参数解析失败；
4. 用户输入为空字符串，但代码按 int 解析；
5. 插件更新后旧缓存未清理；
6. 框架升级后命令注册规则变化。

修复策略通常是：

- 命令入口参数统一使用 `str`；
- 在函数内部手动解析、校验、限制范围；
- 对非法输入返回用户友好提示；
- 保留旧用法兼容；
- 增加边界测试。

### 仓库特有模式和建议

从当前分析看，该仓库可能存在以下模式：

1. 命令参数直接使用类型注解，例如 `count: int = 0`；
2. 函数内部又进行二次类型转换；
3. 插件依赖 AstrBot 的命令解析机制；
4. 管理命令较多，类似问题可能不止一个。

建议仓库维护者进行一次全局排查：

```bash
grep -R "count: int" .
grep -R ": int =" .
grep -R "filter.command" .
```

重点检查所有命令入口参数中使用 `int`、`bool`、`float` 注解且带默认值的情况。  
如果 AstrBot 当前版本确实对这些类型存在兼容问题，建议统一改成字符串入口参数，并在内部集中解析。
