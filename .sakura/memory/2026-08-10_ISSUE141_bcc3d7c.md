# Issue #141 分析结果深度反思

## 1. 分类与优先级准确性

### 分类：`enhancement` ✅ 准确
- 维护者本人发起删除既有命令契约，属于"接口收敛/减法增强"。`bug` 不适用（无报错），`documentation` 不适用（删除命令本身超出文档范畴）。
- **潜在争议**：可考虑 `chore`（内部清理）— 但删除对外可见命令契约属 breaking-change 范畴，维持 `enhancement` 更准确。

### 优先级：`medium` ✅ 合理但需审视

**关键矛盾点**：项目记忆明确硬约束"owner-driven 纯减法应主动降 `low`"，但本次维持 `medium` 的理由是"已部署用户可见命令、外部脚本/教程可能引用"。**这一论证是站得住脚的**——`/取消头衔` 历史上反复出问题（#125/#111/#119）说明它被实际部署并有用户依赖，与"无人使用的内部清理"本质不同。

**决策路径评分**：
- ① 横切重写 + breaking-change → medium ✅
- ② owner-driven 改法明确 → 不升 high ✅
- ③ 工作量可控局部化 → 不升 high ✅
- ④ 与 #124/#126 无冲突 → 维持 ✅

四步决策路径完整且每一步都给出了显式说明，符合 #133 硬约束。**唯一可优化**：可补充第 5 条"对外契约删减 vs 内部清理的边界判定"作为该决策路径的支撑论据，进一步强化 medium 而非 low 的论证。

### 影响范围评估 ✅ 充分
- 识别了"已部署脚本/教程可能引用"的风险点。
- 但**未充分讨论** 用户侧的迁移负担：群管日常工作流中"撤销错误头衔"是高频操作，删除后无替代入口会显著影响体验——这正是分支 B/C 存在的合理性。

## 6. 经验教训

### 本次分析的亮点
1. **九项反向清单 + 七处同步清单双清单完整** — 体现 #139/#140 沉淀的纪律性应用。
2. **优先级决策路径 4 条显式** — 符合 #133 硬约束。
3. **owner-driven vs 对外契约删减的边界论证** — 在 medium vs low 之间给出了有理有据的判定。
4. **A/B/C/D 四分支可行性** — 符合 #139 加 D 的硬约束。

### 本次分析的不足与改进建议

#### 不足 1：重复检测措辞违规（第 10 次触及风险）
- 必须升级为前置自检门槛第一优先级。
- 改进：每个 Issue 分析的第一步加"重复检测措辞预检"——确认用"暂未发现"+ 关键词列表的模板，而非"未检测到重复"。

#### 不足 2：`onebot` 标签语义模糊
- 仓库对 `onebot` 的语义边界需更明确：是"涉及 OneBot API 调用"还是"跨适配器兼容"？
- 建议沉淀到项目记忆：`onebot` 标签使用边界 = 实际调用或修改 OneBot API 时；纯文档/纯内部清理不适用。

#### 不足 3：`deprecation` 标签语义模糊
- 真正的 deprecation 流程：标记废弃 → 公告 → 保留 N 版本 → 删除。
- 本次若选 A 分支直接删除，**不应给 `deprecation` 标签**；若选 B/C 保留替代入口但保留若干版本过渡，才适用。
- 建议：项目记忆明确"`deprecation` 仅在'标记废弃但保留过渡期'时使用"。

#### 不足 4：未充分讨论替代方案的责任归属
- 分支 A（仅硬删除）将"用户清空头衔"的能力完全剥夺。
- 是否项目有意收敛此能力？还是仅为简化代码？**需在 needs-discussion 中明确提出**。
- 改进：补充"建议维护者在 PR 阶段明确：分支 A 是否为最终方案，还是暂存方案待分支 B/C 评估"。

#### 不足 5：跨 Issue 互引不够
- #111/#119/#125 都是与 `/取消头衔` 高度相关的历史 Issue，**应在可行性章节显式互引**而非仅作背景提及。
- 这会强化"为什么本次删除是合理的"论证。

### 仓库特有的模式沉淀建议

**新增模板：owner-driven 命令删除类（#141 案例）**

- 触发：维护者发起删除既有命令契约。
- 与命令重命名（#138）的区别：保留能力 vs 完全删除。
- 必查项：①是否被其他命令依赖（grep 调用点）②用户依赖度（文档/教程/外部脚本）③跨适配器历史问题（导致删除动机）④替代方案需求评估 ⑤迁移路径 ⑥公告发布。
- 必给标签：`enhancement`(0.95) + `command`(0.95) + `breaking-change`(0.90) + `group-management`(按上下文) + `cleanup`/`removal`(0.80) + `documentation`(0.85) + `needs-discussion`(0.80) + `migration`(若分支 B/C)。
- 可行性分支：A 硬删 / B 删+引导 / C 删+替换 / D 分阶段。
- 优先级决策路径：①横切重写 + breaking-change → 最低 medium ②owner-driven → 不升 high ③工作量可控 → 不升 high ④与同类 Issue 方向不冲突 → 维持；**关键边界**：若命令有外部用户依赖（教程/脚本引用）→ 不降 low。
- 反模式：纯内部清理才适用 `low`；对外可见命令删除应保留 `medium`。
