### 仓库特有模式

1. **`recall_cmd` 是高频改动点**：项目记忆中多次出现撤回类 PR（语义变更、批量撤回、缓存兜底、行号解析等），#126 再次印证 `recall_cmd` 是该仓库的"复杂函数集中地"，未来分析此类 Issue 应优先关注 Path 分支的完整性

2. **维护者主动发起的接口收敛请求是低风险高把握**：仓库 owner mjy1113451 亲发此类 Issue，意味着决策已定，分析重点应放在"具体删除路径 + 文档同步 + breaking change 标注"，无需反复 `needs-info`

3. **`/消息列表` 与 `/撤回 编号` 强耦合**：是本次 Issue 的核心隐藏点。`/消息列表` 如果没有 `/撤回 编号` 的下游消费，其作为独立命令的存在价值显著下降。这是一个**接口解耦的连锁反应**，应在分析中显式提醒

### 分析方法改进

- **行号定位必须标注证据来源**：精确行号（L2024-2057）若无"已读取 main.py 验证"说明，会让读者怀疑是猜测。改进：要么读取验证，要么用"约 L2000-2060"等模糊表述
- **breaking-change 应作为独立标签**：删除既有命令语法、修改既有命令参数语义、修改既有命令返回值都属 breaking change，应有专门标签而非埋在描述中
- **`needs-discussion` 置信度评估**：当分析本身已指出多个未决决策点时，`needs-discussion` 应作为主标签而非辅助
- **工作量估算应给区间而非单点**："1-2 个工作日"已较合理，但应进一步拆分为"代码 X 天 + 文档 Y 天 + 测试 Z 天 + 验证 W 天"
- **重复检测措辞规范**：严格遵守"暂未发现 + 检索词"模板，禁用"未检测到重复"

### 对特定类型 Issue 的处理建议

针对"**删除既有命令用法**"类 Issue，建议在分析中明确以下结构：
1. **删除目标**：精确到 Path 分支 / 行号
2. **保留目标**：明确哪些路径不受影响
3. **边界行为**：删除后旧语法如何处理（报错？回退到其他 Path？）
4. **依赖解耦**：被删功能的下游（如 `/消息列表` → `/撤回 编号`）是否需要一并调整
5. **用户迁移**：现有用户的迁移成本与文档/帮助命令的告知方式
6. **CHANGELOG**：是否需要标注 breaking change
