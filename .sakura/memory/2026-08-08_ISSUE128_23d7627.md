# Issue #128 分析反思

## 一、分类与优先级准确性

**分类 `enhancement`（0.95）**：准确。Issue 明确请求新增"语音转文字识别 + 关键词禁言"工作流，属于典型 feature/enhancement，不属于 bug、question 或 documentation。

**优先级 `medium`**：判断合理但有微调空间：
- **支持 medium 的理由**：跨多个模块（消息钩子、STT、关键词匹配、撤回、禁言、配置 schema），涉及敏感操作（自动禁言）、需要 OneBot 适配器兼容矩阵，是典型"中等复杂度横切关注点"。
- **但是否应考虑 `high`？** 我认为不应。原因：① 这是**用户主动请求的新功能**，不是缺陷修复，没有"现有功能不可用"的紧迫性；② 自动禁言虽然是敏感动作，但可通过权限校验/豁免规则缓解，且 bot 已在群内的能力范围内；③ 可分阶段交付（先做"撤回+日志"，后做"禁言"），可降级风险。
- **反例思维**：如果 Issue 描述的是"已有 STT 功能但配置后不生效"，那就属于 bug + medium/high，而不是 enhancement。

**结论**：分类与优先级整体准确，无需调整。

## 二、标签推荐质量

**高质量标签**：
- `enhancement`（0.95）✓ 主分类
- `needs-discussion`（0.9）✓ 关键词匹配规则（大小写/谐音/白名单）需用户决策
- `group-management`（0.85）✓ 涉及禁言
- `configuration`（0.75）✓ 配置 schema 扩展

**可改进项**：

1. **遗漏的模块标签**：
   - **缺 `stt` / `speech-to-text` / `voice` 模块标签**（0.85+）：这是核心新增模块，应该有独立标签。仓库虽未必有现成体系，但分析时应主动建议。
   - **缺 `permission` / `permission-check` 标签**（0.7+）：自动禁言涉及 bot 权限校验、群主/管理员豁免、插件管理员豁免，应显式标注。
   - **缺 `onebot` / `compatibility` 标签**（0.75+）：语音文件获取（`get_record`/`get_file`/URL 下载）在不同 OneBot 实现差异大，与项目记忆中"`/取消头衔` 需 OneBot 实现版本"模式一致。
   - **缺 `moderation` 标签**（0.7+）：这是内容审核场景，与私聊申请解禁工作流同属 moderation 模块。
   - **缺 `privacy` 标签**（0.6+）：STT 转写全文是否缓存、命中日志是否含完整内容等隐私问题需关注。

2. **置信度评估的反思**：
   - `recall`（0.65）：合理偏低，因为撤回只是触发动作之一，不是核心模块。
   - `command`（0.7）：合理偏低，因为这是事件驱动而非命令触发。
   - `message-history`（0.4）：略低，若本地缓存命中记录也算消息历史的一个变体，可提到 0.5。
   - `good first issue`（0.1）✓ 项目记忆明确"增强类涉及设计决策/兼容性/横切关注点时置信度应 ≤0.15"，给出 0.1 正确。
   - `help wanted`（0.25）✓ 项目记忆明确"owner-driven self-implementation 几乎不适用 help wanted"，0.25 偏高，宜降至 0.1。

**与仓库标签体系一致性**：
项目记忆提到常用标签为 `recall`、`command`、`parser`、`message-history`、`group-management`、`onebot`、`title/special-title`。本次推荐覆盖了大部分，但**遗漏了 `onebot`/`compatibility` 这一核心兼容标签**，是一大疏漏。

## 三、可行性判断质量

**优点**：
- 9 个改动面拆解非常细致，远超普通 enhancement 分析的平均水平
- 明确引用了项目记忆中的多个关键约束（§4.7 按群覆盖、§4.3 撤回清单、§4.1 async/yield 风险、PR #116 教训）
- 工作量估算 160-300 行合理，与项目记忆"增强类涉及多模块"案例吻合
- 正确识别了两个核心瓶颈：① AstrBot STT API 暴露方式 ② OneBot 语音文件获取兼容矩阵

**可加强项**：

1. **STT 调用模式未明确**：分析应区分两种 STT 触发模式：
   - **同步模式**：在 `on_group_message` 钩子中同步 await STT → 关键词匹配 → 禁言。优点：实时；缺点：消息处理延迟增加，STT 失败时整条消息处理受影响。
   - **异步模式**：在 `on_group_message` 中转存原始语音消息 → 后台 task 转写 → 命中后召回（但消息已无法撤回，超过 2 分钟）。**这导致"异步模式"对撤回场景基本不可用**，必须明确推荐同步模式。
   
2. **撤回时限硬约束未点出**：OneBot `delete_msg` 限制 2 分钟内，STT 转写若耗时较长（特别是长语音/复杂音频），可能消息已被其他用户看到/响应。应在改动面中加一条："STT 转写超时阈值（如 30 秒），超时则跳过本条以避免撤回窗口失效"。

3. **测试策略缺失**：
   - 没有 STT 模型的 mock/桩（如何测试命中逻辑？需要预录语音样本或 mock STT 返回）
   - 没有不同 OneBot 适配器的兼容测试矩阵
   - 应在改动面中补："测试音频样本库 + STT mock + 适配器兼容矩阵"。

4. **降级方案缺失**：当 STT 不可用/AstrBot 未配置 STT/OneBot 不支持语音文件获取时，插件应如何表现？是禁用整个功能、跳过语音、还是记录错误？应明确降级策略。

5. **群规模性能影响**：大群里每天可能成百上千条语音，同步 STT 会显著增加 API 调用成本和延迟，应明确"每日上限/每分钟限流"。

**结论**：可行性整体良好，但缺 STT 调用模式决策、撤回时限约束、降级策略、性能限流四点。

## 六、经验教训

### 值得在未来 Issue 分析中关注的要点

1. **STT/语音类 Issue 的特殊考量**：
   - OneBot 语音消息类型（`record`/`ptt`）需在消息钩子中单独处理，与文本/图片/at 不同
   - 语音文件获取链路：`file_id` → `get_record`/`get_file` → URL/字节流 → STT provider，每一步都有兼容性问题
   - 撤回时限（2 分钟）与 STT 耗时的硬冲突是核心约束，必须在改动面中显式列出

2. **内容审核类 Issue 的模块标签**：
   - 关键词匹配 + 自动处罚 = 内容审核（moderation），应建立 `moderation` 标签
   - 与现有的 `recall`、`permission`、`group-management` 并列，形成完整的群管理标签体系

3. **降级策略是横切关注点**：
   - 项目记忆强调"横切关注点"对召回、权限、缓存的重要性，本次的"STT 不可用时如何降级"是同样的横切关注点
   - 任何依赖外部能力的功能（STT、AI、LLM、OCR）都应明确降级路径

4. **隐私边界要前置**：
   - STT 转写内容是否缓存？是否日志？是否上传？这些隐私问题应在 schema 设计阶段就明确，而非事后补

5. **配置 schema 的"覆盖语义"陷阱**：
   - 项目记忆强调 `0`、空列表、`None`、缺失 key 的区分
   - STT 配置中"违规词列表为空"的语义需明确：禁用功能、跳过匹配、还是默认全局词库？

### 对特定类型 Issue 的分析经验

**"语音 + 自动处罚"类 Issue 分析模板**：

| 维度 | 必查项 |
|------|--------|
| 触发场景 | 群内语音消息，需识别语音类型（`record`/`ptt`） |
| STT 调用 | AstrBot 是否暴露 STT API？同步/异步？超时阈值？ |
| 语音文件获取 | OneBot 适配器兼容性（NapCat/Lagrange/go-cqhttp），`get_record`/`get_file`/URL |
| 关键词匹配 | 大小写/全半角/繁简/谐音/正则/白名单/列表为空语义 |
| 撤回时限 | 2 分钟硬约束，STT 耗时是否影响窗口？ |
| 禁言权限 | bot 是否管理员、是否豁免群主/管理员、是否豁免触发者本身 |
| 降级策略 | STT 不可用/超时/失败/未配置时的行为 |
| 性能限流 | 大群每日语音量、每分钟上限、API 调用成本 |
| 隐私边界 | 转写内容缓存、日志、审计、撤回后是否清理 |
| 配置 schema | 全局默认 + 群级覆盖、空值语义、旧配置迁移 |
| 文档同步 | README + 帮助 + schema + CHANGELOG 四端 |

**工作瓶颈识别**：
- 第一瓶颈：AstrBot STT API 暴露方式（需确认版本与文档）
- 第二瓶颈：OneBot 语音文件获取兼容矩阵
- 第三瓶颈：撤回时限 vs STT 耗时的硬约束
- 第四瓶颈：自动禁言的权限校验与豁免规则

### 仓库特有的模式和建议

1. **"全局默认 + 群级覆盖"模型**已在仓库多处使用（§4.7），新功能应直接复用而非另起炉灶
2. **撤回类强制清单（§4.3）**同样适用于本 Issue，因为涉及"命中后自动撤回"
3. **本地缓存兜底模式**（§4.2）可借鉴：即便 STT 命中后撤回失败，也可记录违规事件用于统计/审计
4. **审批工作流思路**（§5）可借鉴：自动禁言是敏感动作，应支持管理员事后复核/撤销
