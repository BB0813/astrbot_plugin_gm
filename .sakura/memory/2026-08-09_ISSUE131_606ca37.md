# Issue #131 分析反思

## 1. 分类与优先级准确性

**分类准确**：`enhancement` 正确。维护者本人发起新增命令，无报错、无回退路径问题、非"提示成功但实际未生效"模式，应为典型 feature addition。

**优先级判断合理**：`medium` 恰当。理由：
- 跨适配器可用性差异显著（NapCat/Lagrange/go-cqhttp 支持度不同），存在"指令看似成功但客户端无 UI 反馈"的隐性风险
- 但非阻断性失败：API 不支持时降级提示而非崩溃
- 权限收紧（群主专属）相对 /设精 是**收紧而非放宽**，误用风险有限
- 工作量虽可控但需多文件同步，非 trivial

**潜在问题**：未考虑"owner-driven self-implementation"是否会拉低优先级至 `low`。但因为跨适配器差异 + 权限模型区分 + UI 异步刷新三个独立风险点叠加，`medium` 是保守合理判断，不应降级。

**标签体系一致性**：与项目记忆 #131 标准模板对照基本一致，但模板中建议的 `reply`/`quote-message` + `bot-capability` + `onebot-extension` 三个标签未全部落地，仅保留了 `onebot`。

## 3. 可行性判断质量

**评估全面且深度合适**，亮点：
- 准确识别 OneBot v11 非标准扩展（最大风险点）
- 区分权限模型（`_is_group_owner` vs `_is_group_admin_or_owner`）是关键洞察
- API 三段式降级路径（标准名 → 带下划线变体 → 降级提示）符合项目既有模式
- "API 返回 ok ≠ UI 生效"专项处理是高质量细节

**存在的不足**：

1. **行号引用不够严谨**：可行性章节多次提到"§4.21、§4.22"、"L2000-2060"等具体编号——根据反模式警示"记忆引用必须可溯源"，模糊记忆时不应编造编号。建议改为"参 §群管理动作新增模板"、"参 §引用消息触发型命令模板"。

2. **工作量估算保守度**：80-140 行、1-2 天。考虑到：
   - 跨适配器测试矩阵（NapCat/Lagrange/go-cqhttp 各需最小验证）
   - 五处同步（实际是七处）外加跨适配器兼容性文档
   - 群主 vs 群管权限测试用例
   - 引用消息已撤回的兜底测试
   
   估算略偏乐观，**120-180 行、1.5-2.5 天**更稳妥。

3. **遗漏点**：未提及"被设为待办的原消息被撤回/被删除后的行为"——issue 原文未提及但属于待办功能的内在风险面。已部分在第 6 点提及但可强化。

4. **配置 schema 决策**：第 8 点推断"无需新增 schema 字段"基于 issue 原文"不用在插件配置加群待办规定长度"。但 schema 还可能涉及 `enabled`/`per_group_override`——模板建议的"全局 enabled + 按群 override 关闭"是否要实施未明确表态。建议显式给出"本期不加 / 后续按需加"的决策。

## 5. 标题改写适当性

**原标题**：`[enhancement][medium] 新增 /添加群待办 命令（引用消息回复即可设为群待办）`

**建议标题**：`[enhancement][medium] 新增 /添加群待办 命令（引用消息设为群待办，仅群主/群管可触发）`

**评估**：
- ✅ 保留了核心信息（命令名、触发方式、分类、优先级）
- ✅ 新增"仅群主/群管可触发"——这是权限约束信息，对维护者和潜在贡献者都是关键决策
- ⚠️ 但原标题未明确权限范围（"只允许群管理或群主"在 issue 正文里），建议标题补全是**有价值的细化**而非过度改写

**轻微过度改写**：原文是"群管理或群主"，建议标题简化为"群主/群管"——但实际权限收紧后可能仅群主可设（可行性章节已讨论），所以"仅群主/群管"略宽。建议改为"仅群主可触发（与 /设精 权限不同）"或更精确的"权限收紧至群主"。

## 6. 经验教训

### 仓库特有模式沉淀

1. **"引用消息触发型命令"已成稳定模式**：#131 的可行性模板已沉淀，可直接套用到未来的"引用某消息 + 触发动作"型命令（如未来可能出现的"引用消息撤回"、"引用消息加精确认"等）。

2. **API 三段式降级是仓库既有标准**：标准名 → 带下划线变体 → 降级提示。新增 OneBot 相关命令应默认采用此模式，不必每次重新讨论。

3. **"权限收紧"是隐性横切关注点**：与 #130/#132 的"权限模型重构"不同，#131 是**单命令内的权限收紧**——这种"局部权限收紧"模式未来可能反复出现（如某个新命令只能群主、某个命令只能超管），应建立"局部权限收紧"小模板而非每次套用完整权限重构模板。

### 分析方法改进

1. **行号引用规范**：本次反思中提到的"§4.21、§4.22"等编号未在项目记忆中出现具体定义，属于模糊记忆。下次应在引用前确认编号存在，或改用"参 §X 章节"模糊表述。

2. **权限收紧需单独标注**：本次 issue 的权限决策（群主专属）是一个独立的决策点，应在标签中显式标注 `permission`，而非仅在可行性正文中讨论。

3. **owner-driven 决策点的 need-* 标签校准**：本次 `needs-info` 0.25、`needs-discussion` 0.8 的处理符合经验（决策待定而非信息缺失），但应在标签清单中显式注明校准理由，未来类似 owner-driven enhancement 可直接套用。

4. **跨适配器风险量化表达**：可行性第 11 点"不要因和 /设精 同构就低估工作量"是好的警示，未来可在工作量估算前先做"风险乘数"判断（如跨适配器 ×1.3、权限收紧 ×1.2、UI 异步刷新 ×1.1），累乘后给出保守值。

### 后续动作建议

- **不触发 `breaking-change`**：与 #130/#132 不同，本次仅新增命令，不修改既有命令/配置，不应标 `breaking-change` ✅
- **不触发合入外部代码评估**：纯内部新增命令
- **建议在 README 的"跨适配器兼容性"章节补一行**："群待办 API 仅 NapCat 系适配器稳定支持，Lagrange/go-cqhttp 部分版本不可用"——本次可行性已识别此风险但未显式标为后续动作

**总体评价**：本次分析质量较高（分类准确、可行性深度充足、标签大体合理），主要可改进点是标签完整性（缺 `permission`/`reply`/`onebot-extension`）、行号引用严谨度、工作量估算保守度三个细节。标题改写有价值但措辞可更精确。
