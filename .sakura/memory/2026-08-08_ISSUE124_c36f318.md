# Issue #124 分析反思

## 1. 分类与优先级准确性

**分类 `enhancement` 准确**：本质是 UX 缺口补全（"无编号默认 1 条"+"@用户+单数字按编号路由"），不涉及运行时报错，也不改变已有命令的语义契约（用户期望的语义是新增形式，不是修复错误行为）。`enhancement` 准确，`bug` 不合适。

**优先级 `medium` 合理**：
- 不阻断核心撤回功能（`/撤回 N`、`/撤回 @用户 N` 等已有形式仍可用）
- 不涉及权限、配置 schema 破坏、数据丢失等高风险面
- 仅是命令路由和默认行为的 UX 优化
- 但确实改变了 `/撤回 @用户 5` 的语义（5 条 → 1 条指定编号），对存量用户有行为变更影响，所以不应该是 `low`

**一个潜在问题**：分析中提到的"行为变更"风险（`/撤回 @用户 5` 从"5 条"变为"1 条编号 5"）其实是**用户主动请求的语义修改**，不是回归。在反思中把它当成"风险"略有过度——这本质上是 issue 标题里"按用户指定编号撤回单条消息"明确要求的。但仍需在文档/CHANGELOG 中明确告知，这一点分析已经覆盖。

## 2. 标签推荐质量

**现有标签基本贴切**：
- `enhancement` ✅ 核心分类
- `help wanted` ✅ 合适（依赖 OneBot 适配器行为、需要实际群组测试）

**可补充的标签**（按项目记忆惯例）：
- `command` — 涉及命令解析与路由调整
- `recall` — 撤回功能模块（项目记忆明确提到该标签常用）
- `command-routing` 或 `parser` — 入口分流是核心改动点
- `ux` 或 `user-experience` — 兜底默认行为是 UX 改进

**与仓库标签体系的一致性**：项目记忆反复强调标签要"贴合模块和根因"，仅给 `enhancement` + `help wanted` 偏薄，缺少 `recall`、`command` 这种模块级标签。`help wanted` 的置信度 0.6 也偏低——既然已经定位到具体函数和行号、给出了明确改法、`mjy1113451` 是仓库 owner（高接受度），这个 issue 不需要外部帮助，更像是 routine implementation。`help wanted` 给 0.4 左右或换成 `good-first-issue`（前提是改动确实简单）更合适。

## 3. 可行性判断质量

**代码定位精确**：行号（1984-2172、2025-2057、2059-2071、2128-2162、2163-2172、2209-2214）非常具体，说明做了真实代码勘察而非泛泛而谈。这是分析的亮点。

**改动路径清晰**：三步改动（入口分流、默认 1 条、文案同步）逻辑自洽，工作量"1-2 小时"对中等熟悉度的开发者基本合理。但**测试覆盖部分可能偏少**：

**遗漏的关键检查**（基于项目记忆"撤回类 PR 强制检查清单"）：

## 6. 经验教训

### 通用经验

1. **重复检测字段的措辞模板化**：项目记忆已明确警示但仍出现"未检测到重复"的违规，需要在反思中形成肌肉记忆——**默认使用"暂未发现（建议检索关键词：...）"**，不论是否真的做了充分检索。

2. **`help wanted` 标签的使用边界**：当 issue 已有明确 owner、明确改法、明确工作量时，`help wanted` 并不贴切。可考虑：
   - 已规划清楚、有 owner → `enhancement` + 模块标签即可
   - 改法不明、欢迎外部贡献 → `help wanted` + `needs-design`
   - 简单到任何人可上手 → `good-first-issue`

3. **行为变更 ≠ 风险**：当用户主动请求语义修改时（如本次 `/撤回 @用户 5` 从 5 条 → 1 条），这是需求不是回归。"风险"应聚焦于实现层面的副作用（缓存一致性、对称性破坏、文档缺失），而非用户主动要求的语义变更。

### 仓库特有经验

1. **`recall_cmd` / `recall_user_cmd` 对称性**是本仓库撤回相关改动的核心检查点。每次涉及撤回逻辑修改，必须确认两条命令：
   - 入口分流是否对称
   - 本地缓存写入/读取是否对称
   - 用法提示是否对称

2. **本地缓存 (`message_history`) 的写入路径**是历史 PR 反复强调的基础设施。任何业务逻辑改动都不能破坏：
   - 用户消息走 `on_group_message` 的写入
   - bot 消息走 `after_message_sent` 的写入（**置于业务早退之前**）
   - 按群隔离（`{str(group_id): deque[dict]}`）
   - deque maxlen ≥ 4×N 的上限

3. **本仓库的 UX 改进类 issue 通常工作量低估**：
   - 看似"加个默认 1 条"的改动，背后涉及：入口分流、命令提示、README、帮助命令、`/消息列表` 帮助、行为兼容性说明
   - 实际工作量往往是"代码改动 1 小时 + 文档同步 1 小时 + 测试 1 小时"

### 对未来 Issue 分析的具体建议

1. **涉及 `@用户 + 单数字` 这类歧义路由的改动**，必须在分析中明确：
   - 旧语义的兼容策略（保留多编号/逗号/空格走"按数量 N"分支？或全部改"按编号"？）
   - 用户教育成本（README + 用法提示必须明确）
   - 是否需要在 CHANGELOG 中标注 breaking change

2. **撤回相关 issue 应主动列出"强制检查清单"**：项目记忆有完整清单，但分析中只部分覆盖。建议在反思时主动核对：
   - 权限、时间窗、限流、失败处理、自身消息过滤、bot 消息处理、撤回目标过滤

3. **建议在分析模板中增加一栏"对称性检查"**：列出所有相关命令/helper（本次应包括 `recall_user_cmd`、`recall_cmd`、`/撤回自身`、`/消息列表`），逐项确认改动是否对称。
