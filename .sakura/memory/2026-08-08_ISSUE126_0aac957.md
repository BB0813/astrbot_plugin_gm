# Issue #126 分析反思

## 1. 分类与优先级准确性

**分类**：`enhancement` 准确。这是维护者主动发起的命令形态简化请求（删除两种用法），属于接口收窄而非 bug 修复，也不是完全新增功能。仓库记忆中也明确"语义歧义类 issue 属于命令形态简化"。

**优先级**：`medium` 合理。这是 breaking change（删除既有用法），但属于：
- 维护者主动发起（非用户报错）
- 纯删减，不引入新逻辑
- 影响范围限于使用旧用法的用户（占少数，否则不会主动删）
- 改动局部化在 `recall_cmd`

**潜在问题**：分析结果中提到"`/撤回自身 N` 不受影响，无需对称性修改"——这点正确，但应进一步强调：`/撤回` 帮助文本中若提到"按编号撤回"示例需同步清理（已覆盖），且 CHANGELOG/release notes 需写明破坏性变更（虽然本仓库未必有 CHANGELOG 流程）。`medium` 而非 `low` 的关键在于：这是**对外接口的删减**，已部署的群机器人用户可能因用法失效而困惑。

## 2. 标签推荐质量

**当前标签**：`enhancement`（0.9）、`help wanted`（0.3）

**评估**：
- `enhancement` 置信度 0.9 合理
- `help wanted` 0.3 偏低——维护者自己发起且已给出明确改法、工作量、文件位置，属于"已明确 owner/改法/工作量"场景，按经验**不宜给 `help wanted`**，应降级或移除
- **遗漏的重要标签**：
  - `breaking-change` 或 `interface-removal`：删除既有命令用法属于对外契约变更
  - `command`、`recall`：模块标签（仓库经验要求覆盖）
  - `parser`：涉及命令参数路由的简化
  - `documentation`：README、帮助文本需同步（仓库经验："README + 帮助命令 + docstring 三处同步"）
  - `needs-info` 不需要——维护者自己已经明确要删哪些、改哪里
- `good first issue` 确实不适合（涉及设计决策/横切关注点），分析中未推荐，符合经验

## 6. 经验教训

### 本次 Issue 的特殊性

1. **维护者自提的破坏性变更**：这是少见的"维护者主动删功能"场景，与"用户报错"路径完全相反。分析时应聚焦：
   - 删哪些（精确到行号）
   - 同步改哪些（README/帮助/docstring）
   - 是否需要公告/CHANGELOG
   - 剩余路径的边界是否仍然清晰

2. **"删减类" issue 的检查清单**与"新增类"相反：
   - 新增：功能完整性、向后兼容、默认值、迁移路径
   - 删减：调用点清空、文档同步、帮助文本、CHANGELOG、用户教育

3. **"语义歧义消解"动机**：分析中识别了"消除单数字/编号语义歧义"——这是 `/撤回 5` 既可解释为"撤回 5 条"也可解释为"撤回编号 5 的消息"的歧义。删减后只剩"撤回 5 条"语义。这是**路由简化**而非纯删减，应在摘要中更突出这一点。

### 仓库特有模式

1. **撤回命令高度敏感**：任何对 `recall_cmd` 的修改都必须走"撤回类 PR 强制检查清单"（经验 §4）。即使本次是纯删减，也应：
   - 确认删除分支后，`recall_cmd` 的入口 dispatch 仍能正确路由三种剩余用法
   - 确认分支删除未影响本地缓存写入（`on_group_message`、`after_message_sent` 路径）
   - 确认分支删除未影响 `event.message_id` 过滤逻辑

2. **README 与帮助文本同步是本仓库高频疏漏点**：经验中明确"README + 帮助命令 + docstring 三处同步"。本次分析覆盖了 README 和 `/消息列表` 帮助，但未提及 `/撤回` 自身的 `yield event.plain_result(...)` 帮助文本是否需要同步——应在可行性中补充。

3. **标签体系映射**：本仓库的标签体系需要补充 `breaking-change` 或 `interface-removal` 类标签（若尚未存在），用于覆盖此类"主动删减对外契约"的场景。

### 给未来类似 Issue 的建议

- "维护者主动删减"型 issue，分类锁定 `enhancement`，优先级看影响面（核心命令 → `medium`）
- 必须覆盖：① 调用点清空 ② 帮助/README/docstring 同步 ③ CHANGELOG/公告 ④ 剩余路径边界 ⑤ 验证手段（不只是 `py_compile`，还要实际加载）
- 重复检测措辞必须用"暂未发现" + 检索词
- 标签必须含 `breaking-change`（若仓库有该标签）+ 模块标签（`command`/`recall`/`parser`）+ `documentation`
- `help wanted` 置信度对"维护者自提且已明确改法"的场景应 ≤0.1
