## 二、发现的模式

### 代码模式

1. **集中权限检查趋势**（#130→#132→#147 连贯演进）：
   - 分散 `is_plugin_admin` → 统一 `_is_authorized()`
   - 这是该仓库的**标准化路径**，后续类似变更可直接引用此模式

2. **纯减法特征**：
   - 移除 `/设管`/`/取管` 命令（owner-driven 纯减法）
   - 移除 `batch_max_count` 配置项
   - 简化 `/撤回` 用法

3. **硬编码替代可配置项**：
   - `batch_max_count` → 硬编码 50
   - 需警惕：配置项移除是 breaking-change，应在 CHANGELOG 明确标注

### 架构观察

- **权限模型重构是持续性工作**：从 #130 到 #147，维护者持续推进群原生权限替代 `plugin_admins` 配置

- **命令注册依赖 `_GM_COMMAND_NAMES` 元组**：这是 AstrBot 插件的易错点，命令移除必须同步更新

## 四、经验教训

### 值得在未来审查中关注

1. **README 引用是文档同步的晴雨表**：
   - 本次 L93 提及 `/设管` 被遗漏，暴露了文档变更的审查盲区
   - **教训**：任何命令/配置移除，必须要求提交者提供文档全文 grep 验证

2. **`_GM_COMMAND_NAMES` 是 AstrBot 命令注册的硬约束**：
   - 仅删除 handler 不足以真正移除命令
   - **教训**：对于 AstrBot 插件，必须显式验证 `_GM_COMMAND_NAMES` 是否同步更新

3. **硬编码替代可配置项需显式 breaking-change 标注**：
   - `batch_max_count` 移除影响依赖此配置的多群环境
   - **教训**：即使是无感知的默认值变更，也应在审查中明确评估影响范围

4. **quick 模式的边界意识**：
   - 本次 quick 审查发现了文档问题，说明快速模式也能捕捉关键遗漏
   - **教训**：quick 不代表"浅层"，文档同步检查应提升为 quick 模式的默认必检项

### 对特定技术的审查经验

| 技术点 | 审查要点 |
|--------|---------|
| 权限统一 helper | 抽样所有调用点，验证 success/静默失败双路径 |
| 命令移除 | 显式验证 `_GM_COMMAND_NAMES` + README grep |
| 硬编码常量 | 评估是否应保留可配置性，breaking-change 需标注 |
| 撤回逻辑 | 缓存写入（早退前）→ 业务逻辑 → 回执的完整链路 |
