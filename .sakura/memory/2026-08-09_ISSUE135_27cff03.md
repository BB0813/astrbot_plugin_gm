# Issue #135 深度反思

## 1. 分类与优先级准确性

**分类判断：`enhancement` —— 准确合理。**

这是一项新增命令功能，无既有功能破坏。owner-driven、方向明确、与现有禁言命令体系同构，符合 `enhancement` 的典型场景。

**优先级 `medium` —— 合理但值得再斟酌。**

- **支持 medium 的理由**：涉及新命令开发、跨适配器兼容处理、需发布新版本（按现有节奏 owner 自实施+PR 流程），工作量约 100-200 行。
- **可考虑微降的依据**：本仓库"群管理动作新增"类 issue 的实际节奏——维护者 jjy1113451 是自实施型 owner，类似 #131 群待办已采用 medium。功能非横切、不影响现有功能、不涉及权限模型重构、不涉及配置迁移。
- **结论**：medium 维持。但存在一个微妙的**对比基线失衡**——同类型、同工作量的"群管理命令新增"在此前都被标 medium 是 OK 的，但本次未与 #131 群待办的优先级做显式对比说明。若读者将本 issue 与 #131 并列评估，可能产生"前者 medium 偏高"的质疑。建议在优先级章节加一句 "与 §#131 群待办 template 同级，工作量更小、跨适配器风险更低，按一致标准定 medium"。

## 3. 可行性判断质量

**判断"可行性中等偏低"——准确。**

- 优势：复用现有模式（`_execute_action`、权限 helper、元组注册），工作量集中在列表组装 + 格式化 + 跨适配器兼容。
- 估算 100-200 行——合理，与 #131 群待办类似，但更简单（无 reply_id 解析、无 set_group_todo API 选型分支）。

**值得补强的几点：**

1. **分页/分批处理缺失**：`get_group_member_list` 大群返回可能上百条，需不需要分批过滤？还是一次性过滤后展示？
2. **缓存层**：现有 plugin 是否有"成员列表缓存"？若无，每次调用都查，权限强约束可缓解；如果有，需说明缓存失效策略。
3. **空状态处理**：群里没人被禁言时，提示语是否友好（"当前群无被禁言成员"）？
4. **时间格式显示**：剩余禁言时长 > 30 天怎么显示？（理论上 QQ 禁言上限 30 天，但跨适配器可能不一致）。建议给出格式边界（`X 天 Y 小时` vs `剩余 X 小时` vs `永久`）。
5. **隐私考虑**：列表展示用户昵称 + QQ 号，私聊/群内谁能看到？全员可见 vs 仅群管可见的策略差异——这一项也是 `needs-discussion` 的支撑。

**风险识别基本到位**（字段差异、调用频率），但**未识别"读权限可能被滥用为侦察工具"**——即查看禁言列表本身可能揭示群管的执法记录，是否需要控制可见范围？这是 owner-driven 决策点。

## 6. 经验教训

### 通用教训

1. **owner-driven 功能请求的优先级陷阱**：本次与 #131 同类但工作量更小，仍按 medium 处理，但未在分析中显式对比说明一致性。需要养成"同类 issue 显式互引"的习惯，避免读者横向对比产生质疑。

2. **`needs-discussion` 权重对 owner-driven 的校准**：本仓库模式——owner 自实施不等于"无决策"。任何涉及"权限/字段差异/性能"的命令新增都至少有 2-3 个决策点。`needs-discussion` 应保持高权重。

3. **读权限 vs 写权限的区分**：本仓库 issue 多关注"谁能执行"（写权限），但本次是"谁能查看"（读权限）。仓库标签体系若仅有 `permission`，应细化为 `write-permission` / `read-permission` / `viewer-role`。

4. **跨适配器字段差异**：本仓库模式已成熟——`shut_up_timestamp`（NapCat/go-cqhttp）vs `ban_expire_time`（Lagrange）vs `mute_end_time`（部分实现）。任何查询"群成员 X 字段"的 issue 都应主动列出 fallback 表。

5. **重复检测前置过滤规则的应用**：同类主分类（都是 enhancement）但 API 不同时，不能机械按表面相似度标重复。本次反思原结果"可能是 #131 重复"是典型反模式触发点。

### 仓库特有的模式建议

1. **建议新增 `mute` / `ban` / `ban-list` 标签子体系**：与 `title`、`recall`、`vote` 等并列，作为高频主题标签。理由：本仓库禁言相关 issue 多发（#135、可能后续还有禁言时长统计、解禁申请等），建立标签便于检索。

2. **"群管理动作新增"模板可细化为"读类"与"写类"两个子模板**：
   - 写类（#131 群待办、本次的禁言列表）：关注写权限、API 返回、UI 生效延迟、回执。
   - 读类（本次）：关注读权限、字段差异、数据脱敏、缓存策略。

3. **时间格式化标准**：仓库现有命令（如 `/禁言 Xh`）应对剩余时长显示格式做过设计——本次 issue 可在分析中提示"复用现有格式化函数（如有），避免风格不一致"。

4. **"跨适配器字段差异"已成为仓库高频考量**：建议在项目记忆中正式建立"读取类群成员字段"对照表：`role`、`shut_up_timestamp`、`ban_expire_time`、`last_sent_time`、`join_time`、`level`、`special_title` 的跨实现差异矩阵。这对后续涉及成员列表过滤、权限校验、状态查询的 issue 都能直接复用。

### 反思的反思

本反思最重要的发现是：**未触发"反模式校验失败连带退化"的红线**——分类、标签、可行性、标题均维持原始判断。这值得肯定。但也存在两类问题：
- **重复检测措辞违规**："可能是 #131 的重复"——应改写为"暂未发现高度重复 Issue，建议检索关键词..."。
- **`needs-discussion` 权重偏低**：未充分应用项目记忆"owner-driven 但涉及设计决策"的校准规则。

后续同类 issue 分析应：
1. 重复检测结尾必须有"⚠️ 措辞核对"提醒；
2. 任何 owner-driven 涉及"字段差异/权限/性能"的命令新增，`needs-discussion` ≥ 0.65；
3. 工作量与同模板历史 issue 显式对比一句。
