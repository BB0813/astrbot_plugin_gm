# Issue #140 分析反思

## 1. 分类与优先级准确性

**严重问题：分类应为 `enhancement` 而非 `other`**

原 Issue 明确是 `/举报` 命令的**权限路由逻辑调整**，属于功能增强/权限模型细化，绝非 `other`。仓库记忆 #130/#132 沉淀的"权限模型重构类"模板直接适用——这是把举报通知按"举报人/被举报人角色"做分级路由，本质是权限边界细化。

**优先级应为 `medium` 而非"无法评估"**

- 横切影响：涉及群管/群主通知机制，多群生效
- 有破坏性：原"全员举报→全员收通知"的语义被改变（breaking-change）
- 工作量可控：单纯 if/elif 分支路由 + 群主豁免早退
- 决策点 ≥3 个：通知通道实现方式（消息转发/合并/留痕）、豁免规则的语义边界、被举报人若为 bot 自身如何兜底

不应降 `low`（非纯减法，涉及权限语义变化），但也不应升 `high`（无数据丢失/无安全风险）。

**严重问题：标签完全为空**，违反反模式硬约束："标签在不确定体系时也应给通用候选并注明需映射，**不能留空**"。

## 6. 经验教训

### 关键红旗

**这是第 9 次触发"整体降级"反模式**（#131/#132/#133/#134/#135/#136/#138/#139 之后），必须作为系统性问题处理。

### 校验失败短路器触发链路还原

字段校验失败 → 反思摘要提示 `expected <REASON>` → 分析助手误判"所有判断都不可信" → 整体退化为 `other`/`无法评估`/空标签/"无建议"。

**这正是反模式第一条明令禁止的行为**："看到 `expected <SUGGESTED_TITLE>` 等字段校验错误时，应**仅修复字段输出**，**不得把所有判断都退化为'无法评估'/`other`/空标签/无建议**"。

### 应固化的新模板：举报/通知路由类 Issue

- **触发场景**：命令通知/告警按角色分级路由；典型表现"举报 A→通知 X、举报 B→通知 Y"。
- **必查项**：举报人/被举报人角色获取 API 跨适配器差异、扇出性能、通知风暴、bot 自身被举报兜底、群主豁免检测、通知留痕。
- **分类**：`enhancement` + `breaking-change`（修改既有通知语义）+ `permission-model`，优先级 `medium`。
- **新增标签建议**：`notification-routing`、`report`/`reporting`、`reportee-role`、`reporter-role`、`notification-fanout`。

### 仓库"角色路由"模式识别

仓库历史沉淀：
- #130/#132 权限模型重构（命令执行权限）
- #131 群待办（API 权限按 bot 角色）
- #135 禁言列表（读权限分级）
- **#140 举报通知路由（按举报人/被举报人角色分发通知）**

这是**第四种角色相关模式**，应在项目记忆新增"角色路由/分级通知"模板，与权限模型重构、读权限分级并列。

### 反思 checklist 必检项（再次固化）

1. **字段校验失败 ≠ 信息不足** — 只修字段，不动判断
2. **所有"无法评估"/"无建议"/空标签/空字段都必须追问根因** — 是校验失败还是真的无信息？
