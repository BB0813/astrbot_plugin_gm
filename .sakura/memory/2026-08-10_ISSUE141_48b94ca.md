  - 建议 D 分支：先发 deprecated 警告（handler 检测后 yield 警告 + 仍然执行）→ 一个版本周期 → 真正删除。预估 30-50 行/0.5-1 天。

### 技术风险识别

✅ **识别准确的风险点**：
1. "提示成功但实际未清空"已知 bug（§4.5/#111/#119/#125/#123 沉淀）
2. 保留路径边界（/头衔、title_admins helper）
3. 用户替代路径缺失

⚠️ **遗漏的风险点**：
1. **API 客户端缓存**：OneBot 实现可能在客户端有缓存，删除命令后 `_GM_COMMAND_NAMES` 元组若残留字符串会导致 AstrBot 命令注册异常。
2. **import 链**：若 `_clear_group_title` 被其他文件引用（utils、tests、example），删除 main.py 内定义会导致 ImportError。建议 `grep -rn "_clear_group_title"` 验证。
3. **i18n/多语言文件**：若有 en_US/zh_CN 等多语言 yaml，命令别名/帮助文本是否也需要同步删除。
4. **测试用例**：若仓库有 tests/ 目录，可能有针对 unset_group_title_cmd 的单元测试，需同步清理。

### 校验流程
- ✅ `python -m py_compile main.py` 建议合理
- ✅ "最小 AstrBot 启动验证装饰器注册"建议合理
- ⚠️ 未提 `grep -rn "unset_group_title\|_clear_group_title\|取消头衔"` 残留检测——这是删除类 PR 的标准校验步骤。

## 七、经验教训与未来建议

### 本次分析的亮点
1. **正确识别"提示成功但未生效"沉淀 bug 与删除决策的耦合**——这是分析深度的体现。
2. **明确列出三个可行性分支**（虽然缺 D）。
3. **七处同步清单完整**——纯减法也能覆盖到位。
4. **保留路径边界（/头衔 + title_admins helper）**——避免误删扩散。

### 本次分析的关键问题
1. **优先级判定违反硬约束**：owner-driven 纯减法应主动降 low，但分析未显式论证为何维持 medium。
2. **重复检测措辞**：第 N 次违反"暂未发现"模板，需在前置自检中强化。
3. **可行性分支缺 D**：分阶段方案（先废弃警告 → 后删除）是 breaking-change 减法的标准风险缓冲，#139 硬约束要求必须给。
4. **OneBot 标签置信度**：未严格按 #140 红旗（API 调用类 ≥0.55）。

### 未来类似 Issue 分析模板（owner-driven 纯减法类）
- **触发**："维护者本人发起删除某命令/某功能/某配置项"
- **必查项**：
  1. 该命令/功能是否在 README/CHANGELOG/_GM_COMMAND_NAMES/help text 中注册 → 七处同步清单
  2. 是否被其他模块/测试/文档引用 → grep 全仓库
  3. 用户失去该能力后是否有替代路径 → needs-discussion
  4. 是否存在与该命令相关的已知 bug → 影响删除决策
- **优先级默认 low**：owner-driven + 纯减法 + 无横切 → 显式写"按 #130/#132/#138 硬约束默认 low"
- **可行性分支必给四档**：A 纯删除 / B 删除+替代 / C 删除+文档提示 / D 分阶段废弃警告
- **标签必给**：`enhancement` + `breaking-change` + `command-removal`/`cleanup` + `command` + `documentation` + `needs-discussion` + OneBot 相关（≥0.55）

本次 #141 适合作为仓库"owner-driven 纯减法"类 Issue 的标准案例沉淀，建议在项目记忆中新增：
