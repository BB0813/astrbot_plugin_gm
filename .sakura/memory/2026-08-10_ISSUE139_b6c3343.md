## 5. 标题改写适当性

### ❌ 标题策略错误

建议标题：
> `[enhancement][medium] 拆分 Issue：移除 /删群公告 + 新增 /取消群待办（含权限不对称风险）`

**问题**：
1. **拆分是分析结论，不应写入单个 Issue 标题**——如果真的拆分，会有两个标题
2. "含权限不对称风险"信息量过大，压缩到标题中反而模糊
3. 无法对应到拆分后的两个 Issue

**正确做法**：分别给出两个标题
- 分支 A：`[enhancement][low] 移除 /删群公告 命令（breaking-change）`
- 分支 B：`[enhancement][medium] 新增 /取消群待办 命令`

## 6. 经验教训

### 必须拆分 Issue 时的分析规范

| 要素 | 规范 |
|------|------|
| 优先级 | **分别给出**两个优先级，不可合并判断 |
| 标签 | **分别列出**两个标签集，标注"仅 X 分支适用" |
| 标题 | **分别给出**两个标题建议 |
| breaking-change | **分别评估**置信度，明确"仅 A 分支适用" |
| 工作量 | **分别估算**，显式说明分支间是否有依赖 |

### 分支 A 遗漏的决策点

分析未确认分支 A 是否为 **owner-driven**：
- 若 mjy1113451 是 owner → low（符合 #141 模板）
- 若非 owner 发起 → 需讨论是否维持 medium

应在建议指派人章节或 `needs-discussion` 中显式说明。

### 分支 B 的前置依赖

**未识别关键依赖**：分支 B 应标注"**依赖 #131 实现情况，建议 #131 合入后再评估**"或"**必须先读取 #131 代码确认 API 路径**"。当前分析将此隐含在"工作量估算"中，不够醒目。

### 权限不对称风险处理

分析正确识别了"群管理 vs 群主"权限冲突，但**未给出明确建议**：
- 选项 A：跟随 QQ 原生限制（仅群主可取消）
- 选项 B：放宽限制（群管也可取消）
- 选项 C：按配置覆盖

这属于**需要 maintainer 决策**的事项，应在 `needs-discussion` 中显式列举选项。
