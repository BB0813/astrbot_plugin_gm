## 4. 重复检测准确性

1. **置信度过低且未给依据**：未提供 #1 的标题或内容对比，仅说"可能是"违反项目记忆中的明确反模式——**不能写"未检测到重复"或"无重复"的镜像问题**。

2. **#1 通常是仓库的初始化 Issue**（README/初始功能/模板），与本 issue 主题（撤回语义优化）几乎不可能重复。

3. **正确做法**：
   - 若无法访问 #1 内容，应写"暂未发现重复，建议检索关键词：`/撤回`、`recall_cmd`、`默认 1 条`、`按编号撤回`、`@用户 N 语义`"
   - 应主动列出本 issue 的独特性：单数字路由语义决策、默认 1 条的 fallback 改造、与 PR #123 的兼容性

4. **更可能重复/关联的检索方向**：
   - 之前是否有讨论 `/撤回 N` 数量 vs 编号的 issue
   - 是否有过 `/撤回` 无参行为的反馈
   - `recall_user_cmd` 是否有过类似歧义讨论

## 6. 经验教训

### 6.1 关于"路由语义歧义"类 Issue

**模式识别**：
- 单参数 + 多语义场景是命令解析的高发歧义区
- 类似案例：`/禁言 @用户 N`（N 是时长？次数？序号？）、`/踢出 N`（N 是次数？）
- 分析时必须**显式列出候选语义并请求维护者确认**

**分析框架**：
1. 列出该数字 N 的所有可能语义（数量 / 编号 / 时长 / 次数）
2. 检查现有代码的实际语义
3. 检查文档/帮助的承诺语义
4. 标记"语义决策点"为 `needs-discussion`

### 6.2 关于"默认行为"类 Issue

**模式识别**：
- "无参 = 默认 N 条"改动看似简单，但需要：
  - 与引用撤回优先级协调
  - 与现有 fallback（用法提示）行为对比
  - 与本地缓存兜底路径对接
- 风险点：用户输入错误命令时不再看到"用法提示"，可能误触发撤回

**检查清单**（应纳入分析）：
- [ ] 默认 1 条是否会被"用户误输入空参数"触发？
- [ ] 默认 1 条是否会被"群内长消息前缀解析失败"触发？
- [ ] 引用消息存在时优先级是否仍正确？
- [ ] 默认 1 条是否需要"二次确认"机制？

### 6.3 关于重复检测的反模式

**项目记忆已强调但本次仍踩坑**：
- 写"可能是 #1 的重复"既缺乏依据又违反反模式
- 应**主动列出独特性 + 推荐检索词**，即使置信度低也比模糊"可能是"更有价值

### 6.4 仓库特有模式

**astrbot_plugin_gm 的 `/撤回` 家族**：
- `recall_cmd`（`/撤回`）：统一分发器
- `recall_user_cmd`（`/撤回用户`）：专用命令
- 二者参数语义、缓存回退、提示文案应保持对称
- **本次改动必须显式分析对 `recall_user_cmd` 的影响**，分析结果在这点上偏弱

### 6.5 标签体系的精准度

**仓库高频标签**（基于项目记忆）：
- `recall`、`message-history`、`onebot`、`command`、`parser`、`compatibility`、`group-management`
- 本次推荐的 `enhancement` + `command` + `parser` + `recall` + `needs-discussion` 组合更符合该仓库的标签生态
