# Issue #131 深度反思

## 1. 分类与优先级准确性

**分类正确**：`enhancement` 准确。本期是新增命令、非修复 bug、非纯文档、未涉及权限模型重构（无 breaking-change）。

**优先级 `medium` 合理但偏保守**：
- 维护者自提 + 改法明确 + 工作量小（80-150 行）→ 倾向 `low`
- 但**关键风险点压低优先级**：跨适配器 API 不标准 + 权限边界跨群管/群主差异 + UI 异步刷新可能让用户误判"未生效"
- 因此 `medium` 是合理下限，建议**保留 medium** 而非下调

**值得复盘的点**：分析中提到"权限校验精度"是复杂性来源，但未量化"如果群主专属要求严格，则需要新增 helper 而非复用"，这对工作量和风险评估有实质影响。下次类似 issue 应明确"权限校验是否会引入新代码路径"作为优先级因子。

## 3. 可行性判断质量

**优点**：
- 明确指出 OneBot v11 未定义群待办 API，属扩展能力（关键洞察）
- 给出三段式 fallback（标准名 → 带下划线变体 → 降级提示）
- 列出五个具体风险点，覆盖了"提示成功但实际未生效"模板的链路
- 工作量估算 80-150 行合理

**不足**：
1. **权限 helper 复用的判断需进一步收紧**：原文说"权限校验沿用 `_is_group_admin_or_owner`"，但紧接着又说"群待办按 QQ 规则多为群主专属，建议复核"——这两句话并列会误导实现者。应明确"需要新增 `_is_group_owner_only` helper"作为前置条件。

2. **`_get_reply_id` None 校验的细节缺失**：现有代码对 None 的处理是返回 False 还是发送错误提示？是否需要回退到"手动输入 message_id"模式？可行性分析应给出兜底方案的代码骨架。

3. **未量化适配器矩阵**：NapCat/Lagrange/go-cqhttp 三段覆盖之外的"未知适配器"如何处理？是否抛 `NotImplementedError` 还是静默失败？

4. **未提及与 `/设精` 的相似性复用机会**：两者都是 reply_id + 单 API 的命令结构，命令注册/权限校验/错误提示文案可大量共用，应在可行性中明确"模板代码可 80% 复用 `/设精`"。

5. **CHANGELOG 同步要求**：项目记忆的"五处→七处同步"清单提到 main.py + README + 帮助 + schema + CHANGELOG + 元组注册 + 跨适配器文档，但本次分析遗漏了"跨适配器兼容性文档"是新增条目（仓库若有 docs/ 目录）。

## 5. 标题改写适当性

**原标题**：`[enhancement][medium] 新增 /添加群待办 命令（引用消息回复即可设为群待办，仅群管/群主可用）`

**建议标题**：`[enhancement][medium] 新增 /添加群待办 命令（引用消息回复设为群待办，仅群管/群主可用）`

**评价**：
- 仅做了"即可设为"→"设为"的小幅精简，几乎无价值
- **过度保守**：项目记忆的标题改写经验建议在原标题清晰时标"可保留"而非轻量改写
- 应明确写"标题可保留"或给**有意义**的改写，如加入跨适配器警示：
  - `[enhancement][medium] 新增 /添加群待办 命令（OneBot 扩展 API，引用消息回复设为群待办，仅群管/群主可用）`
  - 这样可让后续维护者一眼看到 API 依赖的关键信息

**更好的做法**：在标题改写章节直接给出"可保留原标题"作为选项之一，避免为了"看起来有产出"而做无意义精简。

## 6. 经验教训

### 仓库特有模式（值得固化的洞察）

1. **"reply_id + 单 API"命令模板已成型**：`/设精` 是 #131 的最佳复用模板，未来类似 `/添加精华`、`/撤回某条` 等命令都可参照本 Issue 的分析结构。这是仓库特有的"轻量级命令新增"模式，建议从 #131 提炼独立小节。

2. **OneBot 扩展能力 vs v11 标准 的明确分层**：本次分析强调了这一点，但应在项目记忆中固化为"任何 OneBot API 调用前必须先回答：是 v11 标准还是扩展？扩展能力需做适配器矩阵"。这是仓库未来分析的**前置检查项**。

3. **owner-driven 命令新增 vs 权限模型重构的差异**：#131 是"加新"，#130/#132 是"改旧"——两者虽都涉及群管理权限，但风险等级、breaking-change 标签、工作量差异巨大。下次遇到权限相关 Issue 应先分类"加新"还是"改旧"再套模板。

### 分析方法改进

1. **标签置信度与项目记忆对齐机制**：本次 `onebot` 标签给了 0.55，但项目记忆明确建议 `onebot` 0.55 + `onebot-extension` 0.75-0.85 双标签。**反思时应主动 grep 项目记忆相关章节，校验标签置信度是否偏离既定基线**。建议在反思流程中加入"项目记忆标签基线校验"步骤。

2. **可行性分析的"代码骨架"要求**：仅说"复用 `_get_reply_id`"不够，应明确"如果 None 时是发提示还是进入备用输入模式"。可行性章节的最低要求是给出**关键判断分支的代码级描述**（非完整代码，但要说清 if/else 分支语义）。

3. **标题改写的"克制原则"**：原标题清晰时应明确标注"可保留"，避免为了"看起来在工作"做无意义精简。这是项目记忆反模式的延伸：**字段产出 ≠ 实质改进**。

4. **重复检测措辞必须用强制模板**：本次反思发现仍是"未检测到重复"措辞，违反明确规则。应在反思流程开头就主动核对"是否用了禁用措辞"，而非等到反思时才修正。

### 风险点校准

- **API 返回 ok ≠ UI 生效**：这一洞察在 #131（群待办）和 #125（头衔）都出现，建议从"个案洞察"升级为**仓库通用风险模板**："所有 OneBot 群管理 API 实现后必须在指令提示中加入 UI 异步刷新说明"。

- **群待办 vs 群公告 语义区分**：项目记忆已记录，但本次分析未在可行性中明确"插件应选群待办而非群公告"，应补充一句"确认维护者意图是群待办（顶部红点）而非群公告（群资料卡）"作为澄清项。
