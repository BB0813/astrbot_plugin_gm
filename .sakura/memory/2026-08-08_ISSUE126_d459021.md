# Issue #126 深度反思

## 1. 分类与优先级准确性

**分类：enhancement（0.95）** ✅ 准确
- 维护者主动请求功能裁剪，是典型的 owner-driven enhancement（功能减法而非加法）。
- "删除功能"严格来说既不是 bug 也不是新功能，但归为 enhancement 比 `refactor` 或 `breaking-change` 更贴合仓库实践（项目记忆中也多次将"功能语义调整"归为 enhancement）。
- **轻微改进**：可在分类注释中补一句"功能裁剪/语义简化"以区别于典型的新增功能 enhancement，避免后续审查者误以为是"加新功能"。

**优先级：medium** ⚠️ 偏高了
- 维护者本人提交、改动集中、影响面仅限"误用旧语法"的少量用户 —— 这是一个非常低风险的本地重构。
- 真正的风险点是文档/帮助/CHANGELOG 同步，属于"卫生问题"而非"业务影响"。
- **建议**：medium → **low** 更合理。理由：
  1. 不涉及权限、撤回、缓存等横切关注点
  2. 改动集中在一个 handler，外部接口减少（破坏性更小）
  3. 维护者即作者，沟通成本为零
  4. 项目记忆中 `low` 通常用于"文档承诺与实际能力不符"、"提示文案调整"等纯卫生问题，本案类似

## 6. 经验教训

### 本案特定教训

1. **"删除功能"类 Issue 不应自动归 medium**：维护者本人提交的、纯减法性质的功能裁剪，本质风险低于功能新增。优先级判断应考虑"主动减法 + owner 自己实施 + 无横切关注点"组合 → low 而非 medium。

2. **猜测式重复检测是高频陷阱**：项目记忆已多次警告，但本案仍出现"可能是 #87 的重复"。需要把"暂未发现 + 检索词"模板做成强制输出模板，而非每次靠自觉。

4. **`help wanted` 对 owner-driven self-implementation 几乎不适用**：维护者本人提交 + 改法明确 + 工作量小的 issue，不应推 `help wanted`。应只在"需要外部贡献者补完某子任务"时推荐。

5. **撤回类 Issue 的模块标签必须完整**：根据项目记忆，`recall`、`command`、`parser` 是本仓库撤回类标准三件套，不能漏。

### 对未来同类 Issue 的分析建议

- **功能裁剪/语义简化类**应单独建立分析模板：分类固定 enhancement、优先级默认 low（除非涉及横切关注点）、必查 CHANGELOG/help/README 三处同步、必查配置 schema 语义缩窄、必查测试用例更新。
- **每条删除请求都要列"保留路径 vs 删除路径"对照表**，避免误删相邻用法（如本案需明确"@用户 N 路径保留，"@用户 编号"路径删除"）。
- **CHANGELOG 同步应在改动点列表中默认占一席**，与 README/help 同等优先级，而非可选。
- **配置 schema 字段语义变化**（如 `batch_max_count` 从"约束两种分支"变为"仅约束按数量分支"）必须显式列为改动点，不能用"措辞微调"糊弄。

### 仓库特有模式补充

本仓库的 `/撤回` 命令族经历了多轮迭代（按数量、按编号、按用户、按引用、撤回自身），每次新增/裁剪都会涉及 main.py + README + 帮助 + schema + CHANGELOG 五处同步。建议在项目记忆中将"撤回命令族五处同步清单"固化为强制输出模板，下次再遇到 `/撤回` 相关 issue 时直接套用。
