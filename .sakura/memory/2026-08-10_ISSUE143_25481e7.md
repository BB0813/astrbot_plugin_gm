### 分类判断
- **`enhancement` (0.95)**：✅ 准确。本 Issue 是新增"踢人后联动清历史"功能，纯加法诉求，未要求删除任何既有命令或破坏既有接口。
- **分类候选检视**：是否应标 `breaking-change`？答案：否。三条子诉求均属新增能力，不删/不改既有命令语义（虽然可能改 `_conf_schema.json`，但属于 schema 扩展而非破坏）。

### 优先级判断
- **判定理由显式梳理**：
  1. 涉及高风险动作（踢人 + 批量撤回）→ 不应低于 medium。
  2. 是新增功能而非修复 bug → 不应升 high。
  3. 配置可关闭（默认 false）→ 默认安全，不会对存量用户造成意外。
  4. 跨适配器风险已识别但有降级（本地缓存兜底）→ 维持 medium。
- **结论 medium 合理**。✅

### 影响范围评估
- ⚠️ **遗漏了"bot 自身权限"分析**：批量调用 `delete_msg` 需要 bot 是群主/管理员吗？多数 OneBot 实现不要求，但若消息是群主发的，bot 是否能撤需要适配器层面验证。这是一个**未在分析中显式提出的技术风险**，建议在难点 D 之后补充"难点 F：bot 权限与可撤回消息发起者的关系"。

- **分支 C 400-600 行 / 7-10 天**：合理但偏上限。"通用 helper 抽取"是工程化重构，工作量评估合理。

### 技术依赖识别

- ✅ 跨适配器差异：已显式列出 NapCat/Lagrange/go-cqhttp。
- ⚠️ **遗漏：bot 账号被踢风险**。批量调用 `delete_msg` 可能触发服务端风控导致 bot 短暂封禁，需在难点中显式提出"难点 F：批量 API 调用风控与 bot 临时封禁"。

- ✅ OneBot 2 分钟时间窗约束。

## 六、经验教训沉淀

### 新沉淀（仓库第 5 种模式确认：**动作联动型**）

**触发场景**：动作 A 成功后自动触发动作 B（kick → clear-history / ban → notify / mute → log 等），且 A 与 B 共享配置与权限。

**与已有 4 种模式对比**：

| 模式 | 案例 | 触发源 | 关注点 |
|---|---|---|---|
| 1. 权限模型重构 | #130/#132/#139 | 全局替换 plugin_admins | 兼容性、回退路径 |
| 2. 引用消息触发型 | #131 群待办 | reply_id 解析 | 跨适配器 reply API |
| 3. 装饰字符 QQ | #134/#136 | 用户名输入 | NFKC/白名单/适配器差异 |
| 4. 举报/通知路由 | #140 | 命令触发按角色路由 | 通知风暴/隐私/恶意刷 |
| **5. 动作联动型（新增）** | **#143** | **A 成功后触发 B** | **回执一致性/通知风暴/限流/可配置** |

### 动作联动型模板必查项
1. **回执一致性**：动作 B 部分失败时如何回执 A 的成功状态？
2. **通知风暴**：B 触发群内"撤回消息"提示是否影响体验？
3. **限流策略**：B 是高成本动作（API 调用 N 次），如何分批？
4. **配置粒度**：是否可关闭？是否可调上限？是否按群覆盖？
5. **权限双校验**：A 和 B 各自权限如何对齐？bot 自身权限边界？
6. **时间窗约束**：B 是否有协议级时间窗（OneBot 2 分钟）？
7. **跨适配器差异矩阵**：B 所依赖 API 的适配器差异？
8. **本地缓存兜底**：B 失败时是否复用既有缓存？
9. **可观测性**：成功 N/M、跳过 X 条因时间窗、失败 Y 条因限流 的分类回执。
10. **去重**：本地缓存与服务端历史可能产生重复 message_id。
