# Issue #125 分析反思

## 核心问题诊断

本次分析触发了项目记忆中**最关键的反模式**——**结构化输出校验失败导致整体降级**。摘要明确显示：`AI Issue analysis output could not be validated: expected <REASON>`，这是字段输出校验失败，但分析结果却把所有实质性判断都退化为：

- 分类退化为 `other`（实际应为 `bug`）
- 可行性退化为"无法评估"（实际有充分信息可条件性判断）
- 建议标签为空（实际应给模块/根因标签）
- 建议标题为"无建议"（被反模式明确禁止）

**根本原因**：未遵守 Pre-check 规则——校验失败应**仅修复字段输出**，不得影响实质性判断。

## 6. 经验教训

### 本次触发的核心反模式（再次重申）

**结构化输出校验失败 ≠ 信息不足**。本次 Issue 信息量充足，却因字段校验失败整体退化为空，**完全违反**项目记忆中的 Pre-check 规则。正确做法：
1. 先完成所有实质性判断（分类、优先级、可行性、标签、标题）
2. 仅在输出层修复校验失败的字段
3. 校验失败不应触发任何实质性判断的降级

### 头衔类 Issue 标准分析模板

基于项目记忆 §3 和本次 Issue，应固化以下分析动作：
1. **必查项**：Bot 在该群角色、目标用户身份、OneBot 实现版本、插件版本/commit、`_extract_at_qq` 解析、`special_title` 传参（`""` vs `" "` vs 空白）、是否 `get_group_member_info` 回读
2. **必加标签**：`bug` + `command` + `group-management` + `title`/`special-title` + `onebot`/`compatibility` + `needs-info`
3. **必给需求**：Bot 权限状态、最近配置变更、OneBot 实现版本、完整执行日志
4. **典型根因**：① API 返回成功但缓存未刷新 ② `special_title` 传 `""` 被某些适配器忽略 ③ Bot 非管理员/群主但未校验 ④ 目标为群主，QQ 限制无法修改

### "提示成功但实际未生效"类 Issue 通用模式

这是 AstrBot 群管插件的高频 bug 模式，应建立标准化分析路径：
- 分类必为 `bug`
- 优先级 `medium`（单群可控）或 `high`（权限校验缺失时）
- 根因排查链路：命令解析→权限判断→API 参数→适配器兼容→API 返回值→**状态回读**→用户提示
- 修复方向：补 `get_group_member_info` 回读 + 明确传参语义 + 适配器差异处理

### 重复检测措辞铁律

任何"暂未发现"场景必须给出建议检索关键词，**禁止**使用"未检测到重复"/"无重复"等绝对化措辞。本规则已被项目记忆反复强调，本次仍违反，说明规则在执行层未真正落地。

## 总结

本次分析是项目记忆 §1"结构化输出校验失败 ≠ 信息不足"反模式的**典型样本**：输入信息充足、字段校验失败、整体降级为空。修复方向明确——**先做判断，再修输出**，分类必为 `bug`，标签必给候选，标题必改写，重复检测措辞必带检索词。可行性可做条件性判断（低-中等风险，低-中等工作量）。
