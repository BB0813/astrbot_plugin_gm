## 1. 分类与优先级准确性

**分类为 `question` 基本合理，但可考虑 `documentation` / `compatibility` 辅助定位。**

该 Issue 的正文并不是典型“功能异常”或“报错堆栈”，而是用户执行：

```text
/撤回 @You have no egg 1
```

后收到插件提示：

```text
当前 OneBot 实现不支持按用户撤回（缺少 get_group_msg_history）。
请使用 /撤回 + 引用消息 撤回指定消息。
```

结合分析结果中对 `main.py` 的确认：插件已有 `/撤回 @用户 N` 路径，逻辑依赖 OneBot action `get_group_msg_history`。当当前 OneBot 实现不支持该接口时，插件无法获取群历史，也就无法筛选指定用户消息。因此这更像是**适配器能力限制说明 / 使用问题 / 文档说明不足**，而不是插件自身逻辑 bug。

不过，如果从用户体验角度看，用户可能认为“命令支持但实际不可用”，所以也可以补充考虑：

- `compatibility`：与 OneBot 实现能力有关；
- `documentation`：README / 帮助中应明确依赖；
- `recall` / `message-history`：如果仓库有细分标签。

**优先级 `low` 合理。**

原因是：

- 不影响插件启动；
- 不影响引用消息撤回；
- 不影响已知 `message_id` 的删除；
- 仅影响部分 OneBot 实现下的“按用户撤回”高级用法；
- 插件已经给出了明确降级提示。

除非后续发现 README 明确承诺所有 OneBot 实现都支持 `/撤回 @用户 N`，或者该命令是核心高频功能，否则不应升到 `medium`。

## 3. 可行性判断质量

可行性评估整体质量较高，主要优点是**确实结合了代码路径**，而不是只根据 Issue 文本推断。

分析中提到了：

- `recall_cmd` 注册为 `/撤回`；
- 帮助说明中已有 `/撤回 + 引用消息`、`/撤回 @用户 N`、`/撤回 N`；
- 按用户撤回会通过 `_extract_at_qq(raw)` 提取目标用户；
- 再调用 OneBot action `get_group_msg_history`；
- 历史为空或接口不可用时输出 Issue 正文中的提示；
- 因此缺少历史接口时插件没有足够数据完成按用户筛选。

这些判断比较扎实。

### 工作量估算合理

将改动分为两类是正确的：

#### 低复杂度方案

- README 增加说明；
- 命令帮助增加依赖提示；
- 错误提示增加建议，例如“请切换支持 `get_group_msg_history` 的 OneBot 实现”。

这类工作量小、风险低，符合 `low`。

#### 高复杂度方案

如果要在没有 `get_group_msg_history` 的情况下支持按用户撤回，就需要插件自行维护消息索引缓存。分析中已经识别了关键风险：

- 需要监听群消息；
- 需要缓存生命周期管理；
- 重启后缓存丢失；
- 消息顺序问题；
- 撤回时间限制；
- 权限和隐私问题；
- 多群隔离；
- 缓存大小控制。

这说明技术依赖和风险识别较充分。

### 可进一步补充的点

可行性分析还可以补充两点：

1. **接口返回格式差异风险**

不同 OneBot 实现即便支持 `get_group_msg_history`，返回字段结构、排序、数量限制也可能不同。按用户撤回逻辑应注意：

- `messages` 字段是否存在；
- `message_id` 类型；
- `user_id` 字段位置；
- 历史顺序是正序还是倒序。

2. **提示信息不应误导**

如果当前提示是：

```text
当前 OneBot 实现不支持按用户撤回
```

这已经很准确。可以进一步优化为：

```text
当前 OneBot 实现不支持 get_group_msg_history，无法按用户筛选历史消息。
请使用引用消息撤回，或切换支持群历史接口的 OneBot 实现。
```

这样能降低用户继续误报的概率。

## 6. 经验教训

### 经验一：撤回功能要区分“插件 bug”和“适配器能力限制”

`/撤回` 类问题容易被误判为 bug，但本例中插件已实现按用户撤回逻辑，只是依赖 OneBot 历史消息接口。没有 `get_group_msg_history` 时，插件无法凭空知道某个用户最近发了哪些消息。

未来分析类似 Issue 时应先判断：

1. 命令入口是否存在；
2. 参数是否正确解析；
3. 是否获取到了目标用户；
4. 是否依赖群历史接口；
5. OneBot 实现是否支持该 action；
6. 是否已经有友好降级提示。

不能只因用户说“不能撤回”就直接归为 bug。

### 经验二：`/撤回 @用户 N` 的关键依赖是消息历史

按用户撤回和引用撤回不同：

- 引用撤回：已有明确 `message_id`，可直接 `delete_msg`；
- 普通 `/撤回 N`：需要从群历史找最近 N 条消息；
- `/撤回 @用户 N`：更需要群历史，并按 `user_id` 过滤。

所以只要涉及“非引用撤回”，就应重点检查：

```text
get_group_msg_history
message_id
user_id
消息排序
当前命令是否包含在历史中
接口不可用时的降级提示
```

### 经验三：文档和命令帮助要提前说明接口依赖

如果 README 或帮助中写了：

```text
/撤回 @用户 N
```

但没有说明依赖 `get_group_msg_history`，用户自然会认为所有 OneBot 实现都支持。  
建议未来对依赖适配器能力的命令统一标注：

```text
该功能依赖 OneBot 实现支持 xxx action。
若不支持，请使用 yyy 替代。
```

### 经验四：不要把“可实现替代方案”低估为简单修复

表面上看，没有历史接口时可以“插件自己缓存消息”。但这实际牵涉较多复杂问题：

- 插件是否能监听所有群消息；
- 缓存是否覆盖机器人重启前消息；
- 缓存量和过期策略；
- 多群隔离；
- 隐私合规；
- 消息撤回时限；
- bot 权限；
- 与 OneBot 历史接口结果一致性。

因此分析中将其判定为高工作量、高风险是合理的。

### 经验五：标签应突出兼容性

本例只给出 `question` 和 `documentation` 还不够完整。  
未来遇到“某 OneBot 实现不支持某 action”的 Issue，应优先考虑：

```text
compatibility
adapter
onebot
documentation
```

如果仓库没有这些标签，也应在建议中说明“可映射为兼容性类标签”。
