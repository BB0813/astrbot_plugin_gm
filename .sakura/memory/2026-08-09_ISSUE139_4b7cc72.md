# Issue #139 深度反思

## 1. 分类与优先级准确性

### 分类判断
- **分类 `enhancement` 准确**：本质是 owner-driven 接口收窄+接口扩展的混合改动，新功能占主导（添加 `/取消群待办`），删除占次要。无运行时报错或行为缺陷证据，不应为 `bug`。
- **但缺少 `breaking-change` 标签是遗漏**：删除既有 `/删群公告` 命令对已部署用户脚本/教程而言是 breaking change。项目记忆已明确强调 `breaking-change` 应作为独立标签，且 #130/#132 权限模型重构类已强制此纪律。
- **`enhancement` 置信度 0.95 合理**：owner-driven + 功能新增，与 #131/#135 同模式。

### 优先级判断
- **优先级 `medium` 合理**：与 #131 群待办完全对等的工作量级（100-150 行 + 跨适配器兼容），属于群管理命令新增的标准工作量。
- **但未按反模式硬约束显式列出决策路径**：项目记忆 #133/#135 沉淀了"优先级决策路径必须显式列出（4 条判定路径）"的硬约束，本反思分析中完全缺失。应补充：
  1. 横切范围（命令新增+命令删除）→ 最低 medium
  2. owner-driven + 已有标准化模板 → 不升 high
  3. 工作量可控（≤3 天）+ 迁移路径明确 → 不升 high
  4. 跨适配器风险已识别但有 #131 同源兜底 → 维持 medium
- **未做同类 Issue 显式互引对比**：项目记忆 #135/#136 沉淀了"同类/同工作量 issue 应在优先级章节显式对比说明一致性（如 #135 与 #131 群待办对比），给出'与 §X 同级，因 Y 原因定 medium'的对比句"。本反思既未与 #131 群待办对比，也未与 #130 权限重构类对比。应补充："与 #131 同级（同等工作量、同等跨适配器风险），因 owner-driven + 删除侧简单 + 新增侧模板完整，不升 high"。
- **优先级定性论证欠充分**："与 #131 群待办对称"已多次出现但本反思未量化对称性风险（如权限对称失败可能让群管能取消他人群主群待办）。

## 3. 可行性判断质量

### 工作量估算整体合理
- **A. 删除侧**：`~30-60 行代码删除 + 五处同步`，半天到 1 天，符合"删减类 issue 检查清单"模式（调用点清空、帮助/README/docstring 同步、CHANGELOG/公告、剩余路径边界、用户迁移路径）。
- **B. 新增侧**：`~100-150 行新增 + 五处/七处同步`，1-2 天，符合 #131 同源模板复用预期。
- **合并实施**：2-3 天合理。

### 但存在三个盲点

**盲点 1：未显式分支判定（违反 #133/#135 硬约束）**
项目记忆硬约束："可行性章节必须显式分支判定 A/B/C 三档（最小/完整/合并实施），禁止只给范围估算不显式分支"。本反思虽在末尾提到 A/B/C 但仅在工作量估算末尾一句话带过，未在每个独立子项（A 删/B 增）内显式给出三档分支。

应修正为：
- A 删：A1 仅删命令（30-60 行/半天）/ A2 删命令+清空所有下游调用点+迁移指南（~50-100 行/1 天）
- B 增：B1 最小对称实现（100-150 行/1-2 天）/ B2 完整实现含跨适配器 fallback 文档+权限对称校验+CHANGELOG（200-300 行/3-4 天）/ B3 与 A 合并实施（300-400 行/3-5 天）

**盲点 2：跨适配器 API 形态盲区未量化**
"OneBot API 形态未明（部分实现可能没有反向 API，需通过'清空所有 + 重设'或仅暴露添加语义）"是关键不确定项，但未量化分支：
- 若 NapCat 提供 `_unset_group_todo` → B1 分支（1-2 天）
- 若仅 Lagrange 提供反向 API → 需加适配器 fallback 逻辑 → B2 分支（3-4 天）
- 若所有适配器都仅支持"清空+重设"间接方案 → 需重新设计接口语义 → B3 分支（5+ 天）

**盲点 3：行号引用合规性已声明**
已显式声明"以下行号基于项目记忆与既有 PR 模式推断，PR 实际编写时以最新 main.py 行号为准"，符合 #134 沉淀的"行号引用必须可溯源"规范。

### 删除侧的"剩余路径边界"未深入
项目记忆"删减类 issue 检查清单"包含"剩余路径边界"——删除 `/删群公告` 后是否影响：
- 帮助文本中相关交叉引用

### B. 仓库特有模式沉淀

**模式 1：对称命令配对类 Issue 模板（建议新增）**
- 触发场景：与既有命令语义对称的撤销/反向命令新增（如本 Issue `/取消群待办` vs #131 `/添加群待办`）。
- 必给标签：`command` + `group-management` + `enhancement` + `onebot-extension` + `reply` + `bot-capability` + `permission`(≥0.55) + `breaking-change`(若涉及删除) + `needs-discussion`(≥0.75) + `configuration`(≥0.55 若新增配置)。
- 必查项：① 反向 API 是否存在或仅支持"清空+重设"间接方案 ② 权限模型严格对称（添加权限=撤销权限） ③ reply_id 解析对称 ④ 跨适配器 fallback 矩阵 ⑤ 与父命令 #131 的代码复用度评估 ⑥ UI 生效延迟对称。
- 优先级决策路径：① owner-driven + 模板完整 → 不升 high ② 工作量可控 + 跨适配器 fallback 已识别 → 维持 medium ③ 涉及删除既有功能 → 最低 medium ④ 与同期权限重构 #130 方向冲突 → 升级 `needs-discussion`。

**模式 2：删减类 Issue 的"剩余路径边界"检查模板（建议新增）**
- 触发场景：维护者本人发起的纯减法性质功能裁剪（如本 Issue 删 `/删群公告`）。
- 必查项（项目记忆已有但需补全）：
  ① 删除目标精确到 Path 分支/行号
  ② 被删功能的内部辅助函数是否被其他命令复用
  ③ 配置 schema 中对应配置项是否需要清理
  ④ 帮助文本交叉引用
  ⑤ 用户迁移路径（替代命令/教程更新）
  ⑥ CHANGELOG 公告
  ⑦ README 中相关截图/示例清理
  ⑧ 已部署用户的脚本兼容性影响范围
- 优先级建议：维护者本人纯减法 → `low` 组合（主动减法+owner 自实施+无横切关注点），但删除的若是核心命令或高频使用命令 → 升级 `medium`。
