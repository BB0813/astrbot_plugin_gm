## 四、经验教训

### 1. 增量审查的"只见树木"风险
本次变更被正确 approve，但：
- 审查者若查看完整方法，会发现 `_msg_save_counter` 重置后立即生效（下次调用从 0 开始）
- 这意味着"50 条写一次"这个设计意图**取决于重置顺序**——这是增量审查难以察觉的

### 2. "安全优先" vs "增量保守"
| 策略 | 优点 | 风险 |
|------|------|------|
| 只看增量 | 快速响应，聚焦问题 | 可能遗漏上下文关联 |
| 查看完整方法 | 发现隐含依赖 | 效率下降 |

**建议**：对于涉及**状态机/计数器**的变更，应扩展至完整方法上下文。

### 3. 防御性编程的审查要点
```python
# 重置顺序错误的潜在后果：
save_stats() 失败 → _msg_save_counter = 0 已执行 → 
下一批消息从 49 开始计数 → 第 50 条时才触发下一次保存
# 结果：丢失一批消息的计数

# 修复后的逻辑：
save_stats() 失败 → _msg_save_counter = 0 未执行（仍为49）→
下一批消息从 49+1=50 开始 → 立即触发保存 → 
结果：触发重试，数据有机会被保存
```
