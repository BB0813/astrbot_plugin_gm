# Issue #142 分析反思

## 1. 分类与优先级准确性

**分类（enhancement）准确**：核心诉求是新增能力（自动+手动批量撤回），非 bug 修复、非纯减法。维护者自提，无歧义。

**优先级（medium）判断准确**，但需复核三条理由的强度：

- ✅ **横切权限维度**：批量撤回横切"删除他人内容"权限面，但默认关闭 + 群主/管理员主动触发 = 主动决策，**远低于误删/越权类 high**。
- ✅ **owner-driven 维度**：#131/#138/#140 沉淀，owner 自提 + 已有标准化模式（复用 `/踢`+`/撤回用户`）不应升 high。
- ✅ **工作量可控 + 迁移路径明确**：分支 A 仅 80-120 行，1.5-2 天可上线；默认关闭 = 零迁移成本。
- ⚠️ **风险已识别但有兜底**：2 分钟撤回时限、API 限速、跨适配器差异——这些是**已知风险且有降级路径**（失败跳过+节流），不构成 high。

**与 #140 决策路径的对比**（#140 也是 enhancement+medium，可作为参照系）：
- #140 涉及**权限矩阵 9 组合 + 通知风暴 + 隐私脱敏**——横切面更广。
- #142 涉及**批量删除他人消息 + 跨适配器历史回读**——横切面接近。
- 两者均为 medium 是合理的，但 #142 应在优先级章节**显式对比 #140**（"与 #140 同级，决策路径同构"），目前缺失这条互引。

**未显式给出的警示**：如果配置 schema 中 `auto_recall_on_kick_enabled` 默认值是 `true`（即使是 owner-driven），`breaking-change` 风险会显著上升，应升 high。分析中虽提及"默认 false"，但未把"默认值"作为优先级决策路径的第 5 条。建议补充：**"默认值决策：默认 false → medium；默认 true → high（silent behavior change）"**。

## 3. 可行性判断质量

**优点**：
- 工作量估算给出 A/B/C/D 四档（符合 #139 硬约束）。
- 核心改造点分 4 个模块清晰列出。
- 风险与必查项识别到位（撤回时限、限速、自身消息排除、缓存写入对称性）。

**需补充/校准**：

**1. 缓存骨架集成度未量化**：分析说"复用 PR #123 本地缓存骨架"，但 `message_history` 的实际容量、`deque maxlen` 默认值、是否在所有群启用、是否在 bot 重启后清空——这些都直接影响"全量撤回"的真实上限。**必查项应列**：
- `message_history` 实际 maxlen（决定"全量"语义边界）
- bot 重启后是否清空（决定"全量"是否依赖历史接口兜底）
- 跨群隔离 vs 共享（决定踢 A 群用户是否会误用 B 群缓存）

**2. `_iter_user_recallable_messages` helper 的接口设计**未明确：
- 是否要返回 `(message_id, time)` 元组（用于 2 分钟时限检测）？
- 是否要支持 `since_time` 过滤（踢出后增量）？
- 失败时返回什么（None/空列表/异常）？
- 至少应在分析中给个**接口草图**。

**3. 配置 schema 的 `group_overrides` 嵌套结构**未展开：
- 是 `group_overrides: { "123456": { "auto_recall_on_kick_enabled": true } }`（扁平键覆盖）还是 `group_overrides: { "123456": { ...全量配置... } }`（全量覆盖）？
- 跨群生效顺序（全局 → 群覆盖 → 用户覆盖？）需明确。
- 这一决策应在 `needs-discussion` 章节显式列出。

**4. 跨适配器差异矩阵未沉淀**：
- NapCat / Lagrange / go-cqhttp 三家对 `get_group_msg_history` 的最大返回条数差异（已知 NapCat 默认 20，go-cqhttp 可配）。
- `delete_msg` 限速差异（已知差异较大，从 1/s 到 5/s 不等）。
- 应建**跨适配器速率限制矩阵**作为沉淀，类似 #135/#136 的字段差异矩阵。

**5. 节流方案**未细化：
- `asyncio.sleep` 是最简单的节流，但全局 `sleep` 会阻塞事件循环其他协程。
- 推荐**令牌桶 / 滑动窗口**或**专用节流队列**。
- 至少应在分析中点出"全局 sleep 可能影响 bot 其他命令响应延迟"。

## 6. 经验教训

### 6.1 仓库新沉淀（本 Issue 应补充的模式）

**撤回增强类 Issue 第 5 种角色相关模式**（继 #122/#124/#126 之后的延伸）：

- **触发场景**：`/踢` + 自动/手动批量撤回被踢用户本群全部历史。
- **必查项**：
  1. OneBot `get_group_msg_history` 跨适配器最大返回差异矩阵
  2. `delete_msg` 限速差异矩阵
  3. 2 分钟撤回时限逐条检测
  4. 缓存骨架（PR #123）的真实容量与重启语义
  5. 自身消息排除（`after_message_sent` 早退前写入）
  6. 业务早退链吞噬共享逻辑规避
  7. 跨群隔离 vs 共享（缓存 key 设计）
  8. "全量"语义在 README 的诚实告知
  9. 节流方案选择（全局 sleep vs 令牌桶）
  10. `group_overrides` 嵌套结构与生效顺序
- **必给标签**：`enhancement`(0.95) + `recall`(0.95) + `command`(0.95) + `message-history`(0.90) + `group-management`(0.88) + `configuration`(0.85) + `onebot`(0.80-0.85) + `onebot-extension`(0.55-0.65, 仓库新建) + `throttling`/`rate-limit`(新建) + `pagination`(新建) + `silent-behavior`(默认 true 时) + `partial-failure`(新建) + `needs-discussion`(0.85) + `needs-info`(≤0.30) + `breaking-change`(0.30-0.40 默认 false 时)。
- **优先级**：`medium`（默认关闭 + owner-driven + 工作量可控 + 风险有兜底）。
- **可行性分支**：A 80-120 行 1.5-2 天 / B 200-350 行 3-5 天 / C 350-500 行 5-7 天 / D 分阶段先 A 后 B/C。
- **标题范式**：`[enhancement][medium] /踢 后按配置自动/手动批量撤回被踢用户本群全部聊天记录（支持按群覆盖）`。

### 6.2 跨 Issue 决策路径对比模板（应作为新沉淀）

当两个 Issue 决策路径同构时（如 #142 与 #140），应在优先级章节**显式互引**：
> "本 Issue 与 #140 决策路径同构（横切权限但有兜底 / owner-driven + 已标准化模式 / 工作量可控 + 迁移路径明确 / 风险已识别但有降级），维持 medium 优先级。"

这条规则目前未沉淀，是 #142 反思首次识别。

### 6.3 重复检测措辞强制模板的违反

本 Issue 第 9-10 次触犯反模式"未检测到重复"。**校验失败短路器自检门槛必须前置**——任何字段出现"无"/"未"/"0"/空字符串前，先确认是否源于校验失败。**本 Issue 这次违反的不是校验失败，而是**反模式明确禁止的措辞"未检测到重复"。**需升级为硬约束**：
> 任何包含"未检测到重复"/"无重复"/"可能是 #X 重复"的输出，**必须改写为"暂未发现重复，建议检索关键词：..."**，无例外。

### 6.4 `breaking-change` 置信度的精细化

#139 沉淀的"删除侧 0.90-0.95，新增侧 ≤0.30"是粗粒度。#142 暴露了**第三种情况**：**新增配置项但修改全局默认行为**——如果默认值从"无"变成"true"，即使是新增配置项也属于 silent behavior change，应给 0.55-0.65（介于新增侧 0.30 与删除侧 0.95 之间）。**新规则**：
- 新增配置项 + 默认 false/缺省：≤0.30
- 新增配置项 + 默认 true：0.55-0.65（silent behavior change）
- 修改既有配置项默认值：0.70-0.80
- 删除既有配置项/命令：0.90-0.95

### 6.5 缓存骨架集成度的代码层验证

PR #123 的 `message_history` 是骨架，是否已 merge、容量多少、是否启用——这些在分析中**必须查证而非假设**。如果 PR #123 未 merge，则 #142 的分支 A 工作量会**翻倍**（需要先建缓存），可行性评估基础发生变化。建议分析中**显式标注依赖状态**："假设 PR #123 已 merge（待查证）"。

### 6.6 默认值决策必须显式列入优先级路径

owner-driven Issue 的"默认开启 vs 默认关闭"是优先级决策的核心变量，但 #133/#135/#139/#140 的优先级路径 4 条**均未涵盖默认值**。建议**升级为 5 条**：
1. 横切权限 + breaking-change → 最低 medium
2. owner-driven + 已标准化模式 → 不升 high
3. 工作量可控 + 迁移路径明确 → 不升 high
4. 跨适配器风险已识别但有兜底 → 维持 medium
5. **默认值决策（默认 false → 维持；默认 true → 升 high/silent behavior change）**
