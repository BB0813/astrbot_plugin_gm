5. **本地缓存不写入 `recall_cmd` 的"命令自身"**：当前 `/撤回 N` 路径要排除当前 command message，但本地缓存回退分支是否做了同样的 `event.message_id` 排除？审查摘要只提了"成功消息追加后缀"，未触及

## 二、发现的模式

### 代码模式

1. **「注释承诺 vs 实际行为」不一致**：本次审查发现两处——`recent_messages` 注释写 `deque[(message_id, user_id), ...]` 实际是 dict；`after_message_sent` 注释承诺「记录 bot 自身发言」但被早退跳过。这是同一类反模式：**注释描述的是设计意图，代码实际执行的是早退后的子集**。建议在审查清单中加一条「注释与代码路径一致性」专项检查

2. **早退语句吞噬共享逻辑**：`after_message_sent` 当前的早退链是「无 raw → 无 group_id → 未启用 → 不在启用列表 → 无关键词 → 无文本 → 无关键词命中」，把"bot 消息缓存"放在早退链之后是典型的逻辑分层错误。共享的基础设施（缓存、统计、日志）应在所有早退之前，业务特化逻辑（自动撤回、关键词匹配）在早退之后

3. **OneBot 兼容性回退的通用模式**：本地缓存 + 标记后缀（来自本地缓存）是项目记忆 §4.4 沉淀的标准回退模式。本次实现完整遵循——先尝试原生接口 → 失败回退本地 → 双重失败才报错 → 成功时附加来源标识。这种"分层降级 + 透明标识"模式值得作为 PR 模板示例

4. **`defaultdict(lambda: factory)` 的微妙陷阱**：当前 `.get()` 安全，但 `if k in self.recent_messages` 不安全。防御性建议是改用普通 dict + setdefault，或保留 defaultdict 但加注释警告

### 架构观察

1. **本地缓存的"进程内、内存态、无持久化"本质**：当前实现合理（QQ 消息历史本身就不持久），但需要明确边界——重启即丢、跨实例不可见、缓存期外的消息不可撤回

2. **bot 消息获取路径不对称**：
   - 用户消息：必经 `on_group_message` → 必入缓存
   - bot 消息：经过 `after_message_sent` → 但被早退跳过
   这种不对称是 major bug 的根源，也提示**bot 消息的缓存入口应该独立于业务早退链**

3. **缓存容量与功能上限的耦合**：maxlen=100（容量）vs N 上限 50（功能）vs 撤回时限（2 分钟）三层约束应一起考虑。当前回退路径在缓存不足时会误报"未找到"，但未在 UI 层面区分"缓存未积累"和"真没有这条消息"

## 三、规范完善建议

### 新增审查规则

#### 规则 R-1：注释与代码路径一致性检查
**触发条件**：审查中发现注释描述了某种"应该发生"的行为，但代码路径（早退/异常/分支）可能导致该行为被跳过
**检查动作**：
- 对每个"基础设施写入"（缓存、统计、日志、监控），确认其位置**先于所有业务早退**
- 对每个"功能开关"，确认关闭时不影响基础设施写入

#### 规则 R-2：缓存/计数器写入点位置审查
**触发条件**：新增了 `deque/list/counter` 等内存数据结构 + 多个写入点
**检查动作**：
- 列出所有写入点的调用链，确认它们是否会被外层早退/异常跳过
- 对每个写入点，确认它的可达性与设计意图一致
- 特别检查 `on_event` vs `after_event` 的对称性

#### 规则 R-3：本地缓存回退路径的完整技术考量清单
**触发条件**：新增本地缓存作为 OneBot 接口不可用时的回退
**必须验证**：
- ① 缓存容量与功能上限的耦合（maxlen vs N）
- ② 时间窗限制（撤回时限）
- ③ 当前命令自身的排除
- ④ 并发/顺序保证（单线程 OK，多线程需加锁）
- ⑤ bot 消息的独立写入路径
- ⑥ 用户消息与 bot 消息的对称覆盖
- ⑦ 重启/跨实例的边界说明
- ⑧ README/帮助/schema 同步

### 修改现有规范

#### 项目记忆 §4.3 补充：bot 消息缓存的独立性原则
> **bot 消息的本地缓存写入必须独立于任何业务早退链**。`after_message_sent` 中的缓存写入应置于所有 `if not enabled: return` / `if not in list: return` 之前，确保即使自动撤回功能未启用，bot 自身发言也能被 `/撤回 N` 回退路径命中。

#### 项目记忆 §4.4 补充：本地缓存容量的多层约束
> 本地缓存 `maxlen` 应与以下三个约束联合考虑：① `/撤回 N` 中 N 的上限；② 撤回时限（QQ 普通成员 2 分钟、管理员更长）；③ 缓存期内的预期消息密度。建议 maxlen ≥ 4 × N，作为安全余量。

#### 新增章节 §4.6：审查评分校准
基于本次审查（4/10，request_changes），补充：
> 涉及撤回/缓存等核心命令回退路径的 bug，无论代码量大小，影响面涉及「绝大多数未启用某配置的群组」时，评分上限不超过 5/10，决策应为 request_changes 或 comments。

## 四、经验教训

### 1. 「早退语句吞噬共享逻辑」是高频陷阱

本次 major bug 的本质是：把基础设施写入（缓存）放在了业务早退（关键词撤回配置检查）之后。这种模式在事件处理、AOP、中间件、装饰器链中都很常见。审查时**应主动列出所有早退点，标记哪些是"基础设施"哪些是"业务特化"，并验证它们的位置关系**。

### 2. 「注释即承诺」原则

每条注释都是对代码行为的隐性承诺。当审查发现注释描述的行为与实际不符，无论大小都应标记。本次同时发现两处（注释写 tuple 实际是 dict、注释承诺记录 bot 发言实际被跳过），说明这是项目级的代码卫生问题，不只是个别疏漏。

### 3. 本地缓存回退是「看似简单实则复杂」的典型

项目记忆 §4.3 已经沉淀了批量撤回的 9 项技术考量。本地缓存看似只是"再加个 deque"，但实际涉及：
- 写入入口的对称性（用户 vs bot）
- 容量与功能上限的耦合
- 时间窗与撤回时限
- 重启边界与文档同步
- 命令自身的排除
- 排序方向（倒序取最近 N 条）

**审查此类 PR 时，应主动对照「批量撤回完整技术考量」清单逐项打勾，而不是只检查"缓存写入了没有"。**

### 4. 「AST 扫描 OK」≠「行为正确」

PR 描述中的验证只用了 `ast.parse` 和 `json.load`，确认无语法错误和 schema 合法性。但本次 major bug 完全是**逻辑/路径问题**，AST 扫描无法发现。验证清单应至少包括：
- 主路径功能测试（`/撤回 1` 在未配置 auto_recall 的群里能否撤回 bot 自己？）
- 边界测试（缓存为空、缓存不足 N 条、N=50 maxlen=100）
- 早退路径测试（每个早退分支触发后，缓存是否仍被写入）

### 5. 「issue 编号即测试用例」原则

本次 PR 引用了 #117 #118 #119，审查时**应把这三个 issue 的"用户故事"作为最小验收用例**：
- #119：用户调用 `/取消头衔 @空格头衔用户`，期望看到"取消成功"且用户头衔真的为空 ✓（已修复）
- #117：用户在不支持 history 的群里 `/撤回 @用户 3`，期望撤回该用户最近 3 条 ✗（当前实现因 bot 缓存被跳过，回退只覆盖用户消息，bot 消息取不到）
- #118：用户在不支持 history 的群里 `/撤回 5`，期望撤回最近 5 条（含 bot） ✗（同上）

如果按这个清单检查，major bug 应该能在审查阶段第一时间发现。

### 6. 评分校准的反思

本次 4/10 + request_changes 决策准确。但可以更进一步：
- 若把"影响所有未启用 auto_recall 的群组"作为评分依据，可降到 3/10
- 若考虑 README 未同步、maxlen 缺口、注释不一致等叠加问题，作为综合评分 4/10 是合理的
