# Issue #143 深度反思

## 一、分类与优先级准确性

**分类 `enhancement` (0.95) 准确**。需求是新增能力（踢人时清除记录 + 新增命令），无运行时报错或现存 bug，属于典型的功能扩展。

**优先级 `medium` 判断合理但论据需加强**。分析中给出的 4 条决策路径（横切踢人链路、owner-driven + 标准化模式、工作量可控、有降级方案）是正确的。但遗漏了一个**红旗信号**：

> 「踢人」 + 「清除记录」是组合破坏性操作，必须评估**恶意误用风险**——管理员踢人可能本身就有争议（"踢错了能不能恢复"），叠加"清除记录"则不可逆（一旦撤回，时间窗过后服务端也无法恢复）。这与 #140 的"恶意互刷防护"是同类风险。

建议在优先级章节显式追加第 5 条决策路径：`⑤ 破坏性不可逆操作（清除他人聊天记录）→ 维持 medium 且 needs-discussion 上调至 0.85+`。

**未触发"owner-driven 纯减法降 low"模板**——正确，因为这不是纯减法。

**置信度偏高**：

- `recall` (0.85) 合理但偏低，分支 B/C 涉及服务端撤回，应到 0.90。
- `onebot` (0.65) 偏低，分支 B/C 强依赖 delete_msg 与跨适配器兼容性，应到 0.70-0.78。

**`needs-info` 缺失**：虽然 owner-driven，但**外部仓库的具体接口、许可证、依赖**未提供，应给 `needs-info` (0.50-0.60)。

## 三、可行性判断质量

**A/B/C 三档评估整体扎实**，特别是：
- ✅ 时间窗 2 分钟限制识别准确（§4.3/§4.11 沉淀）
- ✅ bot 自身消息处理（is_bot=True）作为关键决策点
- ✅ `_kick_member` 失败兜底识别（避免误删"已自动退出又被踢失败"的用户本地记录）
- ✅ `message_history` 进程级缓存重启不可逆的文档化要求

**遗漏的关键检查项**：

1. **跨适配器兼容性矩阵未明示**（#135/#136/#140 沉淀强制要求）。三条适配器（NapCat/Lagrange/go-cqhttp）的 delete_msg 成功率应该像禁言字段差异矩阵一样**列表展示**。

2. **A/B/C 之外缺 D（分阶段）分支**——#139 硬约束要求"删除+新增对称命令"以外的复合改动也应考虑分阶段。此处"分支 B 后再上 C" 是天然分阶段，但未显式标记 D。

3. **`_record_mute_and_maybe_kick` (L870) 是否同步接入**：分析中提到但未明确风险。该路径是**自动踢人**（非用户命令触发），如果接入则需要考虑"自动踢人是否也触发清除"——这又是一个 `needs-discussion` 决策点。

4. **合规与隐私风险未评估**：清除某人聊天记录涉及群聊数据删除，需考虑是否被滥用于"清理某人存在痕迹"。这是数据合规层面的红旗，主流平台（微信、Telegram）的 Bot API 通常**不允许**运营方清空他人消息。

5. **外部仓库 API 差异未前置必查**——分支 C 的 3 项前置检查合理，但应明确"评估前不允许合并分支 C 代码"作为流程约束。

**工作量估算**：
- 分支 A：0.5-1 天 → 偏乐观；缺少命令注册/帮助/CHANGELOG 七处同步，建议 1-1.5 天。
- 分支 B：1.5-2.5 天合理。
- 分支 C：3-5 天合理。

## 五、标题改写适当性

**建议标题**：`[enhancement][medium] 踢人时自动清除该用户聊天记录（可配置+按群覆盖+指令触发）`

**评价**：
- ✅ 比原标题"。"清晰百倍，原标题无意义必须改写
- ✅ 保留核心：踢人 + 清除 + 按群 + 指令
- ⚠️ 略显冗长，可压缩为 `[enhancement][medium] 踢人时自动清除/撤回该用户聊天记录（可配置+按群覆盖+独立命令）`

**关于"撤回"措辞**：原 Issue 用了"清除"，建议标题用了"清除"。但分支 B/C 实际涉及服务端 `delete_msg` 撤回。两者语义不同：
- 仅清本地：标题应写"清除"
- 服务端撤回：标题应写"撤回"

**建议标题应明确语义**：`[enhancement][medium] 踢人时清除/撤回该用户聊天记录（本地+服务端可配置 · 按群覆盖 · 独立指令）`

## 六、经验教训

### 沉淀要点

1. **"owner + 清除数据"红旗**（仓库第 5 类敏感性模式，建议沉淀）：当维护者本人发起"清除/删除他人数据"类需求时，必须显式评估滥用风险、合规风险、不可逆性。建议作为新模板章节沉淀。

2. **`message_history` 本地缓存应用层沉淀**：PR #123 引入的本地缓存至今已应用于自动撤回、踢人清除等多个场景，应在 README/帮助中**统一明示**"本地缓存仅进程内有效，重启丢失；服务端撤回受 2 分钟时间窗限制"。建议沉淀为新的"本地缓存应用通用提示"模板。

3. **外部仓库参考类 Issue 分析前置检查清单**（扩展现有"合入外部仓库类"模板）：
   - 外部仓库许可证兼容性
   - 依赖兼容性（aiohttp/httpx/websocket-client 版本）
   - OneBot 标准 API vs 私有扩展 API 使用清单
   - 维护责任归属（fork vs 复制代码 vs 引入依赖）
   - 配置 schema 扩展冲突

4. **分支 C + 跨适配器 delete_msg 矩阵**必须前置建立，类比 #135/#136 的禁言字段差异矩阵。建议建立 "OneBot delete_msg 跨适配器兼容性表"（NapCat / Lagrange / go-cqhttp × 时间窗内 / 时间窗外 / 批量 / 单条）。

5. **`_record_mute_and_maybe_kick` 自动踢人路径** 在多个 Issue 中被反复触及（L870），建议作为**踢人链路统一接入点**专门审查。

### 仓库特有模式补充

- **"参考 zcj-ui 仓库"是信号**：zgj-ui/astrbot_plugin_group_guardian 已被多次参考（也可能成为后续 issue 的参考源），值得建立一份"外部参考仓库清单"维护其许可证、活跃度、API 兼容性。
