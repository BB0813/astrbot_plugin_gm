## 七、经验教训

### 1. 项目记忆 → 模板化输出的强制路径

本次最大教训：**项目记忆中存在标准模板时，所有字段必须按模板填充，不得因校验失败整体降级**。这本质上是"模板覆盖率"问题——

> 反思机制应该检查"是否有现成模板"作为第一优先级，超过"字段是否校验通过"

### 2. 校验失败短路器的固化优先级

应在反思系统中加硬约束（不仅是软建议）：

```
IF 存在适用模板 THEN
    按模板填充所有字段（即使校验失败也要按模板填充，仅在字段格式层修复）
ELSE
    走常规分析路径
END
```

### 3. #134 第四次触发校验失败的根因分析

四次失败（#131/#132/#133/#134）的共同特征：
- 都是项目记忆中有完整模板的 Issue
- 都是结构化输出字段较多（标签/标题/可行性/分支判定）
- 都在 LLM 输出长内容时因某个字段校验失败而触发"全局降级"防御

**根因**：反思提示词中的"校验失败 → 降级"信号过强，盖过了"按模板填充"的指令。

### 4. 仓库"装饰字符 QQ"模式已形成高频模式

模板已标注"已第四次触发校验失败短路"——这意味着：
- 该模式应升格为"独立 Issue 类型"在 README/CONTRIBUTING 中说明
- 仓库应在 `_extract_at_qq` 顶层**主动**加 `unicodedata.normalize('NFKC', s)` 防御
- 即使本次 Issue 不修复，仓库也应主动发起修复 PR

### 5. 反思自身的元教训

本次反思暴露的更深问题：**反思机制本身未将项目记忆中的模板视为"硬约束"**。未来应在反思系统增加：

```
Pre-check 规则（在任何输出前）：
- 是否存在适用模板？→ 是 → 按模板输出，不允许降级
- 字段校验失败 → 仅局部修复，不影响实质性判断
- 模板未覆盖 → 走常规分析路径
```

### 6. 具体到本仓库的未来工作流建议

应在 `main.py` 的 `_extract_at_qq` 函数顶部加防御性代码（即使 Issue 不修）：

```python
import unicodedata
import re

_QQ_PATTERN = re.compile(r'^\d{5,12}$')

def _extract_at_qq(s: str) -> Optional[str]:
    s = unicodedata.normalize('NFKC', s).strip()
    if not _QQ_PATTERN.match(s):
        return None
    return s
```

这一改动的成本是 3 行代码，但能防御**整个装饰字符 QQ 攻击面**，应在下次维护窗口主动合并。
