- 可行性：`无法评估` ❌

### 应有判断

**分类应为 `enhancement`（或 `feature`）**，证据链：

1. **权限模型重构**：将插件内"插件管理员"机制替换为"复用 QQ 原生群管理身份"——这是典型的**权限模型调整**。

3. 项目记忆明确指出：*"权限/配置粒度调整（按群独立配置头衔/管理/踢人/禁言）应归为 `enhancement`，不是 `other`；辅助 `configuration`、`permission`、`group-management`、`needs-discussion`，移除旧机制需评估 `breaking-change`。"*

**优先级应为 `medium`**：
- 影响范围：所有依赖 `plugin_admins` 鉴权的命令（头衔/踢人/禁言/管理类）都会被影响，但功能不会消失（只是判定依据换了）。

- `low` 偏低：横切关注点（移除现有配置项属于 breaking change），用户可见行为变更。

### 关键遗漏：`breaking-change` 维度

"取消所有插件管理员设置"**显式删除了既有配置项**，按项目记忆：

> **删除既有命令用法是 breaking-change**：用户可见行为变更，必须显式标签标注，不能仅在描述中提及。

即使配置项不是命令，也是用户可见的契约删除，应标 `breaking-change`。

## 七、经验教训（关键反思点）

### 教训 1：校验失败触发的"整体降级"是最严重反模式

本次分析的最大错误是把工具链的字段校验错误误读为"信息不足"，进而把所有实质性判断都退化为空。这是**绝对禁止**的行为——校验失败应**局部修复**而非**整体降级**。下次遇到 `expected <REASON>` 类错误时，必须**保留所有可判断信息**，仅修改字段输出格式。

### 教训 2：权限模型调整类 Issue 有强信号模式

本仓库至少已识别三类权限配置项：
- `plugin_admins`（全局插件管理员）—— #130 本次要废弃
- `title_admins`（头衔管理员）
- `kick_admins` / `group_admin_admins`（踢人/管理群管）

**新增仓库记忆建议**：权限配置项重构类 Issue 应触发"全配置项扫描清单"——分析 #130 时应主动检查 `title_admins` 等同类配置项是否需要同步处理，避免"今天改一个、下周再改一个"的零散迁移。

### 教训 3：基于 sender 角色鉴权 vs 基于配置项鉴权——本质差异

- **基于配置项**（`plugin_admins`）：静态、可由非群管的运维人员预设、不依赖事件元数据。
- **基于 sender 角色**（群管/群主）：动态、自动同步 QQ 原生权限、依赖事件元数据完整。

改造时必须显式回答：
1. 私聊场景如何处理（无 group_id）？
2. 匿名消息如何处理（sender.role 不准确）？
3. bot 自身角色如何降级？
4. `get_group_member_info` 调用频度（每次都查还是缓存）？

### 教训 4：删除配置项必须配"迁移指南"

仅删除 `plugin_admins` 配置项而不告诉用户如何迁移，等同于制造静默破坏。建议在 CHANGELOG 中明确：
- 该配置项从哪个版本移除
- 用户应当清理本地配置（避免 schema 校验失败）
- 是否有兼容期（先警告后移除）

### 教训 5：新增仓库级标签建议

- **`bot-role`** / **`sender-role`**：基于 sender 在群内角色的鉴权机制，应建立此模块标签。
- **`permission-model`**：权限模型重构的专用标签，区别于单点 `permission`。
- **`deprecation`**：废弃配置项/命令用法的专用标签。
