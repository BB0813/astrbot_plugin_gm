## 6. 经验教训

### A. async generator 中 `return <值>` 的陷阱

- Python 语法明确规定：`return <expr>` 在 `async def` + 含有 `yield` 的函数中是 `SyntaxError`，无任何运行时警告。
- 这是“写代码时 IDE 不会报红、运行时直接 SyntaxError”的典型陷阱，**必须在 PR 审查阶段拦截**。
- 建议在 `.sakura/memory` 或仓库 CONTRIBUTING 中加入 lint 规则：检测 `async def` 函数体内同时出现 `yield` 与 `return [^N]`。

### B. 装饰器函数形态决策流程

记忆中没有专门条目，建议新增：

> **AstrBot 装饰器函数形态判断流程**：
> 1. 查看装饰器文档/源码，确认期望的函数类型（`async def` vs async generator）。
> 2. 同文件中查找同类装饰器包裹的函数，统一形态。
> 3. 若装饰器是 `@filter.command` / `@filter.permission_type` / `@perm.require_*`，**默认是普通 `async def`**。
> 4. 若装饰器是 `@event_message_type` / `@event_message` 等需要逐步 yield 事件流的，**默认是 async generator**。
> 5. 混用 `yield` + `return <值>` 必然 SyntaxError，必须二选一。

### C. 阻断式缺陷的影响面验证

- 看到“所有其他插件也无法加载”这类结论，必须回到 `star_manager` 源码确认是否真的会连带影响，不能从单条 ERROR 日志直接外推。
- 在 Issue 回复中应明确区分“已确认的影响”和“疑似的影响”。

### D. 全局搜索同类模式的 SOP

针对此类“单点错误暗示同类风险”的 Issue，应在可行性中固定包含：

1. 正则 `async def [^\n]*:\n(?:[^d]|d(?!ef))*yield` 粗筛含 yield 的 async 函数。

3. 列出所有疑似文件与行号，作为“建议同时修复”的附录。
