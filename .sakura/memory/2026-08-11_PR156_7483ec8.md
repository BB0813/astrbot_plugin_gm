## 二、发现的模式

### 2.1 代码模式

| 模式 | 观察 |
|------|------|
| **缓存结构** | 统一使用`deque(maxlen=N)`，由常量控制容量 |
| **命令注册** | `_GM_COMMAND_NAMES`元组 + handler函数双注册 |
| **配置分离** | schema与config分离，schema定义约束，config存储用户值 |
| **权限模型** | 三层架构：`_is_authorized()` → 各类admin检查函数 |
| **类型注解** | 混合风格——定义处用`Dict[str, deque]`，部分处用类名（本次问题） |

### 2.2 架构观察

```
_handle_dm_message
    │
    ├─ 参数解析 (message_id, message_seq, group_id, user_id)
    │
    ├─ 缓存写入 ← 审查关注点：时序问题
    │
    ├─ enabled检查 (if not enabled: return) ← 早退点
    │
    └─ 业务逻辑 (撤回操作)
```

**当前架构问题**：缓存写入与业务逻辑耦合，未采用"记录层→业务层→响应层"的清晰分层。

## 三、规范完善建议

### 3.1 新增审查规则

**规则N：PR描述完整性校验**
```
□ 审查摘要中的变更点 ≥ PR描述中的变更点
□ 新增功能/配置/命令必须在PR描述中明确列出
□ 缺失项应标记为"描述缺失"而非默认"无此项"
```

**规则O：缓存安全性检查**
```
□ 新增本地缓存是否定义容量上限？
□ 是否有TTL机制或显式清理函数？
□ 是否存在内存泄漏风险？
```

**规则P：功能设计意图确认**
```
□ 配置项enabled=false时的预期行为是什么？
□ "不执行" vs "执行但不提供UI" 必须明确区分
□ 审查建议需基于确认的设计意图，而非通用原则
```

### 3.2 现有规则优化

**§2.3 "本地缓存回退骨架"需修订**：
```
当前：
"bot 消息写入必须独立于业务早退链（置于 if not enabled: return 之前）"

建议改为：
"缓存写入的位置取决于功能设计意图：
 - 若'记录'独立于'功能开关' → 置于 enabled 检查之前
 - 若'记录'是'功能'的一部分 → 置于 enabled 检查之后
 审查者需先确认设计意图再提出建议"
```

## 四、经验教训

### 4.1 关键洞察

**1. PR描述≠代码变更**
审查摘要与PR描述出现严重不一致时，应：
- 在审查报告中明确标注"PR描述未涵盖以下变更"
- 暂定"全部变更"为审查范围边界
- 要求PR作者补充描述或解释

**2. "消息不丢失"是假设而非事实**
并非所有功能都需要"记录先行"：
- `dm_history_recall=false`可能是设计意图：用户不想被记录
- 建议需基于功能设计，而非通用安全原则

**3. 类型注解是代码契约**
```
# 定义处
private_message_history: DMHistoryManager = {}  # 类名？运行时是dict

# 使用处
private_message_history: Dict[str, deque] = {}
```
类型不一致暴露了代码演进中的历史痕迹，应在审查中统一要求。

### 4.2 未来审查关注点

| 场景 | 关注点 |
|------|--------|
| 新增缓存结构 | 容量上限、清理机制、内存风险 |
| 启用/禁用开关 | 功能设计意图、记录是否独立于开关 |
| PR描述与代码差异 | 标注不一致，要求澄清 |
| OneBot协议相关 | message_id vs message_seq 语义区分 |
| 类型注解 | 定义处与使用处一致性 |
