## 6. 经验教训

### 必须固化的反思要点

1. **"删除 + 新增"复合诉求 Issue 应强制拆分建议**：维护者合并两条独立诉求时，分析必须显式建议拆分为两个独立 Issue 跟踪，除非有强约束必须合并实施。两条诉求的工作量、风险、决策点完全不同，混合 PR 会导致审查困难。

2. **breaking-change 置信度必须按子诉求分别评估**：删除部分 0.95，新增部分 ≤0.30，不能给出统一置信度。这是对"对称命令扩展"类 Issue 的强制要求。

3. **deprecation 标签必须必给**：删除既有命令/配置项时，#130/#132 模板已固化 `deprecation` ≥0.75 是硬约束，本次遗漏。

4. **行号引用必须前置声明可溯源状态**：精确行号若无"已读取 main.py 验证"，应在可行性章节开头声明"基于项目记忆与既有 PR 模式推断"。

5. **重复检测措辞强制模板**：禁用"未检测到重复"/"无重复"/"可能是#X的重复"。无历史列表时**写"暂未发现"并列出建议检索关键词**。本次反思第 4 次触发此反模式，必须升级为反思 checklist 的硬门槛。

6. **必给标签逐项核对硬约束**：分析涉及"群待办 / 引用消息触发型命令"时，第一步必须对照 #131 模板的"必给标签清单"逐项勾选。本次遗漏 `reply`/`quote-message`、`onebot-extension`、`permission-model`、`deprecation`。

7. **owner-driven ≠ 单一诉求**：本次 Issue 是 owner-driven 复合诉求，证明了"维护者本人提交不等于简单线性实现"的反模式（#135 已沉淀）。即使 owner-driven 也需在优先级章节显式说明"两条诉求相互独立，建议拆分"。

### 仓库特有模式建议

**"对称命令扩展"类 Issue 应建立专用模板**（基于本 Issue + #131 沉淀）：
- 触发场景：add/remove、enable/disable、set/unset、start/stop、bind/unbind 等对称命令
- 必查项：① 对称性（参数、权限、回执是否对称）② 共享 helper 抽取机会 ③ 一方已实现时另一方的依赖反转 ④ 权限语义可能不同（添加通常宽于撤销）⑤ 跨适配器 API 矩阵
- 标签基线：`enhancement`(0.95) + `command`(0.95) + `group-management`(0.85-0.92) + `onebot`(0.55-0.70) + `compatibility`/`onebot-extension`(0.75-0.85) + `permission-model`(0.70) + `configuration`(0.65-0.75) + `needs-discussion`(0.75-0.85) + `breaking-change`(0.85+ 若删除方)

**写类对称命令权限不对称风险**：添加群待办可能允许群管，撤销群待办通常需群主。分析时必须显式对比"添加侧权限 vs 撤销侧权限"，与 #136 沉淀的"误解禁 vs 误禁言风险对比"对等。

**七处同步清单对"删除既有命令"特别适用**：删除操作需要清理的扩散点比新增更多（README/帮助/CHANGELOG/metadata/schema/元组注册/公告），建议在可行性章节强制列七处而不是五处。
