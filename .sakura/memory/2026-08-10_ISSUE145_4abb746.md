## 1. 分类与优先级准确性

**分类（enhancement）**：✅ 准确。新增"踢人后清历史"功能属于功能增强，非 bug 修复。

**优先级（medium）**：⚠️ **需重新审视**。

按 #142 升级后的决策路径 5 条逐项核对：
- ①横切权限 + breaking-change：本功能为动作联动型，**owner-driven 触发机制** + **新增配置项**（全局开关 + 按群覆盖），符合"新增配置"档 → breaking-change 0.55-0.65

- ⑤**默认值决策**：**需明确默认值**——若默认 `false`（用户需主动启用）→ 维持 medium；**若默认 `true`**（开启后所有群自动清历史）→ 升 high（隐私风险）

## 6. 经验教训

### 6.1 本 Issue 特定教训

1. **动作联动型 Issue 的默认值决策点是优先级关键**：必须显式列出"默认 false vs 默认 true"对优先级的影响，不能跳过
2. **重复检测前置过滤严格执行**：主分类不同（权限 vs 功能联动）应上限 0.3，不能仅因"都是 enhancement"就高估重复
3. **撤回/清历史类 Issue 的硬约束清单**：撤回时限、通知风暴、去重视、回执一致性必须**逐项在分支细化中显式列出**，不能合并为"含速率限制"一笔带过

### 6.2 跨 Issue 经验

1. **#142/#143/#145 三者关系需建立索引**：
   - #142：动作 A → 动作 B（A=踢人, B=撤回）——**撤回方向**
   - #143：动作 A → 动作 B（A=踢人, B=清历史）——**清历史方向**
   - #145：与 #143 几乎一致 —— **建议合并**
   
   未来分析类似 Issue 时，应在项目记忆中建立"动作联动型 Issue 索引表"，按"触发动作 + 目标动作"二维分类。

2. **owner-driven Issue 的双校准对冲**：`needs-info` ≤0.30 + `needs-discussion` ≥0.75-0.80 应作为 owner-driven Issue 的标准标签组合。

3. **外部仓库参考 vs 合入的判断时机**：本 Issue 提到"按照这个仓库的代码实现"，**但未明确是参考借鉴还是真合入**。按 #143 硬约束，必须先访问外部仓库验证实现路径，然后判断：

   - 若真合入 → `merge-request`+`external-repo`(0.90) + `license-check`
   - **不可混用**

### 6.3 仓库特有模式建议

1. **"动作联动型"已成为第 5 种高频模式**（#142/#143/#145），应在项目记忆中正式固化模板，包括：
