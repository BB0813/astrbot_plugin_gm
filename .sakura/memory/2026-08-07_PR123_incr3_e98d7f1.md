## 2. 发现的模式

### 代码模式
1. **缓存回退的统一抽象**：本仓库开始形成"主路径 → 辅助回退"的模式（本地缓存 → 历史接口 → 报错）。这是值得记录的项目级模式，未来类似兼容性问题可复用此骨架（写记录入口 + 读取回退 + 标识来源）。
2. **`setdefault(str(group_id), deque(maxlen=100))`** 是比 `defaultdict(lambda: deque(...))` 更稳健的工厂模式选择，避免了 `__contains__` 等检查意外触发工厂。值得在项目记忆中**正向推广**。
3. **严格判空优于 falsy 判空**：本 PR 的 `_clear_group_title` 修复（`title is None or title == ""`）和审查建议的 `message_id is None or user_id is None` 形成了一致的"严格判空"风格。这是项目应沉淀的反模式之一。

### 架构观察
1. **`after_message_sent` 钩子的使用是新的依赖面**：之前 main.py 大概率没有用 bot 自身消息钩子，本次新增意味着插件对 AstrBot 事件生命周期的依赖加深。后续若 AstrBot 升级导致 `after_message_sent` 签名变化，缓存写入会静默失效。
2. **按群隔离的内存缓存结构**：`{str(group_id): deque[dict]}` 是合理的最小化设计（仅存 message_id + user_id），符合 §4.3 关于隐私边界与重启不可恢复的考量。
3. **配置与命令描述未同步**：本地缓存回退是新的运行机制，但 `_conf_schema.json` 未新增开关（如 `recall_local_cache_enabled`），README 未更新。这是一个**架构层面的不完整**——机制上线但配置面缺位。

## 3. 规范完善建议

### 新增项目记忆条目建议

**§4.6 本地缓存回退模式（新增）**：
- "主路径失败 → 本地缓存回退"是处理 OneBot 接口兼容性问题的推荐骨架。
- 缓存设计要点：① 按群隔离 ② 最小化存储（仅 message_id + user_id）③ 显式上限（deque maxlen）④ 写入入口对称（用户消息走 on_group_message，bot 消息走 after_message_sent）⑤ 回退标识（"（来自本地缓存）"）⑥ 文档明示重启不可恢复。
- 工厂函数选择：`{}` + `setdefault(key, factory())` 优于 `defaultdict(factory)`，避免 `in` 检查、序列化、`copy` 等操作意外触发工厂。

**§4.7 严格判空 vs falsy 判空（新增）**：
- 对外暴露的 helper 函数优先用 `x is None` / `x == ""` 严格判空，避免误丢合法值（0、空集合等）。
- 内部业务 helper（如 OneBot 回调）若确认业务值不会为 0，可用 falsy 过滤但需在 docstring 注明。

**§3.2 增量（关于 #119）**：
- 头衔清空必须严格区分 `""`、`" "`、`None`、字段缺失；`strip()` 会把单空格误判为空，是已知反模式。

### 修改建议
- §2 增加"本地缓存撤回的隐私边界"条目（仅存元数据不存内容）
- §4.3 增加"机制上线必须同步 README + 配置 schema + 帮助文本"的硬性要求

## 4. 经验教训

### 增量审查的核心风险
**本次审查的最大盲区正是增量审查的结构性弱点**：
- 只看了 73 行 diff，未验证 `self.recent_messages` 在 `__init__` 中的初始化是否与 `{}` 替换兼容
- 未验证 `after_message_sent` 钩子是否已正确注册（@filter.on_event 装饰器是否齐全）
- 未验证缓存读取逻辑（`_get_recent_messages_for_recall`）与新数据结构（`dict[str, message_id, user_id]`）是否真的兼容

**教训**：增量审查应至少包含一轮**"对接面扫描"**——快速浏览本次 diff 之外的相关函数（__init__、注册装饰器、其他调用点），验证修改未破坏既有假设。本次评分 9/10，但严格说应降至 8.5/10，因为缺少对接面验证。

### `defaultdict` vs `{} + setdefault` 的选择
这是一个**易被忽视的微陷阱**。`defaultdict(lambda: deque(maxlen=100))` 的工厂副作用在以下场景会暴露：
- `key in d` 检查时不会触发，但 `dict(d)`、`copy.copy(d)`、`json.dumps` 等操作会触发工厂创建新 key
- 测试或调试时遍历会创建大量空 deque，污染内存

本次修复**主动消除了这个隐患**，且审查**准确识别了它**，是值得记录的正面案例。
