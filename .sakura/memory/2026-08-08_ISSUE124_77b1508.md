# Issue #124 深度反思

## 1. 分类与优先级准确性

**分类准确**：`enhancement` 正确。Issue 描述的是命令默认行为与默认路由的体验优化，并非 bug（没有"运行报错"或"行为错误"），也非 feature request（已存在完整功能，仅调整默认行为）。与项目记忆 §1 "调整默认行为/边界体验" 的判定契合。

**优先级判断合理**：`medium` 合适。理由：
- 不阻断插件运行（已有替代路径：无参场景可用 `/撤回 1`，`@用户 + 单数字` 场景可用 `/撤回 @用户 1 N` 类似多数字形式）
- 影响常用核心命令的默认交互体验，符合项目记忆 §1 中"核心命令局部不可用"→`medium` 的判定
- 虽非 high（无"启动失败/越权/误撤大量消息"等高危场景），但确实改变用户已习惯的默认语义，存在用户认知摩擦

**潜在不足**：分析中提到"对齐 `astrbot_plugin_batchrecall` 行为"——若该外部仓库属于 fork/参考实现，这种"对齐行为"本质是项目记忆 §6 涉及的"合入外部仓库/外部代码"模式，但本次仅是命令语义对齐并不涉及代码合入，影响不大。

## 6. 经验教训

### 6.1 仓库特定模式

**`astrbot_plugin_gm` 仓库的"撤回命令"已成为核心模块**，从多次反思（#117/#118/#123）和 #124 来看：
- 撤回相关 issue 集中在 `recall_cmd` 的分支逻辑、参数解析、本地缓存回退
- 后续若出现 `/撤回` 相关 issue，应预设属于 `recall_cmd` (~1984-2172 行) 家族
- 强烈建议为 `recall_cmd` 维护一张"分支路由表"作为项目记忆，列出每个分支的进入条件与功能

### 6.2 "默认行为变更"分析范式

针对此类 issue，应固化以下分析模板：
1. **现状描述**：每个分支当前的判定条件与默认行为
2. **目标行为**：期望的判定逻辑与默认行为
3. **兼容性影响**：是否存在老用户已习惯的行为被破坏
4. **替代方案**：保留旧行为的语法设计（如显式前缀、命令迁移、双数字语义）
5. **边界场景**：单数字 `0`、负数、超大值、空历史、单条历史
6. **文档/schema 同步清单**：README、帮助命令、配置 schema、用法提示

### 6.3 重复检测的"降级原则"

当无法直接确认两个 issue 是否重复时，应采用项目记忆 §7 的降级策略：
- "暂未发现" + 建议检索关键词
- "关联" 而非 "重复"（除非用户故事链完全一致）
- 避免直接下"可能是 X 的重复"这种模棱结论，除非有明确证据

### 6.4 单数字/默认值的歧义风险

这是一个跨 PR/Issue 的长期模式：
- `count=0`、`count=1`、单数字在多人/多编号场景下的歧义
- 建议在 `recall_cmd` 文档中固化"单数字默认路由"决策，并形成"两条腿走路"原则：
  - 路线 A：单数字默认按编号（更符合"指定"语义），但需提供明确的按数量语法（如 `/撤回 last N`）
  - 路线 B：单数字默认按数量（保留旧行为），但需提供明确的按编号语法（如 `/撤回 @用户 #N`）
- 这一决策应在仓库维度的项目记忆中记录，避免后续 issue 反复讨论

### 6.5 工作量估算校准

针对本仓库 "撤回 + 文档/schema + 测试" 类型的 issue：
- 纯分支调整：0.5 天
- + 测试覆盖（8+ 用例）：+0.5 天
- + README/help/schema 同步：+0.5 天
- + 兼容性决策讨论与双语法设计：+0.5 天
- **合计 1.5-2.5 天** 较为合理，原分析 0.5-1.5 天偏乐观

### 6.6 引用与历史 PR 的关联

本次分析正确引用了 PR #123（本地缓存回退骨架）和 #122/#118，但可以更明确指出：
- #124 的实现**依赖** PR #123 已合入（若未合入则本次改动需先完成 #123）
- 暗示这类 issue 应有隐含的前置依赖检查流程
