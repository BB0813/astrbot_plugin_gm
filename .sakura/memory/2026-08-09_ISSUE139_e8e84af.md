# Issue #139 分析反思

## 1. 分类与优先级准确性

**分类准确**：`enhancement` 是正确的主分类，因为 Issue 同时包含"功能裁剪"和"功能新增"两种性质，但都属于"主动修改既有命令集/扩展命令集"范畴。不过更精确的描述应该是"接口收敛 + 新接口引入的混合增强"，这个语义在分析摘要中已点明。

**优先级 medium 的判定值得推敲**：

- 项目记忆明确指出："维护者本人纯减法性质的功能裁剪 → low 组合（主动减法+owner 自实施+无横切关注点）"
- 本 Issue 同时包含减法（删 `/删群公告`）和加法（增 `/取消群待办`），不能直接套用"纯减法 → low"
- 加法部分涉及 OneBot 扩展 API（群待办非 v11 标准）、跨适配器兼容性（NapCat/Lagrange/go-cqhttp 支持矩阵差异）、权限差异（群主专属 vs 群管可执行），属于典型的横切关注点
- 因此 medium 是合理的，但**优先级决策路径没有显式列出**，违背了 #133 沉淀的硬约束（"4 条判定路径显式列出"）

**应当显式列出的判定路径**：
1. 双向改动（删+增）非纯减法 → 不能降 low
2. 涉及 OneBot 扩展 API（群待办）→ 跨适配器风险 → 维持 medium
3. owner-driven 主动实施 + 改法明确 → 不升 high
4. 与 #131 强耦合（依赖 `/添加群待办` 提供待办对象）→ 需联动讨论，维持 medium

## 2. 标签推荐质量

**整体贴切**，但有几处可以优化：

**置信度偏低的标签应当重新审视**：

- `documentation` 0.65：删除 + 新增命令必然涉及 README、CHANGELOG、帮助命令、docstring 四处文档同步，0.65 偏保守，可上调至 0.75
- `onebot` 0.7：考虑到群待办 API 跨 OneBot 实现差异巨大，建议上调至 0.80

**应当补充的标签**：

- `breaking-change` 0.92 是合适的，但还可以加 `deprecation`（0.75+，标记 `/删群公告` 废弃/移除）
- 应当加 `permission-model`（0.65，群待办权限边界与设精/群管不同）或更细的 `bot-role`（0.70）
- 应当加 `reply`/`quote-message`（0.85+，撤销群待办需要引用消息），这与 #131 沉淀的标签建议一致

- 应当加 `changelog`（0.85，breaking-change 必须 CHANGELOG 标注）

**未对齐项目记忆模板的硬约束**：

项目记忆的"引用消息触发型命令 / OneBot 群待办类 Issue 标准模板（#131 案例）"明确给出了必给标签基线：

## 3. 可行性判断质量

**分支 A 和分支 B 的估算基本合理**，但有以下问题：

**过度乐观**：删除 `/删群公告` 不只是简单的"删除 30-50 行"。需要考虑的：

- 帮助命令的 yield 文本（命令列表、用法说明、示例）
- `_conf_schema.json` 中是否有 `notice_enabled` 之类的配置项需语义缩窄
- 是否有群组配置覆盖（`group_overrides` 中 `notice_enabled: false` 等）
- 是否有别名/中文/英文命令注册（`_GM_COMMAND_NAMES` 元组可能有多个变体）
- 是否有依赖该命令的下游代码（如审批工作流、广告拦截可能引用）
- CHANGELOG breaking-change 段落需要完整的迁移说明（已使用 `/删群公告` 的用户怎么办？提示用户用什么替代方案？）

**任务 2 的实现复杂度被低估**：

- 撤销群待办需要"找到原待办"，但 OneBot 群待办 API 通常没有"列出待办"接口。撤销流程需要 reply_id（原待办消息 ID），这意味着：
  - 撤销命令必须配对原待办消息使用
  - 用户体验差（"你必须先引用要撤销的那条群待办"）
  - 可能需要"列出当前群所有群待办"作为辅助命令
- 这与 #131 沉淀的"撤销类需要原 message_id"问题一致，但分析中没有显式展开

**应当显式讨论的设计决策**：

1. `/取消群待办` 的语义边界：是撤销任意一条群待办，还是撤销自己创建的最新一条？
2. 如果用户引用了非群待办消息，是报错还是静默忽略？
3. 如果原消息已撤回，撤销命令的行为（建议提示"请手动操作"）
4. 撤销操作的权限：群主专属 vs 群管可执行（与 #131 `/添加群待办` 必须保持对称）

**关键技术风险点未展开**：

- `_delete_group_todo` API 在不同适配器下的支持情况需要明确：
  - NapCat 是否提供 `_delete_group_todo`？
  - Lagrange 是否支持？
  - go-cqhttp 是否需要 HTTP API 插件扩展？
- 如果不支持，是否需要降级到"撤回原群待办消息"（但消息已发到群里就撤不回）

## 4. 重复检测准确性

**"可能是 #138 的重复"是禁用的措辞**，明确违反项目记忆中的反模式硬约束：

> "重复检测措辞强制模板：无历史列表时**写'暂未发现'并列出建议检索关键词**，"未检测到重复"/"无重复"/"可能是 #X 的重复"均被明令禁止。"

**且 #138 的具体内容没有验证就盲指**，这与 #136 沉淀的"#136 还有'可能是 #128 的重复'无依据盲指"是同款错误。

**正确的输出应当是**：

- 与"删减既有命令"类 Issue（#130/#132 权限模型重构中的命令删减）应做关联

## 6. 经验教训

### 6.1 模板对齐检查必须前置（再次强调 #136 沉淀）

本次分析再次触犯"项目记忆模板对齐检查"硬约束。**Issue 涉及 OneBot 群待办 API** 时，**第一步**必须对照"引用消息触发型命令 / OneBot 群待办类 Issue 标准模板（#131 案例）"逐项勾选必给标签和必查项。

### 6.2 删减+新增复合改动的新模板需求

本仓库首次出现"删除命令 + 新增命令"的复合改动（区别于纯减法如 #130/#132，或纯加法如 #131）。建议沉淀新模板：

**"命令集重构 / 双向复合改动"标准模板**：
- 删除路径精确到行号 + 帮助/README/docstring/schema/CHANGELOG 五处清理
- 新增路径复用既有三段式（API → 带下划线变体 → 降级提示）
- 用户迁移路径（已使用旧命令的用户如何告知）
- 替代方案（删除的命令引导用户用什么替代）
- 与同期 Issue 的依赖关系（删除依赖 / 新增被依赖）

### 6.3 跨 Issue 联动讨论的显式化

本次分析正确识别了"与 #131 强耦合"，但没有明确建议：
- 应当在 #139 中显式引用 #131（`Refs #131` 或 `Depends on #131`）
- 维护者应决定是合并到一个 PR 还是拆分为两个 PR
- 如果拆分，必须明确实施顺序（先 #131 再 #139，因为撤销依赖添加）

### 6.4 撤销类命令的额外复杂度

本次分析中"撤销群待办"被类比 `/取消设精`（同为 reply_id + 单 API），但群待办与设精有本质差异：

| 维度 | /设精 | /取消设精 | /添加群待办 | /取消群待办 |
|------|------|----------|------------|------------|
| API 标准性 | v11 标准 | v11 标准 | 扩展 API | 扩展 API |
| 跨适配器支持 | 全支持 | 全支持 | 差异大 | 差异更大 |
| reply_id 必要性 | 必须 | 必须 | 可选 | 必须 |
| 权限 | 群管即可 | 群管即可 | 群主专属 | 群主专属 |
| UI 异步刷新 | 无 | 无 | 有 | 有 |

**结论**：`/取消群待办` 的可行性远低于 `/取消设精`，不能简单复用设精模板。必须显式说明这是"扩展 API 撤销动作"的特殊模式，工作量估算应上调。

### 6.5 权限模型的细节对称要求

本 Issue 涉及两个权限边界：
- `/删群公告` 当前权限：`_is_group_admin_or_owner`（群管+群主）
- `/取消群待办` 建议权限：`_is_group_owner_only`（群主专属，与 #131 对称）

权限不一是合理的设计决策（QQ 原生行为：群待办只能群主撤销），但分析中没有显式说明这一权限提升的影响（原本群管可以删公告，现在还能撤销群主设置的群待办吗？不能，因为权限降级：群待办撤销仅群主）。

### 6.6 配置 schema 扩展的必要性

建议新增 `group_todo_enabled` 配置项（按群开关），但分析中没有讨论：
- 是否与既有的 `notice_enabled`、`essence_enabled` 等同类配置保持命名一致？
- 默认值策略：全局 enabled、按群 override 关闭为主（与 #131 沉淀一致）
- 是否需要 `group_todo_admin_qqs` 等超级管理员覆盖？

### 6.7 CHANGELOG breaking-change 标注格式

项目记忆反复强调 CHANGELOG 同步，但本次分析没有给出 CHANGELOG 条目格式建议。建议：

```markdown
## [Unreleased] - 2026-XX-XX

### Breaking Changes
- **删除命令**：`/删群公告` 命令已移除。原有功能可通过群管理面板手动删除公告，或等待公告自动过期。如有强需求请提 Issue 讨论替代方案。

### Added
- **新增命令**：`/取消群待办` 命令，引用要撤销的群待办消息即可。注意：本功能依赖 OneBot 适配器的扩展 API（NapCat 支持，Lagrange/go-cqhttp 支持情况请参考 README 兼容性表格）。
```

## 反思总结

本次分析**整体质量较高**（分类准确、工作量估算合理、技术细节丰富），但有以下**必须改进的红旗**：

1. **模板对齐检查遗漏**（违背 #136 硬约束）：未对照 #131 群待办模板逐项勾选，遗漏 `onebot-extension`、`reply`/`quote-message` 等关键标签
2. **优先级决策路径未显式列出**（违背 #133 硬约束）：4 条判定路径应当显式给出
3. **重复检测措辞违规**（违背反模式硬约束）："可能是 #138 的重复"是被明令禁止的措辞，且 #138 内容未验证
4. **撤销类复杂度被低估**：群待办与设精的本质差异（扩展 API + 群主专属 + UI 异步）未充分展开
5. **用户迁移路径未明确**：`/删群公告` 删除后用户怎么办，缺少替代方案提示

**建议下次遇到"删除 + 新增"复合改动时**，第一步调用新模板（命令集重构 / 双向复合改动），第二步对照相关子模板（#131 群待办 + #133 删减类 9 项反向清单）逐项勾选必查项和必给标签。
