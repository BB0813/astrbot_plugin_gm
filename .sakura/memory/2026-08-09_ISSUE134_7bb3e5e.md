## 1. 分类与优先级准确性

### 分类准确性
**`bug`（置信度 0.95）判定准确**。Issue 明确报告"`/解禁 @𝓒𝓪𝓷𝓬𝓮𝓻` 导致 bot 误对装饰字符命中的用户执行了解禁"，属于运行期命令行为错误，符合 bug 分类硬指标。

**细微改进空间**：摘要中"群管 API 可能取得第一条匹配即视为成功"的推测——若想保持 0.95 高置信度，应明确区分"已确认行为"与"推断行为"。从 Issue 原文看，"bot 解禁了 𝓒𝓪𝓷𝓬𝓮𝓻"已经是观察事实，无需推测"可能"——建议措辞收紧为"已观察到误解禁行为"。

### 优先级合理性
`medium` 判定**合理**，但需注意项目记忆中的**判定路径显式化**要求——本次分析未列出优先级决策路径，与 #133 沉淀的经验存在落差。建议补全：
- ① 核心解禁命令解析层错误 → 最低 medium
- ② 误解禁比误禁言影响更严重（用户被错误解除处罚） → 倾向升级
- ③ 单群单次影响，未扩散 → 不升 high
- ④ 修复路径明确（NFKC + 正则），兜底成本低 → 不升 high

### 影响范围遗漏
摘要提到"`/解禁`、`/禁言` 多 @ 场景"，但**未量化横切影响**：`_extract_at_qq` 若被 `/踢人`、`/设管`、`/取管`、`/头衔`、`/设群昵称` 等命令共享，则一处解析漏洞会同时污染多个高危命令。建议在优先级章节补充"横切面估算：~N 个 handler 受影响，其中 M 个属高危写操作（踢人/禁言/解禁）"。

## 6. 经验教训

### 值得在未来 Issue 分析中关注的要点

1. **横切解析层的 issue 必须量化影响面**：发现 `_extract_at_qq` 类共享函数漏洞时，必须主动 grep 所有调用点并列出影响命令清单。**这是 #134 模板的应有之意，本次未充分执行**。

2. **跨案例互引是高频模式**：#133（解禁 API 层）+ #134（解禁解析层）= 同一命令双 bug 面。未来解禁类 issue 应主动检查解析层和 API 层是否同时有问题，并在重复检测章节明示关联。

3. **重复检测的"硬约束"是反模式防御线**：项目记忆**三次明确**要求"无历史时写'暂未发现 + 建议检索关键词'，禁用'未检测到重复'"——本次违反，必须当作严重警告。**建议未来反思时把这一条作为强制 pre-check 项**。

4. **优先级决策路径必须显式**：项目记忆 #133/#134 沉淀的核心经验之一。本次未列出优先级决策路径，与既有标准存在落差。

5. **标签置信度应体现"已识别风险"权重**：本次 `onebot`/`compatibility` 给 0.55/0.5（下限），但跨适配器差异已经识别为明确风险面——置信度应反映识别深度而非仅有"提及度"。

### 装饰字符 QQ / 视觉欺骗型 Issue 分析经验（沉淀建议）

在 #134 既有模板基础上，**新增以下沉淀**：

- **横切面估算必备**：发现共享解析函数漏洞时，必须列出"受影响 handler 数 + 高危写操作 handler 数"两个量化指标
- **跨案例互引检测**：若解析层 bug 涉及 X 命令、API 层 bug 也涉及 X 命令，必须在重复检测章节明示"同命令双 bug 面，建议合并修复或互引"
- **标签置信度下限校准**：当某风险面（onebot/compatibility）已被明确识别时，置信度应 ≥ 0.65，而非 ≤ 0.55
- **测试矩阵时间单独拆分**：装饰字符 QQ 测试矩阵（3 适配器 × 3-5 字符风格）至少 0.5 天，必须从"主工作量"中独立列出
