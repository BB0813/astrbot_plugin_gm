# Issue #127 分析反思

## 1. 分类与优先级准确性

**分类**：标为 `enhancement` 是准确的——本质是"现有违规词 → 撤回/禁言链路的扩展，新增 STT 输入源"，符合"自动化审核能力新增"的增强定义。**未考虑 `bug` 维度**虽合理（原 Issue 是主动功能请求），但需注意：若现有违规词链路已声称支持"任意消息类型"，则"语音不触发"可能被视为既有能力缺口，分析中应显式说明本仓库**当前是否承诺覆盖语音**——若未承诺，纯属新功能；若 README/changelog 暗示覆盖，则需讨论是否属于 bug fix。

**优先级 `medium`**：判定合理，但理由应更扎实。当前支撑理由偏"实现复杂度"，而优先级判定的核心维度应是**影响面 × 阻断性 × 误触发风险**：
- 影响面：群管理插件，活跃群可能很多，语音滥用是真实场景；
- 阻断性：非阻断（现有违规词链路对纯文本仍生效）；
- 误触发风险：**高**（语音转写本身误识别 + 违规词模糊匹配 = 双重误判 → 误撤回/误禁言）。

**反思**：优先级 `medium` OK，但应在描述中显式标注**"误触发风险使优先级不低于 medium"** 这一关键理由，而非仅给工作量估算。

## 2. 标签推荐质量

**贴切度**：
- `enhancement` 0.95、`group-management` 0.9、`recall` 0.75 合理。
- `parser` 0.5 偏弱——本 Issue 解析对象是 STT 输出文本，与"命令参数 parser"无关，应替换为 **`stt`/`speech-to-text`/`voice`** 或 **`moderation`**（更贴合"自动化审核"语境）。当前仓库若无现成标签，应在描述中给出候选并注明需映射。
- `needs-info` 0.75、`needs-discussion` 0.6：根据记忆，**维护者本人发起的 issue 缺的是决策而非信息**，`needs-info` 应 ≤0.2，`needs-discussion` 应保持高权重（0.8+）。本 Issue 缺的是：
  - 决策类：STT 引擎选型（Whisper/云端/第三方）？是否允许用户自配？
  - 信息类：现有违规词链路是否已对"非文本消息"留有扩展点？
  
  应**显式区分两类缺失**。

**遗漏的标签**：
- **`moderation`**（自动化审核，本仓库应有类似标签或可映射）；
- **`configuration`**（必须扩展 schema）；
- **`privacy`** 或 **`compliance`**（语音 = 敏感生物特征，README 必告知）；
- **`breaking-change` 不适用**（无删减，纯增量）；
- **`help wanted` 0.35 偏高**：维护者本人提交 + 改法明确（"语音 + 违规词 + 撤回 + 禁言"链路清晰），`help wanted` 应 ≤0.1 或不推荐——除非显式寻求外部贡献 STT 引擎集成。

**与仓库标签体系一致性**：未明确仓库当前是否有 `stt`/`speech`/`moderation`/`automation` 等标签，分析中应**先列现有标签体系**，再给候选映射，避免凭空生成新标签名。

## 3. 可行性判断质量

**优点**：
- 五个维度拆解（STT 接入 / 违规词谱复用 / 撤回禁言动作 / 配置 schema / 风险边界）较完整；
- 显式列出环境依赖与适配器差异；
- 给出两档工作量估算（演示版 1-2 人天 / 生产版 1 人周+）；
- 提出"mock STT 先跑通链路"的渐进路径。

**不足**：

1. **未与代码库实际对接**：可行性分析停留在"概念层"，缺少对当前 main.py 现有违规词匹配、撤回、禁言函数的精确引用。记忆中有 `recall_cmd`、`_extract_at_qq` 等具体函数名，分析中应**指出哪些既有函数可直接复用、哪些需重构**，而不是笼统说"复用现有 delete_msg / set_group_ban 封装"。

2. **STT 引擎依赖评估片面**：仅列出"本地 Whisper / 云端 API / 第三方 SDK"三类，缺少：
   - AstrBot 框架自身是否已提供 STT 能力（如 `event.message` 是否含语音 segment 的转写接口）；
   - OneBot 端获取语音文件的标准路径（`get_record` / `get_file` / 消息 segment 中的 `file` 字段）；
   - 依赖体积（Whisper large-v3 约 3GB+，对部署环境的硬约束）。
   
   若框架已提供 STT，可行性可上调，工作量可下调。

3. **异步链路遗漏**：
   - STT 通常秒级耗时，主消息链路不能阻塞——分析提到"后台任务"，但未明确**长任务取消策略、超时控制、部分转写失败的处理**；
   - 跨事件边界：用户发完语音立即撤回群内其他消息，STT 还没转完怎么办？需不需要"先占位禁言，转写完再判定"？

4. **配置 schema 五处同步**未按记忆中的"五处同步清单"框架列出——根据项目记忆，**main.py 代码 + README + 帮助命令 + 配置 schema + CHANGELOG** 是仓库强制的同步清单，本 Issue 应按此清单列出，而非仅说"配置 schema 扩展"。

## 4. 重复检测准确性

**"可能是 #35 的重复"**：这是**高风险判断**——根据项目记忆强制模板：
- "可能是 #X 的重复"被明令禁止（#35 几乎不可能与本 Issue 同主题，除非 #35 也是"语音转文字 + 违规词"）；
- 无历史列表时应写**"暂未发现重复，建议检索关键词：语音、STT、speech、违规词、voice、whisper、撤回+语音"**；
- 必须给出"为何 #35 可能是重复"的依据，或降级为"暂未发现 + 检索词"。

**可能漏报的关联**：
- 若仓库曾有"撤回类功能请求"Issue 涉及语音消息处理，应主动检索；
- 若有"违规词支持更多消息类型"或"插件 STT 集成"的旧 Issue，应作为关联而非重复。

## 5. 标题改写适当性

**原标题**："功能增加"——信息量极低，几乎无价值。

**建议标题**："[enhancement][medium] 新增语音转文字 + 违规词命中自动撤回与禁言"——

**优点**：
- 明确标 `[enhancement][medium]`，符合仓库标题规范；
- 描述了核心链路：STT → 违规词 → 撤回 + 禁言。

**可改进**：
- 应包含**触发主体**（"语音消息"）和**关键风险**（如"误触发"），例如：
  `[enhancement][medium] 语音消息转文字命中违规词时自动撤回并禁言（需注意 STT 误识别风险）`
- 或更简洁：`[enhancement][medium] 语音消息违规词审核：STT + 自动撤回禁言`
- 当前标题把"STT"和"违规词命中"并列，但用户更关心的是**业务行为**（"语音违规自动撤回禁言"），技术实现细节（STT）可放入描述而非标题。

**过度改写评估**：未过度改写，原标题几乎无信息可保留，改写是必要的。

## 6. 经验教训

### 仓库特有模式

1. **"撤回/禁言 + 输入源扩展"是本仓库的典型扩展模式**：分析时必须显式考虑"新输入源如何接入既有违规词链路"——是否复用 matcher、是否需要 source tag、是否影响统计/日志。

2. **本仓库的"五处同步清单"（main.py + README + 帮助命令 + schema + CHANGELOG）应作为所有功能增强类 Issue 的强制输出框架**，本反思对应 Issue 未按此模板展开，是显著疏漏。

3. **本仓库的"权限粒度"经验**：语音违规词审核的禁言动作应复用既有禁言权限体系（`plugin_admins`、`group_overrides`、白名单），不应单独搞一套 STT 专属权限。

### 通用经验

1. **"STT + 内容审核"类 Issue 的标准可行性框架**：
   - 输入源获取（消息 segment / 缓存文件 / URL）
   - 转写引擎选型（依赖、体积、鉴权、错误率）
   - 异步处理（超时、取消、不阻塞主链路）
   - 结果接入既有审核链路（避免双份匹配逻辑）
   - 动作执行（撤回 / 禁言 / 复用既有 helper）
   - 配置 schema（引擎、密钥、白名单、阈值、群覆盖）
   - 风险边界（误识别、隐私合规、灰度、可观测性）
   - 五处同步（代码 + README + 帮助 + schema + CHANGELOG）

2. **`needs-info` vs `needs-discussion` 的精确使用**：
   - `needs-info`：缺关键事实（API 返回值、版本号、复现步骤）；
   - `needs-discussion`：决策待定（引擎选型、阈值、是否启用某特性）。
   - 维护者本人提交的 Issue 通常缺决策而非事实，应高权重 `needs-discussion`、低权重 `needs-info`。

3. **"误触发风险"作为优先级抬升的独立维度**：纯工作量大未必需要 medium，但**误触发会伤及无辜用户**（误禁言/误撤回）的功能必须至少 medium。本反思对应 Issue 应显式给出"误触发风险 → 优先级 ≥ medium"这一论证。

4. **重复检测的"检索关键词先行"原则**：在没有历史列表时，**先列检索词，再下结论**，避免误报 #35 这种几乎不可能重复的 Issue。

5. **隐私/合规是高敏感功能不可省略的维度**：语音 = 敏感生物特征 + 隐私内容，即使仓库整体风格偏务实，README 显著告知是底线要求，分析中应主动列出。

### 下次遇到同类 Issue 的标准动作清单

1. 检索 `stt`、`语音`、`voice`、`whisper`、`speech`、`违规词`、`moderation`；
2. 确认 AstrBot 框架是否已提供 STT 能力（影响工作量 ±50%）；
3. 列出 OneBot 端获取语音文件的标准路径；
4. 明确既有违规词链路的扩展点（是否需要 source tag）；
5. 按"五处同步清单"展开改动点；
6. 标注误触发风险与隐私合规要求；
7. 重复检测先列检索词再下结论；
8. `needs-info` ≤0.2、`needs-discussion` ≥0.8（决策缺失为主）。
