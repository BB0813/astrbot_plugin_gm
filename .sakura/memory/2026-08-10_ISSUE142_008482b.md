# Issue #142 分析反思

## 1. 分类与优先级准确性

**分类 `enhancement` 是正确的。** 这是维护者自提的功能新增诉求，将既有"踢人"和"撤回消息"两个能力组合为新工作流，不属于 bug 修复或纯粹重构。

**优先级 `medium` 合理但需补充决策路径显式化。** 按 #133 硬约束，优先级决策路径必须显式列出 4 条。当前分析直接给出 medium 但未展开推理，应补充类似：
- ① **影响范围**：涉及所有启用插件的群，但需要先 kick 成功才触发，不会误伤
- ② **横切关注点**：撤回类是仓库高敏感点（recall_cmd 高频改动），但有 `delete_msg` 既有 API 兜底
- ③ **owner-driven**：维护者本人提需求，方向已知，无需讨论是否要做
- ④ **隐私边界**：清空他人记录是中等敏感动作，但 kick 本身已需管理员权限

→ 这些因素综合定 medium。

**潜在质疑点**：是否应升至 `high`？撤回类命令一旦时序错乱（先撤回再 kick）可能导致撤回失败但用户已被踢的可观察副作用，影响中等但非阻断。建议维持 medium，与 §举报/通知路由 案例（#140）同级。

## 2. 标签推荐质量

**现有标签评估合理**，但有几处需要修正：

- ✅ `enhancement` 0.95 / `command` 0.9 / `group-management` 0.92：准确
- ✅ `recall` 0.88：核心能力之一，合适
- ⚠️ `message-history` 0.82：作为新建标签，置信度过高。这是个不常见标签，仓库历史无相关 Issue 沉淀。建议降到 0.65-0.75 或归入 `recall`。
- ⚠️ `needs-info` 0.3 vs `needs-discussion` 0.8：按 #140 红旗对 owner-driven Issue 应同时满足低 needs-info / 高 needs-discussion，✅ 符合。
- ❌ **遗漏 `breaking-change` 评估**：新增"批量撤回被踢用户历史"对部分群可能不希望自动触发，配置粒度变化是否构成 breaking-change？应分析：默认行为是否关闭（建议默认关闭 → 不构成）。应给出 0.30-0.45 置信度的 `breaking-change` 候选并说明判断依据。
- ❌ **遗漏 `privacy` 标签**：清空他人历史记录涉及隐私边界（成员是否同意），是仓库新维度。建议 0.55-0.65 新建。
- ❌ **缺 `event-driven`/`on-kick` 标签**：核心触发机制是"踢出事件 hook"，是新增能力维度。建议 0.60-0.70。
- ⚠️ `configuration` 0.88：高。按群覆盖只是诉求中一项，"配置粒度"对全局影响有限，建议 0.70-0.78。

**七处同步点是否遗漏？** #139 硬约束：分支A 的七处同步清单。本 Issue 不涉及"删除既有命令"，但涉及"新增命令 + 新增配置项 + 新增事件触发器"，同步清单为：
- `main.py` + `_GM_COMMAND_NAMES` + `kick` handler 改造 + `_conf_schema.json` 新字段 + `README` + 帮助文本 + `CHANGELOG`
分析中提及了，但**未明确指出元组注册**是易错点（#139 案例的硬约束级同步点）。

## 3. 可行性判断质量

**三档分支估算大体合理**，但存在以下问题：

### 估算校准问题

- **分支A 80-150 行/1.5-2.5 天**偏低。考虑：① `message_history` 必须按群+用户双键索引（不是单用户过滤）② 加入踢人事件订阅入口 ③ 批撤回的限流/分批处理 ④ 排除 bot 自身消息 ⑤ 帮助/CHANGELOG/README 同步。实际应 **120-200 行/2-3 天**。
- **分支B 180-300 行/3-5 天**合理，但缺一项关键依赖：**AstrBot 框架是否暴露踢出事件 hook**？当前分析已提及，但应作为前置硬约束而非风险点之一。若框架未暴露，需要 hook OneBot `notice` 类事件（`group_decrease`/`group_member_leave`/`group_member_kick`），跨适配器名称不一致，是分支B 真实工作量翻倍点。
- **分支C 250-450 行/4-6 天**合理。

### 技术依赖识别

✅ **已识别**：① 撤回 2 分钟时限 ② 批撤回限速 ③ bot 消息排除 ④ OneBot 跨适配器差异 ⑤ 时序（先 kick 后撤回）

❌ **遗漏**：
- **踢人事件触发源**：是维护者执行 `/踢` 才触发，还是任何形式（机器人踢、用户自助退群、管理员 QQ 移动端踢人）都要触发？差异极大。前者简单（命令 handler 内即可），后者需要订阅 OneBot `notice` 事件。
- **`message_id` 有效性窗口**：超过 2 分钟的 `delete_msg` 调用会失败，需要静默忽略还是统计失败数？建议降级为 warning 日志而非用户报错。
- **`message_history` 容量**：deque maxlen 设多大？仓库现状如何？应核查。
- **群成员退群后 `get_group_member_info` 是否可用**：用户被踢后该 API 通常仍可回读（部分适配器），部分会返回 404。应作为分支B 的回读兜底明确化。

### 风险点遗漏

- **撤回风暴限流**：高频发言群（500 人 + 高活跃），踢一人可能需撤回数百条消息。OneBot 限速通常 20-30 msg/s，需要 sleep 分批或队列。
- **撤回隐私边界**：撤回是"删除消息"语义，对其他群成员而言仍是可见的历史撤回提示（"XXX 撤回了一条消息"），并非真正清除。摘要未明示此局限，可能误导用户。

## 6. 经验教训

### 本 Issue 特有的仓库模式沉淀

**新模板候选：事件驱动型命令（踢出事件 → 批量撤销动作）**

- **触发识别关键词**：`被踢`、`退出群`、`退群后`、`on-kick`、`leave-event`、`group_decrease`
- **必查清单**：
  1. AstrBot 是否暴露 kick/leave 事件 hook，还是需要 hook OneBot `notice`
  2. OneBot `notice` 事件跨适配器字段名差异（`sub_type`/`event`/`notice_type`）
  3. `message_history` 容量现状与 deque maxlen
  4. 撤回 2 分钟硬约束下的降级策略
  5. 批撤回限速（OneBot 通常 20-30/s）
  6. bot 自身消息排除
  7. 撤回 ≠ 清除（对其他群员仍可见撤回提示）
  8. 配置 schema：`clear_history_on_kick` 全局 + `group_overrides` 覆盖
  9. 区分"维护者踢人命令触发" vs "任意踢出事件触发"
  10. 撤回失败的统计与日志

### 跨模板复用要点

- ✅ **撤回缓存三层链路**（`recent_messages` → `message_history` → `get_group_msg_history`）已识别
- ✅ **按群配置 schema 模式**（全局默认 + 群级覆盖 + 0 是合法配置）已识别
- ✅ **七处同步清单**已部分识别，应明示 `_GM_COMMAND_NAMES` 元组注册为易错点
- ⚠️ **owner-driven ≠ 无决策**（#140 沉淀）适用：本 Issue 有 4+ 决策点（默认开关、群覆盖策略、撤回超时降级、批撤回限流），`needs-discussion` ≥0.80 ✅

### 必须落入项目记忆的教训

1. **事件驱动型工作流是新一类 Issue 模板**：与既有的"权限模型重构"/"举报通知路由"/"命令集重构"并列。建议入库为第 5 种模式。
2. **撤回 ≠ 清除**：分析时必须明示该区分，否则用户预期会与实际行为不符。
3. **OneBot 跨适配器 notice 事件字段差异**：目前项目记忆沉淀了 message 类字段差异（#135/#136），但 **notice 类（kick/leave/admin 变化）差异矩阵未沉淀**。应在本次或下次触及时的反思中建立。
4. **校验失败短路器、重复检测措辞禁令**：本次在重复检测章节触犯"未检测到重复"措辞禁令（#136/#139/#140 第 9-10 次触犯），必须升级为第一优先级自检项。
5. **`message-history` 等生僻标签置信度上限**：新建标签首次使用建议置信度 ≤0.75，避免误导后续检索。
