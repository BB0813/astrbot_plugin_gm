## 3. 可行性判断质量

**高质量部分：**
- ✅ 明确指出"复用 /设精 模式"——这是本 Issue 最关键的可行性论据
- ✅ 识别 OneBot 适配器差异风险

- ✅ 风险点列表清晰（API 差异、bot 权限、消息撤回兜底）

**薄弱部分：**

1. **未明确 OneBot 群待办 API 的真实存在性**：
   - 这是关键技术依赖。OneBot v11 标准协议中**并未定义 `set_group_todo` 或 `send_group_todo`**——这是 go-cqhttp/NapCat/Lagrange 等实现的非标准扩展。
   - 主流支持情况：
     - **go-cqhttp**：无标准群待办 API（需 HTTP API 插件扩展）
     - **NapCat**：通过 `_set_group_todo` 或类似扩展提供
     - **Lagrange**：通常不支持或依赖插件
   - 分析应**明确指出 "主流 OneBot v11 实现中群待办 API 并非标准协议，属扩展能力"**，否则会误导实现者。

2. **跨适配器差异描述过于乐观**：
   - 分析说"沿用现有 _execute_action 双名 fallback 模式"——但双名 fallback 适用于**已知两种命名**，而群待办可能根本**无标准命名**。
   - 应明确："若多数适配器不支持，需 `needs-info` 收集用户适配器类型后再决策"。

3. **权限风险未充分展开**：
   - QQ 群中**只有群主**能设置群待办（部分客户端允许管理员），与"群管理员可设精"不同
   - 应建议：复用 `_is_group_owner` 而非 `_is_group_admin_or_owner`

4. **撤回兜底分析不足**：
   - "被设消息已撤回的兜底提示"——OneBot 群待办 API 对已撤回消息的行为未明确，需实测
   - 建议补充："需在引用消息解析后立即校验 reply_id 有效性"

5. **未提及 CHANGELOG 同步**：
   - 按项目记忆，五处同步清单包括 CHANGELOG
   - 虽然是新增而非修改，仍应在 changelog 中登记

## 6. 经验教训

### 6.1 本 Issue 的关键洞察

**群待办 vs 群精华 是表面相似实质不同**：
- /设精：OneBot v11 标准 `set_essence_msg`，跨适配器一致
- /添加群待办：**非 OneBot v11 标准**，属扩展能力，跨适配器差异大
- 分析将两者"几乎同构"——这是**关键的可行性误判**。表面看都是 reply_id + 单 API 调用，但 API 可用性本身就是个未解问题。

### 6.2 仓库特有的模式沉淀建议

**新增"引用消息触发型命令"类 Issue 标准分析模板**：

必查项：
1. **OneBot API 标准性**：是否为 v11 标准协议？若是扩展能力需 `needs-info` 高权重
2. **API 权限要求**：群主专属 vs 群管即可 vs bot 自身权限
3. **reply_id 解析路径**：`_get_reply_id` 兼容性校验（防 reply_id 为 None）
4. **跨适配器 fallback**：若扩展能力，需列出已知适配器支持矩阵
5. **消息已撤回兜底**：引用消息可能已被目标消息发送者撤回

### 6.3 标签体系建议

建议在仓库新增/强化以下标签（若尚未建立）：
- `reply` 或 `quote-message`：标识依赖 reply_id 解析的命令
- `bot-capability`：标识依赖 bot 特定能力（如群待办、群精华）的命令
- `onebot-extension`：标识依赖 OneBot 扩展 API（非 v11 标准）的命令——本 Issue 应打此标签

### 6.4 配置 schema 设计的经验

**按群覆盖 vs 全局开关**的决策清单：
- 是否需要"某些群禁用"场景？（几乎所有群管命令都建议支持）
- 是否需要"某些群仅特定人可用"？（权限模型问题，独立 issue）
- 建议默认值：全局 enabled，按群 override 关闭为主（与现有 `group_overrides` 模式一致）
