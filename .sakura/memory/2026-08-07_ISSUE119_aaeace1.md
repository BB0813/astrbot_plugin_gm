不过可以进一步说明：

## 6. 经验教训

### 对此类 Issue 的分析要点

1. **“提示成功但实际未生效”要优先怀疑回读校验逻辑**
   不能只看 API 是否返回成功，尤其是群管理 API，必须结合状态回读确认。

2. **空字符串与空白字符串必须严格区分**
   对“清空头衔”这类功能，`""`、`" "`、`\t`、`None`、字段缺失代表完全不同的状态。  
   使用 `strip()` 判断会掩盖真实状态。

3. **兼容性兜底不能伪装成成功**
   如果代码为了兼容旧适配器而设置 `special_title=" "`，那它本质上不是“恢复默认头衔”，而是“设置为空白显示头衔”。提示必须准确。

4. **OneBot 适配器差异是核心风险**
   NapCat、Lagrange、go-cqhttp 对 `set_group_special_title` 的参数接受程度、返回结果和状态回读可能不同。分析时应避免把某一个实现的行为当作标准行为。

5. **关联 Issue 不等于重复 Issue**
   如果旧 Issue 是“取消头衔不生效”，新 Issue 明确指出“空格头衔”根因，那么新 Issue 可能提供了更好的复现证据。应优先标记关联，而不是草率关闭为重复。

### 对仓库特有模式的建议

- 群管理命令应统一形成“调用 API → 回读状态 → 判断真实结果 → 输出准确提示”的模式。
- 涉及头衔、管理员、踢人、禁言等高差异 OneBot API 时，应维护适配器兼容说明。
- 对降级策略应提供配置开关，例如：
  - 禁用空格兜底；
  - 启用旧适配器兼容模式；
  - 成功提示区分“已恢复默认”和“已使用兼容空白头衔”。
