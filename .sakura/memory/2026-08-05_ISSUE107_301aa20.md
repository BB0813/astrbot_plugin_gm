## 1. 分类与优先级准确性

### 分类

分类为 `bug` 基本准确。

Issue 的核心不是“希望新增按群配置能力”，而是用户认为该阈值已经配置为按群维度，但展示或配置入口仍表现为全局插件配置，造成实际能力与用户界面/文档不一致。这属于已有功能行为不一致或配置体验错误，因此归为 `bug` 合理。

不过也可以补充次级类别：

- `configuration`
- `ui` / `config-ui`
- `documentation`
- `group-config`

如果仓库标签体系中有这些标签，应该一并推荐。因为该问题不一定是核心业务逻辑错误，而更偏向配置 schema、展示命令、文档和管理入口不一致。

### 优先级

`medium` 合理。

理由：

- 该问题影响按群配置体验，尤其是多群场景下可能导致管理员误判当前群阈值。
- 但根据分析，核心自动踢出逻辑已经通过 `get_group_setting` 读取 `mute_kick_threshold`，不一定导致功能完全不可用。
- 不是启动失败、权限绕过、数据损坏等高危问题。

因此不应升为 `high`。如果实际情况是配置 UI 完全无法设置群级阈值，且普通用户只能通过全局 UI 操作，那么可以在多群管理场景下接近 `medium-high`，但仍不至于严重阻断。

### 是否有关键词误判

没有明显机械匹配标题 `[bug][medium]` 的问题。分析结果结合了代码路径和影响范围，判断较可信。

### 优点

5. 测试建议较完整，尤其是：
   - 未配置群回退全局
   - 覆盖为 `0` 表示关闭且不回退

### 可改进点

#### 1. 需要进一步区分“配置 UI”与“插件命令展示”

Issue 原文“还在插件配置设置”可能有两种含义：

1. AstrBot 控制台/配置 UI 中仍显示为全局配置；
2. 插件内 `/配置` 或类似命令仍显示为全局配置。

分析中同时提到了 `config_cmd` 和 `_conf_schema.json`，这是合理的，但应明确“需要先确认用户指的是哪一个入口”。因为这两个入口的修复路径不同：

- 如果是插件命令展示问题：修改 `config_cmd` 较直接。
- 如果是 AstrBot 配置 UI 问题：可能受框架限制，只能通过 schema 描述、README、群级命令弥补。

#### 2. 对 `_conf_schema.json` 的处理需要更谨慎

分析建议“在 `_conf_schema.json` 中明确支持按群覆盖”是合理的，但如果该字段仍作为全局默认值存在，就不一定应该从 schema 删除。

更准确的修复策略应是：

- 保留 `mute_kick_threshold` 作为全局默认值；
- 修改名称/描述为“全局默认禁言踢出阈值”；
- 在说明中标注“可通过群级命令覆盖”；
- 避免让用户误以为它是唯一配置来源；
- 若框架支持分组展示，可将 `group_overrides` 或群级设置说明放到更明显位置。

#### 3. 需要考虑配置迁移兼容性

如果开发者决定把配置项从全局 schema 中移除，可能导致旧配置无法直观看到或迁移风险。分析中提到“保留全局默认 + 群级覆盖”较稳妥，这是正确的，但可以更明确地建议不要直接删除全局项。

## 6. 经验教训

### 1. 按群配置类 Issue 要区分三层问题

未来分析类似 Issue 时，应明确区分：

1. **业务读取层**  
   代码实际执行时是否使用 `get_group_setting` 或等价逻辑读取群级覆盖。

2. **命令管理层**  
   群级设置、查看、清除命令是否能正确写入和展示 `group_overrides[group_id][key]`。

3. **配置展示/UI/schema 层**  
   `_conf_schema.json`、AstrBot UI、README、插件配置命令是否正确表达“全局默认 + 群级覆盖”的语义。

本 Issue 的核心大概率在第三层，而不是第一层。

### 2. 不要把“全局配置项存在”直接视为 bug

对于支持群级覆盖的配置项，保留全局默认值是合理设计。真正的问题是：

- 是否清楚标注它是“全局默认”；
- 是否能查看当前群有效值；
- 是否能看出该值来自全局还是群级覆盖；
- 是否提供群级覆盖入口。

因此修复时不应简单删除 `mute_kick_threshold` 的全局配置。

### 3. 状态展示应显示“有效值 + 来源”

对多群配置最友好的展示方式是：

```text
禁言踢出阈值：3
来源：当前群覆盖
全局默认值：5
```

或：

```text
禁言踢出阈值：5
来源：全局默认
```

这比单纯展示 `c.get("mute_kick_threshold")` 更不容易误导用户。

### 4. 注意 `0`、空值、缺失值的语义

本次分析正确提到“覆盖为 0 表示关闭且不回退”。这是按群配置里非常关键的边界。

未来分析类似配置项时，也应特别检查：

- `0` 是否有效配置；
- 空列表是否表示覆盖为空还是回退；
- `None`、缺失 key、空字符串是否被混淆；
- `dict.get(key, default)` 是否错误吞掉了合法假值。

### 5. 文档与 schema 是配置类 bug 的一部分

配置相关 Issue 不应只看运行逻辑。对 AstrBot 插件来说，至少要同步检查：

- `_conf_schema.json`
- README
- 帮助命令
- 配置查看命令
- 示例配置
- 默认配置初始化

否则容易出现“功能其实支持，但用户不知道怎么用”的伪 bug 或体验 bug。
