# Issue #125 分析反思

## 1. 分类与优先级准确性

**分类：bug（置信度 0.9）——准确**

该 Issue 描述的是用户执行 `/取消头衔` 后系统提示"头衔清除后仍被读到"，明确是功能未达预期，符合 bug 定义。但需注意一个微妙之处：从插件视角看，三段兜底策略已经"尽职"执行了，set_group_special_title 也可能返回成功，**真正的失败发生在 QQ 协议层**（Bot 无权修改目标头衔）。这其实是"环境/权限限制导致的预期失败"，而非代码逻辑 bug。分类为 bug 是合理的（用户感受到的就是功能失效），但分析中应该明确"代码层无 bug，本质是环境限制"。

**优先级：medium ——基本合理，但值得讨论**

- 当前判断依据：核心命令局部不可用，权限/环境因素影响，非完全阻断
- 替代视角：考虑到 `/取消头衔` 是群管理基础命令，且失败原因是**结构性**的（Bot 权限等级 ≤ 目标用户时 QQ 协议不允许修改），这并非一次性 bug 而是**普遍性限制**。如果 issue 仓库里此类问题反复出现（PR #123 已修过相关判空逻辑），说明用户期待与协议现实存在持续落差。
- 建议优先级保持 medium，但分析中应强调这是"协议层硬限制 + 提示文案可优化"的双重问题。

## 6. 经验教训

### a) 头衔类 Issue 的特定模式

本 Issue 揭示了一个**反复出现的反模式**：
1. 用户执行 `/取消头衔` → 失败
2. 插件代码已经尽力（PR #123 三段兜底）
3. 真实失败原因是 **Bot 权限等级 ≤ 目标用户**（QQ 协议硬限制）
4. 用户感到困惑："代码都改了为啥还不行？"

**建议**：在 README 中显式说明 `/取消头衔` 的限制条件（Bot 必须是群主或目标用户不是群主/管理员），减少此类 issue 反复出现。

### b) "代码已尽力"的提示文案设计

当前失败提示"头衔清除后仍被读到"在技术上是准确的，但对用户**不友好**——用户不知道"仍被读到"是回读校验触发的，也不知道自己该怎么办（换个目标？升级 Bot？检查群设置？）。

**优化方向**：失败提示应包含：
- 已尝试的策略（"已尝试特殊标题空/空格两种清空策略"）
- 最可能的环境原因（"目标用户为群主/管理员时，Bot 无法修改其头衔"）
- 用户可执行的下一步（"如 Bot 为群主仍失败，请检查 OneBot 实现版本"）

### c) 环境信息收集的代码化

分析中提到"补齐环境信息收集"，这应该作为独立的 enhancement 而非依附于 bug fix。建议新增：
- 调试命令 `/头衔诊断 @用户`：输出 Bot 群角色、目标用户身份、当前 special_title、调用 API 的 retcode
- 这样既减少重复 issue，又能给用户提供自助排查工具

### d) 标签系统的模块化覆盖

项目记忆已经反复强调头衔类 bug 应给 `title`/`special-title` 标签，但本次分析仍然遗漏。这说明**标签完整性原则需要在每次分析时主动 checklist**，而非依赖记忆。**建议未来给类似分析添加显式的标签 checklist**：
- [ ] bug/enhancement/question 主分类
- [ ] 模块标签（command/parser/group-management/recall/title/...）
- [ ] 适配器标签（onebot/napcat/lagrange/...）
- [ ] 决策标签（needs-info/needs-discussion/help wanted/...）

### e) 重复检测的措辞纪律

"可能是 #111 的重复"是典型的高风险判断（#1 通常是初始化 issue，#111 这种中段编号可能是另一个完全无关的 bug）。即使分析者主观上觉得相似，也应该：
1. 降级为"暂未发现 + 检索词"，或
2. 明确给出"与 #111 同症状/同命令/同模块"的依据链
