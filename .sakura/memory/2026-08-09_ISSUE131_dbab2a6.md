# Issue #131 分析反思

## 1. 分类与优先级准确性

**分类：`enhancement` — 准确**
- 维护者本人发起新增功能请求，与项目记忆中 #125（bug）、#130（enhancement + breaking-change）的处理模式区分清晰。
- 没有任何"提示成功但实际未生效"的反馈信息，不属于 bug。
- 不涉及权限模型重构，不属于 breaking-change。

**优先级：`medium` — 合理但可再斟酌**
- 群待办属于"群管理增强能力"，非核心命令（撤回/禁言/头衔）。
- 风险点：① OneBot 跨适配器支持度差异大 ② 用户可能误以为功能可用但实际静默失败 ③ 权限边界（仅群管/群主/插件管理员可调用）需明确。
- 项目记忆 §4.5/§4.12 已记录"API 返回 ok ≠ 实际生效"反模式，群待办是典型场景（QQ 客户端 UI 显示异步），优先级应反映"中低风险 + 跨适配器不确定性"。
- **建议维持 `medium`**：比 #130 权限模型重构轻（无 breaking-change、无配置迁移），但比纯文档/小重构重（涉及 API 调用 + 权限校验 + 引用提取 + 失败回退）。

**潜在改进**：如果严格按照"维护者本人 + 单文件改动 + 工作量 60-100 行"的组合，可考虑降至 `low`，但鉴于跨适配器不确定性 + "成功提示但 UI 不显示"风险，`medium` 更稳妥。

**风险识别**：
- ✅ 跨适配器差异（NapCat / Lagrange / go-cqhttp）

**遗漏风险**：
1. **群待办消息内容是否允许为空/为空时的处理**：如果引用的消息是图片/表情/合并转发，OneBot 端能否处理？是否需要提示"仅支持文本消息"？
2. **同一消息被多次设为群待办**：是否需要去重或提示"已存在"？
3. **bot 自身权限**：bot 是否必须是群管理员才能调用 set_group_todo？QQ 客户端层面群待办的创建权限是什么？（QQ 群待办通常需要群主或管理员权限）

5. **消息撤回与群待办的相互作用**：如果原消息被撤回，群待办是否失效？这关系到撤回缓存链路的横切关注点。

## 6. 经验教训

### 6.1 仓库特有的"群管理动作"模式总结

通过 #131 分析，可提炼仓库"群管理动作新增"的标准模板：

```
1. 权限校验：_is_group_admin_or_owner + is_plugin_admin
2. 引用提取：_get_reply_id(event)
3. 参数转换：_execute_action 已处理 group_id/user_id/message_id int 转换
4. API 调用三段式：标准名 → 带下划线变体 → 降级为提示
5. 失败回退：返回成功 ≠ UI 生效（项目记忆 §4.5/§4.12）
6. 元组注册：_GM_COMMAND_NAMES 加入新指令名
7. 同步清单：main.py + README + 帮助 + CHANGELOG + (可能) _conf_schema.json
```

### 6.2 跨适配器差异的"参考适配器矩阵"

本次分析未给出完整的"参考适配器矩阵"，未来类似 Issue 应补充：

| 适配器 | API 名称 | 参数 | 已知限制 |
|--------|---------|------|---------|
| NapCat | `_set_group_todo` | group_id, message_id | 待验证 |
| go-cqhttp | `set_group_todo` / 未实现 | - | 待验证 |
| Lagrange | `set_group_todo` | group_id, message_id | 待验证 |

### 6.3 "API 返回 ok ≠ UI 生效"反模式的群待办专项警示

QQ 群待办的特殊性：
- API 返回成功 → QQ 服务端写入 → 客户端 UI 异步刷新
- 部分适配器（尤其旧版 go-cqhttp）API 接受但实际不写入
- 用户反馈"添加了但看不到"是高频问题

建议在指令提示中加入："已设为群待办，请打开群消息顶部查看（约 1-2 秒后生效）"，降低用户误判概率。

### 6.4 行号引用的可溯源问题

项目记忆 §1 明确"行号引用必须可溯源"。本次分析中 main.py 的 5 处行号引用（L398-401、L454-468、L607-620、L2266-2296、L2387-2433）密度高，但未声明验证方式。建议在可行性章节开头补一句：
