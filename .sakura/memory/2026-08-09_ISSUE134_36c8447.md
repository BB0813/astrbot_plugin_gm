# Issue #134 分析反思

## 一、整体判断

本次分析**整体降级失败**——触发反模式"校验失败短路器"。摘要明确写 `expected <REASON>` 字段校验错误，按反模式规则**应只修复字段输出，维持原始实质性判断**。但实际连分类、可行性、标签、标题、重复检测全部退化为 `other` / `无法评估` / 空 / "可能是 #125 的重复"。

**这正是反模式预描述的典型场景**：校验失败 → 整体降级 → 一连串决策崩塌。

## 二、逐维度反思

### 1. 分类与优先级

**正确做法**：Issue 内容是用户用 `解禁@用户` 命令，bot 实际解除了命令文本里的 `@𝓒𝓪𝓷𝓬𝓮𝓻` 字面量（被花体字转换前的部分），本质是**命令解析阶段 `@用户` 提取失败**或**参数解析把装饰字符当目标 QQ**。这明确属于：

- 主分类：**`bug`**（命令"成功"但实际行为错误）
- 辅助：`command` + `parser` + `at-parse` + `group-management` + `needs-info`（缺日志/版本/适配器信息）

**实际输出**：`other`——**错误**。摘要中"禁解禁获取信息问题"已是 bug 信号，且 `_extract_at_qq` 在项目记忆中是已知问题点（参 §头衔类模板的必查项⑦）。

**优先级**：核心禁言/解禁命令对群管理的影响范围大（误解禁可能放大已有禁言执行错误），但用户场景是单群单次误操作，**`medium`** 合适，不应升 high（未造成实际损害），也不应降 low（命令确实行为错误）。

### 2. 标签推荐

应给标签（按现有体系+仓库高频模式推断）：

| 标签 | 置信度 | 理由 |
|---|---|---|
| `bug` | 0.95 | 命令行为与意图不符 |
| `command` | 0.90 | 命令解析类问题 |
| `parser` | 0.85 | `@用户` 解析失败 |
| `at-parse`/`at-extract` | 0.80 | 仓库可新建该标签 |
| `group-management` | 0.75 | 禁言/解禁属于群管 |
| `onebot`/`compatibility` | 0.65 | 装饰字符 QQ 在不同适配器表现可能不同 |
| `needs-info` | 0.55 | 缺版本、commit、完整日志、装饰字符来源 |
| `mute`/`unmute` | 0.70 | 仓库可新建命令类标签 |

**实际输出**：空——**严重错误**，违反"标签在不确定体系时也应给通用候选"。

### 3. 可行性

应做条件判断（按"提示成功但实际未生效"通用模式）：

- **必查项**：① `_extract_at_qq` 是否对装饰字符（数学字母、组合字符、Emoji 风格 QQ）做了归一化 ② 装饰字符 QQ 经 AstrBot 事件框架后是原始字符串还是已规范化 ③ OneBot v11 `message` 段 `qq` 字段类型（字符串 vs 数字）④ 跨适配器对装饰字符 QQ 的处理 ⑤ 群号是否被装饰字符污染 ⑥ 是否有 `get_group_member_info` 回读校验
- **修复方向**：在 `_extract_at_qq` 增加归一化层（NFKC + 数字段提取），或要求装饰字符 QQ 必须 `@真实QQ` 同时输入
- **工作量**：20-60 行（条件判断+测试用例），1-2 天

**实际输出**：`无法评估`——**错误**。信息虽不完整，但**根因排查路径清晰**，足以做条件评估。

### 4. 重复检测

**严重错误**：`可能是 #125 的重复`。

- #125 是**头衔类**（`special_title` 解析+OneBot 兼容性），主分类 `bug`+`title`+`needs-info`。
- #134 是**禁言/解禁命令 `@用户` 解析**，主分类 `bug`+`parser`+`command`。

两者主分类虽都是 `bug`，但**根因模块完全不同**：一个是 `special_title` 传参与回读，一个是 `_extract_at_qq` 输入解析。按反模式"重复检测前置过滤"，#132 误报 #125 的教训就在记忆里，**这次又重蹈覆辙**。

表面相似点："解禁+获取信息问题" vs "头衔+获取信息问题"——都用了"获取信息"描述错误症状，但属于不同模块的同类症状。

正确做法：

```
未发现重复。建议检索关键词：`解禁`、`@用户解析`、`_extract_at_qq`、装饰字符 QQ、NFKC 归一化
⚠️ 措辞核对：是否使用了禁用的'未检测到重复'/'无重复'/'可能是#X的重复'？——是，已违规
```

### 5. 标题改写

原标题 `bug` 几乎无语义，应改写为：

```
[bug][medium] 禁言/解禁命令 @用户 解析异常：装饰字符 QQ 被误识别为解禁目标
```

或更简洁：

```
[bug] /解禁 命令对装饰字符 @用户 的解析错误
```

**实际输出**：`无建议`——**错误**，违反"标题字段禁止写'无建议'"。

## 三、经验教训（需固化）

### L1. 装饰字符 QQ / 视觉欺骗型用户名 是新晋高频模式

花体字（𝓒𝓪𝓷𝓬𝓮𝓻）、手写体、装饰字符、组合 Unicode 字母（如 𝐀、𝕒 等数学字母块）等"看起来是 QQ 号"但实际是字符串的输入，是**命令解析类 issue 的常见根因**。

**应建立的分析模板**：
- 触发关键词：`@用户` + `解禁`/`禁言`/`踢人`/`设管` + 装饰字符/数学字母/花体字
- 必查项：① `_extract_at_qq` 是否 NFKC 归一化 ② OneBot 适配器是否对装饰字符 QQ 拒绝/截断 ③ 群号是否也污染 ④ 是否需要在输入层加"QQ 必须是纯数字"硬校验 ⑤ 装饰字符 QQ 跨适配器命令成功率矩阵
- 修复建议：在 `_extract_at_qq` 顶部加 `unicodedata.normalize('NFKC', s)` + 正则 `\d{5,12}` 强校验 + 错误提示"目标 QQ 格式不正确"

### L2. "解禁+禁言"类命令比标题/踢人更敏感

误解禁的**安全影响**大于误禁言（用户已被禁言状态下，误解禁使其重新获得发言权，可能放大后续违规）。优先级评估时应纳入此权重。

### L3. 反模式再犯：`其他`+`无法评估`+空标签+`无建议`+`可能是#X重复`

本次完整触发五条反模式红线，**校验失败短路器没起作用**。建议在反思指令中显式加：

> 若反思摘要提及字段校验错误（如 `expected <REASON>`），则**只修复字段格式**，实质性判断（分类/优先级/标签/可行性/标题、重复检测）必须基于 Issue 实质内容独立完成，**不得连带退化**。

### L4. 重复检测的"症状相似 ≠ 根因相似"陷阱

#125（头衔）和本次（禁言）都用"获取信息问题"作为症状描述，但根因模块不同。下次遇到"获取信息问题"+"命令解析错误"模板时，**先按模块归类再判断重复**，不要按症状字符串相似度。

### L5. 项目记忆中已有的 `_extract_at_qq` 必查项应被主动激活

记忆 §头衔类模板必查项⑦："`_extract_at_qq` 解析"——但本次分析**未激活**这条记忆。说明基于关键词的模板触发机制对"解禁/禁言"类命令不敏感，应扩展关键词覆盖范围。

### L6. 工作量估算的反向校准

对"小修复"（<50 行）也要避免低估为 1 天内——装饰字符 QQ 测试矩阵（NapCat/Lagrange/go-cqhttp × 数学字母/手写体/Emoji 风格）至少需要半天构造测试用例。建议小修复工作量下限 1 天，包含最小适配器验证。
