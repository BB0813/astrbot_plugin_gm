# Issue #140 分析反思

## 1. 分类与优先级准确性

**分类**：`enhancement` 准确无误。这是维护者本人提出的功能增强需求（权限路由调整），不是 bug 修复。

**优先级 `medium`**：合理但需要更充分的论证。本次分析的优先级判定路径不够显式，应按项目记忆要求列出 4 条决策路径：
- ① 涉及权限模型变更 → 最低 medium ✓
- ② owner-driven + 已有 #130/#132/#139 标准化模板 → 不升 high ✓
- ③ 工作量可控 + 迁移路径明确 → 不升 high ✓
- ④ 跨适配器风险已识别但有降级路径 → 维持 medium ✓

**潜在升 high 因素**（被正确地没有采纳）：
- 全员可举报群员/管理员是重大权限变更，普通成员获得"举报权"实质上是给了一个潜在骚扰管理者的工具
- 但 issue 描述清晰、维护者主动发起、范围可控，维持 medium 合理

**潜在降 low 因素**：
- 不属于"纯减法"，是权限重构 + 通知路由改造，横切关注点多
- 不能降 low ✓

**应补充的论证**：与 #130/#132/#139（权限模型重构）的对比句——"与 §X 同级，因 Y 原因定 medium"。

## 3. 可行性判断质量

**优点**：
- 显式给出了 A/B/C 三档分支（符合 #133/#135/#139 沉淀硬约束）✓
- 识别了跨适配器字段差异 ✓
- 识别了群主早退分支 ✓
- 识别了五处同步清单 ✓

**不足与遗漏**：

1. **未显式讨论 `defaultdict`/缓存策略**（#130/#132 沉淀）：举报人角色 + 被举报人角色缓存策略、缓存失效、群成员退群后缓存清理
2. **未显式讨论 `get_group_member_info` 调用频率**：每条举报命令都查两次（举报人+被举报人），大群高频举报场景下的 API 限流风险
3. **未显式列出"举报群主"边界**：issue 未明确"举报群主"是否允许，分析中提到"需在 needs-discussion 中确认"但没给出推荐方案
4. **未显式列出隐私风险**：举报内容可能涉及隐私（"这个人在群里发色情链接"），通知给管理员/群主时的隐私边界
5. **未显式列出"匿名举报 vs 实名举报"决策点**：全员可举报场景下，匿名举报可减少报复风险但增加滥用风险，需明确决策
6. **未讨论"举报理由"字段**：当前设计是否携带举报理由？是否需新增参数？与原命令签名是否冲突？

**工作量估算**：
- 分支 A 80-150 行 / 1.5-2.5 天：合理
- 分支 B 200-300 行 / 3-4 天：合理但可能偏低，缺隐私/匿名/缓存/回读校验
- 分支 C 300-450 行 / 4-6 天：合理

**建议分支 D**（#139 沉淀第四档）：先最小化上线（分支 A），收集反馈后再迭代频次限制/匿名举报（分支 B/C），可作为分阶段方案。

## 5. 标题改写适当性

**原标题**：`[enhancement][medium] 调整 /举报 命令权限路由（举报普通成员/管理员分别走不同通知通道，群主不响应）`

**建议标题**：`[enhancement][medium] /举报 命令按举报人/被举报人角色分级路由通知通道（群主豁免）`

**评价**：
- 优点：更简洁、突出"角色分级路由"和"群主豁免"两个核心机制
- 缺点：
  - 丢失了"普通成员也可举报"这一关键信息（这是重大权限变更，必须在标题突出）
  - "群主豁免"语义略模糊（原标题"群主不响应"更直白）

**建议改写为**：
```
[enhancement][medium] /举报 命令全员开放并按角色分级通知（举报群员→全员管理，举报群管→仅群主，群主豁免）
```

保留"全员开放"这一关键权限变更信号，并明示三种角色×三种被举报人的路由规则。

## 6. 经验教训

### 6.1 仓库特有模式
- **本仓库的"权限模型变更"已形成稳定模式**（#130/#132/#139 加上本次 #140），未来涉及 `sender.role` 识别的权限重构应直接套用本次模板
- **"全员可 X"是重大权限变更信号**：必须在优先级章节显式对比"原本谁能做 vs 现在谁能做"，并评估恶意滥用风险

### 6.2 通用教训

1. **`needs-discussion` 对 owner-driven issue 仍应 ≥0.80**：issue 描述清晰不等于无决策点，"举报群主是否允许/通知私聊还是群内/频次限制/匿名与否"等都是未明确的设计决策

2. **权限矩阵改造类 issue 必须显式列出 2 维矩阵**：举报人 ∈ {群主,群管,普通成员} × 被举报人 ∈ {群员,群管,群主} = 9 种组合，每种组合的预期行为都应列清

3. **通知类命令必须明确"通知通道 + 通知对象 + 通知形式"三要素**：
   - 通道：私聊 vs 群内
   - 对象：哪些 QQ（所有管理/仅群主/特定名单）
   - 形式：@全体 vs 单发 vs 群待办

4. **"群主豁免/早退分支"是边界条件**：必须在分析中显式标注，避免后续 PR 漏处理

5. **"全员可 X"必须评估滥用风险**：恶意刷举报、虚假举报骚扰、被举报身份公开化、举报内容隐私边界——应在 needs-discussion 中列为决策点

### 6.3 仓库标签体系建议（新增）
- `notification` / `notification-channel`：通知通道分级专用
- `report` / `reporting`：举报类命令专用（与 #125 头衔、#135 禁言列表形成子体系）
