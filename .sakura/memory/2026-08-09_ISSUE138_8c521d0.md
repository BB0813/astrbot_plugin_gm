# Issue #138 分析反思

## 1. 分类与优先级准确性

### 分类评估：`enhancement` ✓
判断准确。本 Issue 包含**两个动作**：
- **去除** `/删群公告`（纯减法裁剪）
- **新增** `/取消群精华`（实质是 `/取消设精` 的语义收敛/别名重命名）

两者均属 enhancement，无歧义。

### 优先级评估：`medium` ⚠️ 需校准

**问题所在**：根据项目记忆明确沉淀的规则：
> **"删除功能"类 Issue 不应自动归 medium**：维护者本人纯减法性质的功能裁剪 → low 组合（主动减法+owner 自实施+无横切关注点）。

本 Issue 中**"去除 /删群公告"部分**符合上述规则的所有特征：
- 主动减法（维护者主动要求删除）
- owner-driven（作者就是维护者）
- 无横切关注点（仅一处 helper + 一处 handler + 元组注册 + README）

**但"新增 /取消群精华"部分**实质是别名/重命名，工作量极小（60-100 行）。

**反思结论**：将整个 Issue 定为 `medium` 偏高。理论上应降为 `low`，但因涉及**既有命令语法删除**（breaking-change 性质）且需要保留别名决策，影响文档与用户迁移路径，维持 `medium` 有一定合理性——但**应在分析中显式说明**为何不降 `low`，而非默认沿用 medium。

**建议修正**：在优先级章节增加显式决策路径：
- 路径①：纯减法+owner-driven → 应降 low
- 路径②：但涉及既有命令删除（breaking-change）+ 用户迁移 → 维持 medium
- 路径③：工作量 1-2 天可控 → 不升 high
- 路径④：跨适配器风险低（v11 标准协议）→ 维持 medium

### 影响范围分析
- **存量教程/用户习惯**：`/删群公告` 用法已被极少使用（要求 notice_id，使用门槛高），实际影响面小
- **`/取消设精` 已存在**：新命令不会破坏现有功能
- **跨群影响**：无
- **跨适配器影响**：`delete_essence_msg` 属 v11 标准协议，风险低

### 关键问题

**1. `parser` (0.45) 误标** ❌
本 Issue 不涉及命令解析逻辑改动（`_get_reply_id`、`_extract_at_qq` 等解析器无需变更）。仅是注册新 handler 函数并复制现有模板。**应删除此标签**。

**2. `recall` (0.15) 误标** ❌
虽然"取消群精华"在功能语义上与"消息撤回/取消"有表面相似性，但**本质是设置类命令的反向操作**（set_essence_msg 的撤销）。项目记忆中 `recall_cmd` 特指消息撤回（2 分钟时限内的消息删除），与本命令的 API（`delete_essence_msg`）和语义（取消精华标记）完全不同。**应删除此标签**。

**3. `breaking-change` (0.85) 偏高** ⚠️
仅有 `/删群公告` 一处命令删除（且本就使用门槛高、存量用户少）。breaking-change 应反映**对终端用户的实际破坏程度**，本案例破坏程度低。**建议降至 0.65-0.70**。

**4. `documentation` (0.75) 偏高** ⚠️
虽然涉及 README + 帮助命令 + CHANGELOG 三处同步，但这是**所有命令改动的常规同步项**，不属于"主要工作是文档"。**建议降至 0.55-0.60**，作为辅助标签。

### 遗漏的关键标签

**1. `rename` / `alias` 标签** ❌
本 Issue 核心是 `/取消设精` → `/取消群精华` 的重命名/别名化决策。**建议仓库新增 `rename` 或 `alias` 标签**（与 `command`、`group-management` 并列），置信度 0.75-0.85。这是本 Issue 最具区分度的标签，**必须添加**。

**2. `onebot` (0.35-0.50) 标签缺失** ⚠️
虽然 `delete_essence_msg` 属 v11 标准协议（vs #131 群待办的非标准 API），风险较低，但既然分析中提到了跨适配器兼容性考量，**应保留 `onebot` 标签（0.30-0.40）**作为风险标记。

## 6. 经验教训

### 仓库特定模式沉淀

**1. "命令别名/重命名"决策类 Issue 模式**（#138 新沉淀）

本仓库已出现多个命令命名相关 Issue（如 #131 群待办命名、#133 解禁/解除禁言措辞），建议固化以下模板：

- **触发场景**：维护者或用户反馈命令名不直观/易混淆
- **必查项**：① 既有命令使用频率与用户迁移成本 ② 别名 vs 重命名的取舍 ③ 帮助命令/教程/外部文档影响 ④ `_GM_COMMAND_NAMES` 元组同步 ⑤ CHANGELOG breaking-change 标注
- **标签基线**：`enhancement`(0.95) + `command`(0.95) + `rename`/`alias`(0.75-0.85, 新) + `breaking-change`(0.65-0.70) + `group-management`(0.85) + `needs-discussion`(0.75-0.85) + `documentation`(0.55-0.65)
- **可行性分支必显式**：分支A 最小（仅重命名，不保留别名）/ 分支B 完整（重命名+保留别名+迁移指南）/ 分支C 完整版+配置 schema 调整
- **优先级决策路径**：① 主动减法+owner-driven → 应降 low ② 但涉及既有命令删除 → 维持 medium ③ 别名决策未确定 → `needs-discussion` 高权重

**2. "纯减法功能裁剪"分析纪律**

- 此类 Issue 应**主动降低优先级**至 low（除非涉及横切关注点）
- 但应保留 `breaking-change` + `deprecation` 标签以标记潜在影响
- 工作量估算应聚焦"调用点清空 + 文档同步"两部分

**3. 标签体系的精细化方向**

- **建议仓库新增标签**：
  - `rename` / `alias`：命令重命名/别名专用
  - `cleanup` / `removal`：功能裁剪专用
  - `ui-text`：命令名/帮助文案修改专用

**4. 引用消息触发型命令的"实质新增 vs 别名化"区分**

#138 表面是"新增 /取消群精华"，实质是"为已有 `/取消设精` 添加更友好的命名入口"。这种"语义收敛型"改动与 #131"全新能力扩展"应在标签上有所区分：
- 全新能力：`bot-capability` + `onebot-extension` 高权重
- 语义收敛：`rename`/`alias` 高权重，`onebot-extension` 低权重

### 分析流程改进建议

**1. 优先级章节必须显式决策路径**（#133 沉淀硬约束）
本案例应列出 4 条判定路径：
1. 主动减法+owner-driven → 应降 low
