# Issue #128 分析反思

## 1. 分类与优先级准确性

**分类（enhancement）✅ 准确**
- 用户明确请求"加一个"功能，非 bug 修复，归 enhancement 无误。
- 与现有违规检测链路高度对称，属于"已有基础设施上的能力扩展"，非全新子系统，enhancement 比 feature 更贴切。

**优先级（medium）✅ 合理**
- 用户主动请求、非故障阻断、单群可控，符合 medium 典型场景。
- 但有一点值得反思：**medium 与 low 的边界**——本功能高度复用现有 `_handle_violation` 链路，模式成熟（参考 #105/#124 沉淀），技术风险主要集中在 STT 接口可用性这一个变量。如果 STT 能力是 AstrBot 框架层稳定提供（用户已说"使用 Astrbot 内置模型"），则实现工作量偏低，medium 偏高估。建议**有条件地标注**：默认 medium，若确认 STT 框架级可用可降至 low。当前 medium 决策可接受，但分析中未显式讨论"是否可能降级"。

**影响范围考量**
- 分析未充分讨论**误伤风险**：语音转文字的准确率远低于文本（方言、噪声、专业术语、口音均影响），关键词误命中概率高于纯文本检测。这意味着同样一组违禁词，在语音通道的误伤率更高，可能导致**正常用户被错误撤回+禁言**。这是一个被低估的横切关注点，应在风险章节显式标注，并建议：
  - 首次实施使用更严格的匹配策略（如多关键词同时命中、加入置信度阈值）
  - 提供"仅撤回不禁言"或"仅记录不处置"的中间档
  - 在 README 显式提醒误伤风险

## 3. 可行性判断质量

**优点**
- 正确识别了"复用现有基础设施"的核心优势，列出的可复用点（`_moderation_dispatch`、`_handle_violation`、`get_group_setting`、`_check_profanity`）准确。
- 工作量估算参照历史 issue 经验，给出了"100-200 行 main.py + schema + README/帮助同步"的合理区间。
- async/yield 风险评估准确，主动关联 PR #123 沉淀。

**不足与改进**

1. **未充分讨论"框架依赖"对可行性的决定性影响**
   - 用户说"使用 Astrbot 内置模型"——但 AstrBot 是否有统一的 STT provider 接口？语音消息段是否携带转写文本？还是需要插件自行调用 STT API？这两个分支的实现工作量差距巨大：
     - 分支A（消息段已带转写文本）：~100-150 行，2-3 天
     - 分支B（需插件自行调 STT API）：~200-300 行 + STT endpoint 配置 + 流式识别处理 + 大文件上传/下载 + 错误处理 + 配额管理，5-7 天
   - 分析中虽提到了这一风险，但未给出**分支判断后工作量的差异**。建议在可行性章节明确"若分支A则……若分支B则……"。

2. **语音转写的额外技术挑战未充分展开**
   - **流式 vs 整段识别**：长语音（>1分钟）需要流式识别还是先下载完整文件再识别？
   - **音频格式兼容**：silk/opus/amr/mp3 不同格式需不同解码路径
   - **下载与缓存**：QQ 语音通常以 silk 格式存储在 OneBot 服务器，需先 `get_record` 或类似接口获取
   - **超时与重试**：语音文件可能较大，下载超时需处理
   - **配额与成本**：若使用云端 STT API，调用成本与配额管理
   - 这些虽然不是项目记忆要求的核心，但应至少在风险章节列出 1-2 个关键点。

3. **跨适配器兼容性讨论不充分**
   - 分析提到"NapCat/Lagrange 对 voice segment 的字段名可能不一致"，但仅一句带过。建议给出具体清单（已知差异：`file`、`url`、`file_size`、`duration`、`format` 等字段在不同适配器下的命名）。

4. **"误伤风险"作为技术风险被低估**
   - 如前述，语音转文字准确率低于纯文本，关键词误命中概率显著上升，应作为可行性章节的**主要风险**之一讨论，而非仅作为分类提示。

## 6. 经验教训

### 6.1 仓库特有模式（本 issue 触发的新沉淀）

1. **"非文本消息类型违规检测" 是新一类横切关注点**
   - 现有 `_handle_violation` 链路假设输入是纯文本。本 issue 扩展到语音，意味着：
     - 消息类型识别逻辑需独立维护（文本/语音/图片/文件/转发）
     - 每种类型需对应的"转文字/转 OCR/转文件名"中间层
     - 关键词匹配与处置动作可复用，但**准确率/误伤率差异巨大**（文本 100% vs 语音 ~85-95%）
   - 建议在项目记忆中固化为**"多模态违规检测标准模式"**：消息类型 → 转文字层 → 关键词匹配 → 标准处置。
   - 未来若有图片 OCR 关键词检测、文件名校验、转发消息检测等同类需求，应自动套用此模式。

2. **"STT/OCR/CV 能力依赖"是新的可行性分支变量**
   - 之前的 issue 主要依赖 AstrBot 框架本身的纯文本消息处理能力。本 issue 引入了对 AstrBot 是否暴露 STT provider 的依赖，这是新的可行性分支判定点。
   - 建议在项目记忆"分类与可行性"章节固化为：**涉及多媒体转写（STT/OCR）的 issue，可行性判断必须先确认框架层是否提供对应能力，否则分支工作量差异显著**。

3. **"撤回命令族五处同步清单"需扩展为"撤回+禁言命令族七处同步清单"**
   - 现有清单：main.py + README + 帮助命令 + 配置 schema + CHANGELOG。
   - 本类 issue 新增两个同步项：①**STT 配置文件/字段**（如 AstrBot 框架 STT 配置项的位置）②**误伤率文档说明**（README 风险提示）。
   - 未来涉及"消息预处理层"（语音/图片/文件转文字）的 issue 都应包含这两个同步项。

### 6.2 通用分析经验

1. **`needs-info` 置信度应基于"用户已表达明确性"动态调整**
   - 本 issue 用户已明确说"使用 Astrbot 内置模型"，缺失的是**框架能力确认**而非**用户意图确认**。此时 `needs-info` 应保持中低（0.35-0.50），`needs-discussion` 应更高（0.80+），因为核心待办是"如何集成"而非"用户想要什么"。
   - 反模式提醒：不要把"系统能力待确认"等同于"needs-info 高权重"。

2. **"用户主动请求 + 复用现有链路"类 issue 的工作量普遍被高估**
   - 维护者反复提交此类 issue 意味着已心中有数。工作量估算应主动向"中等偏低"倾斜，而非套用全新子系统的中等估算。
   - 但 STT 接入是新的不确定性变量，工作量上限应保留"中等"的可能。

3. **误伤风险作为"非显式但关键"的可行性变量**
   - 纯文本违规检测：误伤率 ~0%（除非关键词本身有歧义）
   - 语音转文字违规检测：误伤率 5-15%（取决于音频质量、口音、噪声）
   - 图片 OCR：误伤率 10-20%
   - 任何非文本消息类型的关键词检测都应**默认上调误伤风险权重**，并主动建议：
     - 灰度发布（仅特定群启用）
     - 阈值策略（多关键词同时命中才触发）
     - 降级动作（先仅撤回+警告，不立即禁言）
   - 这是项目记忆未覆盖的新维度，建议补充。

4. **重复检测反模式的应用强化**
   - 本次违反"暂未发现+关键词"模板，说明反模式的应用需在每次重复检测时主动核对。应在每次重复检测输出的最末强制加注："⚠️ 措辞核对：是否使用了禁用的'未检测到重复'/'无重复'/'可能是#1的重复'？"

## 总结

**整体评估**：分析质量较高，分类与可行性核心判断准确，标签体系与项目记忆保持一致。

**主要改进点**：
1. **重复检测措辞违反反模式**，需修正为"暂未发现+检索词"模板。
2. **误伤风险作为横切关注点未被充分识别**，建议在风险章节显式展开。
3. **STT 框架能力依赖的分支工作量差异未充分展开**，可行性判断需明确"分支A vs 分支B"。
4. **`needs-info` 置信度偏高**，应降至 0.40 左右，`needs-discussion` 保持高位。
5. **新增标签建议**：`stt`/`voice`、`recall`、`profanity`/`moderation`、`configuration`、`whitelist`。
6. **标题副标题过度技术化**，精简为"语音消息转文字后命中关键词自动撤回并禁言"。
7. **项目记忆新沉淀**：建议固化"非文本消息类型违规检测"模式、"多媒体转写依赖分支判定"原则、"撤回+禁言命令族七处同步清单"。

**优先级微调建议**：medium 可保留但建议在分析中补充"若 STT 框架能力确认可降至 low"的备注，避免对维护者本人提交的高度复用类 issue 过度分级。
