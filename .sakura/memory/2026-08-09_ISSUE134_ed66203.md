# Issue #134 分析反思

## 1. 分类与优先级准确性

**分类 `bug` ✅ 准确**。命令行为与用户意图严重不符（误解禁装饰字符用户），属典型运行期解析错误，无歧义。

**优先级 `medium` ✅ 合理**，但分析中存在一处隐含逻辑需要审视：
- 摘要中提到"误解禁比误禁言影响更严重"——但本 Issue 的实际症状是"误将装饰字符 QQ 当作合法 user_id 执行解禁"，**并未涉及误禁言**。装饰字符在 QQ 后端解析失败时通常会被 NapCat/Lagrange 静默忽略或抛错，**直接误解禁真人目标的概率极低**（除非装饰字符恰好 NFKD 归一化后等于某个真实 QQ 号，这种碰撞概率几乎为 0）。
- 所以 "medium" 的理由应改为：**核心命令解析存在输入校验缺陷** + **跨适配器行为不一致** + **影响所有群管理命令族**（/禁言、/踢人、/设管、/取管），而非"误解禁比误禁言影响更严重"。

**建议补充到优先级决策路径**：
1. 核心命令行为错误 → 最低 medium
2. 单群单次未升 high（无证据显示影响范围扩散）
3. 同命令族全部受影响 → 维持 medium 而非降 low
4. 已有兜底（适配器大多会拒绝非法 user_id）→ 维持 medium 而非升 high

## 6. 经验教训

### 6.1 沉淀到项目记忆的新模式

**装饰字符 Unicode 数字块攻击向量（必须加入模板）**：
- 不仅要拦截"花体字母"，还要拦截 NFKD 归一化后会变成数字的 Unicode 字符（`𝟘-𝟡` U+1D7D8-1D7E1、`⁰-⁹` U+2070-U+2079、`₀-₉` U+2080-U+2089、`０-９` U+FF10-U+FF19 全角数字等）
- 安全校验顺序必须是：**正则失败 → 直接拒绝**，**不得**先尝试 NFKD 归一化再校验
- 推荐：先用 `r'^\d{5,12}$'` 严格匹配，匹配失败再做 NFKD 归一化做兜底提示，但**不得**把归一化后的结果当作合法 QQ

**优先从消息 segment 提取而非从文本正则提取**：
- AstrBot 的 `event.message_obj.message` 列表中 `type='at'` 的 segment 含有真实的 `data.qq`，不会被装饰字符欺骗
- 从原始文本用 `r'@(.+?)'` 提取昵称或字符串是危险的（昵称可任意装饰）
- 仓库应统一封装 `_extract_at_qq_via_segment(event)` 作为唯一权威入口

### 6.2 对特定类型 Issue 的分析经验

**输入校验类 bug 的标准分析骨架**：
1. **校验位置**：解析层 vs 输入层 vs API 层（应在哪个环节早退？）
2. **校验强度**：宽松（接受装饰字符但下游报错）/ 严格（直接拒绝非纯数字输入）
3. **归一化安全性**：NFKC/NFKD 归一化可能引入安全漏洞（数字块攻击）
4. **消息段 vs 文本**：协议层数据 vs 用户输入文本，前者优先
5. **同命令族扫描**：单点修复 vs 全命令族修复
6. **跨适配器差异**：上游校验 vs 下游校验的边界
7. **错误提示友好度**：技术报错 vs 用户可理解的提示

### 6.3 仓库特有模式和建议

**装饰字符 / 视觉欺骗类用户名已是仓库高频解析 bug 模式**（项目记忆已标记为"已第四次触发校验失败短路"）。建议：
- 在仓库 README 显式声明"QQ 输入必须是 5-12 位纯数字 ASCII，禁止花体字/数学字母/手写体"
- 在 `_extract_at_qq` 添加 docstring 警示未来的修改者"不得移除 NFKC 归一化和正则硬校验"
- 增加单元测试覆盖：花体字母、数学字母块、Unicode 数字块、混合 ASCII + 装饰字符、emoji 风格用户名

**owner-driven Issue 的标签校准模板**：
- `needs-info` 应低（≤0.35）——维护者自己最清楚问题
- `needs-discussion` 应中等（≥0.55）——设计决策点存在（输入层 vs 解析层校验）
- `help wanted` / `good first issue` 应极低（≤0.10）——非新手友好任务
