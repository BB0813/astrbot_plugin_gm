### 3. 可行性判断质量

**应纠正为**：必须显式给出 A/B/C/D 四档分支（#139 硬约束）。

**分支 A（最小可行）**：仅踢人后自动清历史 + 全局开关 + 一条命令 `/清历史 @user`
- 工作量：80-150 行 / 1-2 天
- 风险点：聊天记录 API 跨适配器差异、踢人事件钩子

**分支 B（完整）**：分支 A + 按群覆盖配置 + 私聊/群聊命令双入口
- 工作量：150-250 行 / 2-3 天
- 配置项：`clear_history_on_kick` / `clear_history_group_overrides` / `clear_history_command_enabled`

**分支 C（完整 + 跨适配器回读）**：分支 B + 适配 OneBot/aiocqhttp/官方消息 API 差异矩阵 + 装饰字符 QQ 防护（继承 #134/#136 模板）
- 工作量：250-400 行 / 3-5 天

**分支 D（分阶段）**：先 A 后 B/C，对应两个独立 Issue 跟踪
- 工作量：累计 4-6 天

**关键技术依赖与必检清单**：
- ① AstrBot 踢人事件回调/钩子（`group_decrease` 事件）跨适配器差异
- ② 聊天记录删除 API（OneBot `delete_msg` 仅能撤回机器人自己的消息，"清历史"通常需**撤回**该用户所有消息——实质是"撤回某用户历史消息"）
- ③ 缓存依赖：必须复用现有 `recent_messages`/`message_history` 链路（项目记忆"#135 撤回缓存三层"），否则无法定位要撤回哪些消息
- ④ 跨适配器撤回权限差异（管理员撤回他人消息的权限）
- ⑤ 隐私边界：是否清空自己的？是仅清被踢者发送的还是也清接收的？
- ⑥ 按群覆盖需扩展 `group_overrides` schema
- ⑦ 装饰字符 QQ 防护（继承 #134/#136）
- ⑧ 命令命名（`/清历史` vs `/清除历史` vs `/cleanhistory`）
- ⑨ 大量撤回的速率限制（QQ 风控）
- ⑩ 权限模型：执行命令者必须是 plugin_admins 或群管

**与参考仓库的关系**：必须**先访问** `https://github.com/zcj-ui/astrbot_plugin_group_guardian` 验证其实现路径。若实现基于 OneBot 撤回 API 且不支持跨适配器，需在建议章节明确"参考实现仅覆盖 OneBot 路径"。
