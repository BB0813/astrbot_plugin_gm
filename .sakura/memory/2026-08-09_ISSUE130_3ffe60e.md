## 6. 经验教训

### 关键教训 1：校验失败必须局部修复，不能整体降级

本次分析触发了**最严重的反模式**：
- 看到一个字段报错（`reserved tag syntax in USERNAME`）
- 把所有字段都退化为"无法评估"/`other`/空

正确做法：
1. 识别错误来源——某个字段（如 USERNAME 标签）格式校验失败
2. **仅修复该字段的输出**（如换用不同标签格式或写"待确认"）
3. 其他字段基于 Issue 内容正常评估

### 关键教训 2：项目记忆已有 #130 标准模板，必须复用

项目记忆 §"权限模型重构类 Issue 标准模式（#130 案例）" 是一份**预制标准模板**，明确给出了：
- 必查项（7 项）
- 分类（`enhancement` + `breaking-change`）
- 优先级（`medium`）
- 五处同步清单
- 新增标签建议（4 个）

未来遇到权限模型重构 Issue 时，**必须先检查项目记忆中是否有该案例模板**，避免重复从零分析。

### 关键教训 3：USERNAME 等保留字校验错误的处置

Issue 中"作者：unknown"、原标题"。"等异常输入不应触发整体降级。应：
1. 单独标注"作者信息缺失，建议人工补充"
2. 对"。"标题进行主动改写（反模式记忆明令）
3. 其他字段继续基于 Issue 正文评估

## 总结

本次分析暴露的**核心问题是流程纪律性**——遇到字段校验错误就放弃全部判断，把"无法评估"当作万能挡箭牌。这是项目记忆反模式章节明确警示、**但本次仍然犯下**的错误。

未来遇到类似情况时，必须先做"Pre-check"：在任何字段出现"无建议/无法评估/空/未检测到重复"前，先确认是否源于校验失败——校验失败应**局部修复**而非**整体降级**。

对于权限模型重构类 Issue，项目记忆已有完整模板，**应优先复用而非重新评估**。
