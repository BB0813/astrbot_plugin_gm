# Issue #136 分析反思

## 1. 分类与优先级准确性

**分类 `bug` ✓ 准确**：命令解析层错误导致装饰字符被误识别为 QQ 号，属明确运行逻辑错误而非配置/增强需求。

**优先级 `medium` ✓ 合理但需细化决策路径**：
- 分析中给出的理由"误解禁比误禁言影响更严重"是定性叙述，未显式列出 4 条判定路径，违反 #133 沉淀的"优先级决策路径显式化"原则。
- 应显式列出：① 核心解禁命令解析错误（high 倾向）② 但仅特定装饰字符场景触发（降一档）③ 单群单次未扩散（降一档）④ 已有 #134 同根因模板可复用（不算新风险）→ medium。
- **误判警示**：若将此 issue 标为 `high`，会与 #134 同根因模式产生不一致（#134 也是 medium），需保持同根因一致性。

**遗漏点**：未评估"误解禁的连锁影响"——若误解禁的是"被禁言的反机器人账号/管理保护对象"，可能引发安全风险；这是潜在 high 因素，建议在优先级章节补一句"若目标群存在保护对象需重新评估"。

## 2. 标签推荐质量

**贴切的标签**：`bug` + `command` + `parser` + `group-management` ✓ 与 #134 模板完全一致，符合"同根因同标签"原则。

**置信度评估问题**：
- `needs-info` 0.3 — 项目记忆 #134 模板建议 `needs-info` 0.55+，本 issue 实际信息（装饰字符样本、触发命令、解析错位的具体 QQ）已比 #134 更充分（#134 仅"获取信息问题"四字），降 0.3 反而合理，但应在文中说明理由而非孤立数字。
- `duplicate` 0.85 — 与 #134 同根因但触发命令不同（解禁 vs 禁言），不应直接打 `duplicate` 标签，应打 `related-to` 或 `same-root-cause`，置信度上限 0.65（项目记忆"主分类+API 双过滤"原则要求重复检测前先做模块判定）。

**遗漏标签**：
- 缺 `at-parse`/`at-extract`（#134 模板建议新建）— 既然是同根因，应主动建议标签体系对齐。
- 缺 `mute-action`/`unmute`（#133/#135 沉淀）— 解禁命令必给标签。
- 缺 `unicode-normalization` 或 `decorative-unicode` — 这是装饰字符特化的标签，应沉淀为仓库标签体系的一部分。

**与仓库标签一致性**：现有标签（bug/command/parser/group-management）与 #134 完全对齐，但未主动建议仓库建立"装饰字符 QQ"专用标签，不利于后续 #137+/同类检索。

## 3. 可行性判断质量

**显式分支判定 ✓ 优秀**：分支 A/B/C 三档（20-40/40-80/80-150 行）符合 #133 沉淀的"显式分支判定"要求，且推荐"分支 B 起步"给出明确决策。

**NFKD vs NFKC 技术细节 ✓ 精准**：分析明确指出 NFKC 对 U+1D400-U+1D7FF 区段无效，必须用 NFKD 或白名单拒绝方案。这是关键技术陷阱，能避免维护者踩坑，**沉淀价值高**。

**传染性测试成本低估**：
- 列出 13+ 调用点扫描（_parse_qq、_parse_qq_list、_extract_at_qq、_extract_at_qqs）是必要的，但"传染性测试成本 +0.5 天"偏乐观。
- 实际还需：① 跨命令回归测试用例构造 ② 适配器差异测试（NapCat/Lagrange/go-cqhttp 装饰字符 AT 段字段差异）③ 边界场景（混装饰 + 半数字、中间夹装饰）。建议调整为 +1 天，总工作量 2-3 天。

**未识别的风险点**：
- 缺"装饰字符 QQ"在 OneBot v11 协议层是否被 NapCat/Lagrange 预处理（部分实现会把无法识别的 at 直接丢弃）—— 这会改变修复优先级（若是协议层拦截后插件看到的字段已损坏，则需在适配器层处理而非插件层）。
- 缺"raw["message"] 中装饰字符 AT 段的字段差异"——v11 标准是 `{type:"at", data:{qq:"xxx"}}`，但部分扩展会用 `{type:"at", data:{user_id:"xxx"}}`，字段名差异会污染修复方案。

## 4. 重复检测准确性

**"可能是 #134 的重复" ✓ 准确但措辞违反反模式**：项目记忆明令禁止"可能是#X的重复"措辞，应改为"高度疑似重复（与 #134 同根因模式：_extract_at_qq 未做装饰字符校验），建议合并到 #134 或互相引用，置信度 0.85"。

**置信度问题**：
- 0.85 偏高。应调整为 0.75，理由：① 触发命令不同（解禁 vs 禁言），虽然根因相同但症状表现不同 ② #134 模板建议的标签清单比 #136 更通用 ③ 两个独立 issue 便于分别跟踪修复进度。
- 触发"主分类+API 双过滤"前置过滤：两者主分类都是 bug，API 都是 at 段解析，过滤后应聚焦"症状差异"——#134 是"踢人命令误识别"，#136 是"解禁命令误识别"，症状不同不应直接打 `duplicate`。

**漏报检测**：
- 未检索是否还有同类 issue（如 #137+ 触发装饰字符但描述为其他症状）—— 建议在重复检测章节补"建议同时检索 #134 同类触发关键词：装饰字符/花体字/数学字母/手写体/Emoji 风格/@𝓒𝓪𝓷𝓬𝓮𝓻/@𝐀/@𝕒"。

**反模式检查**：
- ✓ 未使用"未检测到重复"

## 6. 经验教训

### 关键沉淀（应进入项目记忆）

1. **"装饰字符 QQ 解析"已形成独立高频模式**（#134 → #136 两次触发）—— 建议在项目记忆"装饰字符 QQ 标准模板"章节明确标注"已第二次触发，应作为仓库高频解析类 bug 模式第一序列"。

2. **NFKD vs NFKC 技术细节**应沉淀到模板——"U+1D400-U+1D7FF 区段装饰字符（如 𝓒𝓪𝓷𝓬𝓮𝓻）必须用 NFKD 归一化或白名单拒绝，NFKC 对此区段无效"。这是具体可复用的技术沉淀。

3. **"同根因不同症状"的重复检测置信度上限**——主分类 + API 都相同时，置信度上限 0.75-0.85；若症状/触发命令差异明显（如 #134 踢人 vs #136 解禁），置信度上限 0.75。

4. **传染性测试成本低估陷阱**——13+ 调用点的扫描 + 适配器差异测试 + 边界场景构造，传染性测试成本应为 +1 天而非 +0.5 天，应更新 #134 模板的"工作量"区间。

- **装饰字符/视觉欺骗型解析 bug**：触发关键词矩阵已稳定（花体字 + 数学字母 + 手写体 + Emoji 风格 + 区段 U+1D400-U+1D7FF），未来遇到应直接套 #134 模板。

- **`_extract_at_qq` 是仓库高频解析入口**：除 #134/#136 外，需主动扫描 #133 解禁类 issue 是否也存在同类解析问题，避免遗漏。
