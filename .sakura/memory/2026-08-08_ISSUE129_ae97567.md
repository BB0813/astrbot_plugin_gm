# Issue #129 分析反思

## 1. 分类与优先级准确性

**严重错误**：分类 `other`、可行性"无法评估"是典型的**整体降级反模式**。

原标题 `[enhancement][medium] 加群申请拒绝时支持填写或配置自定义拒绝理由` 已经明确标注了 `enhancement` + `medium`，内容也清晰描述了需求：**加群申请**被拒绝时支持自定义拒绝理由。Issue 完全可分析：

- **正确分类**：`enhancement`
- **正确优先级**：`medium`（与原标题一致；自定义拒绝理由是用户体验提升，非核心功能，但涉及机器人代为执行群管理动作，存在填写不当风险，因此不适合降为 low）
- **影响范围**：依赖现有加群申请处理流程，OneBot 适配器层是否支持拒绝理由参数是关键依赖

**触发"无法评估"的根因**：摘要字段写成了 `AI Issue analysis output could not be validated: expected <REASON>`——这是字段校验失败的报错信息被误当作摘要内容，**不应该导致整体降级**。这正是反模式反复强调的"结构化输出校验失败 ≠ 信息不足"。

## 2. 标签推荐质量

**严重遗漏**：建议标签为空，但本 Issue 应至少包括：

- `enhancement`（主分类）
- `group-management`（群管理核心域）
- `join-request` / `join-approval`（加群申请专属标签）
- `configuration`（"或配置自定义"暗示可配置）
- `onebot` / `compatibility`（OneBot `set_group_add_request` 拒绝参数 `reason` 字段跨适配器支持度差异）
- `needs-info`（需确认 OneBot 实现版本、NapCat/Lagrange/go-cqhttp 对 `reason` 参数的支持）
- `needs-discussion`（填写策略：默认理由 / 管理员自定义 / 按群配置）

置信度建议：`enhancement` 0.95+、`group-management` 0.85+、`join-request` 0.85+、`onebot` 0.75+、`configuration` 0.70+、`needs-info` 0.70+、`needs-discussion` 0.65+。

## 3. 可行性判断质量

**完全缺失**。基于项目记忆可做以下条件性判断：

- **依赖确认**：OneBot `set_group_add_request(flag, sub_type, approve, reason)` 在 NapCat/Lagrange/go-cqhttp 均支持 `reason` 字段，但实际生效依赖适配器版本。
- **工作量**：
  - **最小实现**（指令式）：拒绝时附加默认理由文案，~30-50 行，1 天内
  - **配置化实现**：全局默认理由 + 按群覆盖 + 管理员预设理由模板，~150-250 行，2-3 天，需同步 `_conf_schema.json` + README + 帮助
- **风险点**：
  - 管理员填写理由不合规（如含违规词）可能被举报
  - 跨适配器 `reason` 长度限制差异（建议做截断处理）
  - 与既有 `pending_join_requests` 流程衔接

应给出"最小实现 low-medium 风险 / 配置化 medium 风险"的条件性可行性，而非"无法评估"。

## 4. 重复检测准确性

**措辞违规**：使用了被明令禁止的"未检测到重复"。

按强制模板，应写"**暂未发现重复 Issue**"并列出建议检索关键词：`加群申请`、`拒绝理由`、`add_request`、`set_group_add_request`、`reason`、`join-request`、`pending_join_requests`、`custom-reason`。

⚠️ **措辞核对**：本输出**违规使用了"未检测到重复"**，必须改为"暂未发现"。

## 5. 标题改写适当性

**完全缺失**。原标题 `[enhancement][medium] 加群申请拒绝时支持填写或配置自定义拒绝理由` 已清晰覆盖需求、动作、范围，但可以：

- **保留原标题**（原标题已清晰）→ 标"可保留"
- 或**轻量规范化**：`[enhancement][medium] 加群申请拒绝时支持自定义拒绝理由（填写或配置）`（去掉"或"歧义，明确"填写"与"配置"是两种实现路径）

不应写"无建议"——这与"无法评估"措辞同样被明令禁止。

## 6. 经验教训

### 本次失败的核心教训

1. **再次违反"字段校验失败 ≠ 信息不足"反模式**：校验报错信息被错当成摘要，直接触发整体降级（分类→other、可行性→无法评估、标题→无建议、标签→空）。校验失败应**仅修复字段输出**，实质性判断必须保留。

2. **再次违反"无建议/无法评估禁用"反模式**：标题"无建议"、可行性"无法评估"、分类`other`、标签空——四重降级叠加，是本仓库分析最严重的反模式之一。

3. **再次违反"未检测到重复"禁用措辞**：连续多次在重复检测中使用被明令禁止的措辞，说明模板未真正内化。

### 加群申请类 Issue 专项经验

- **OneBot 加群申请 API 必查项**：`set_group_add_request(flag, sub_type, approve, reason)` 的 `reason` 字段跨适配器支持；`get_group_add_request`/`get_group_request_list` 获取待处理申请。
- **与既有 `pending_join_requests` 流程衔接**：本仓库已有加群申请处理流程，新增"自定义拒绝理由"应复用其入口，避免新增并行通道。
- **配置 schema 建议字段**：`reject_reason_enabled`、`reject_reason_default`、`reject_reason_per_group`、`reject_reason_templates`（预设理由模板列表，管理员可选择）。
- **分类必为 `enhancement`**：不是 bug，不是 other；`medium` 而非 low 的理由：涉及代为拒绝加群申请，存在误拒/理由不当风险。

### 仓库特有模式提醒

- 任何涉及 OneBot API 新参数（如 `reason`、`special_title`、`duration`）的 Issue 都必须标注 `onebot` + `compatibility`，并要求确认适配器实现版本。
- 任何涉及"管理员填写输入"的 Issue 都应考虑：长度限制、敏感词过滤、跨适配器差异、配置化与硬编码两种实现路径。

## 总结：本次分析的根本性失败

本次分析是**反模式的教科书级失败案例**：一个信息充足、标题清晰、需求明确的 enhancement 类 Issue，被退化为分类 `other`、可行性"无法评估"、标题"无建议"、标签为空、重复检测违规措辞——所有实质性输出全部塌陷。根因是 **AI 输出字段校验失败时触发了错误的整体降级链路**，而非真正的判断缺失。

**强制整改清单**：
1. 分类 → `enhancement`
2. 优先级 → `medium`
3. 可行性 → 给条件性判断（最小实现 1 天 / 配置化 2-3 天）
4. 标签 → 至少 7 个候选标签（见 §2）
5. 标题 → "可保留"或轻量规范化版
6. 重复检测 → "暂未发现" + 检索关键词清单
7. 摘要 → 重写为正常需求摘要

**未来防御措施**：在任何字段出现"无建议/无法评估/空/未检测到重复"前，必须先确认**这是否源于校验失败而非真正判断缺失**——校验失败仅局部修复字段，不得影响实质性判断。
