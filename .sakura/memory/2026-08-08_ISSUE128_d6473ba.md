# Issue #128 分析反思

## 1. 分类与优先级准确性

**分类：`enhancement`（置信度 0.95）— 准确**

- 维护者本人提交的新功能请求（语音 STT 转写 + 复用违规检测链路），属典型增强需求，分类正确。
- 与既有规范"权限/配置粒度调整归 enhancement"一致，且明确是新增输入源（语音 segment）→ 既有处置链路，不涉及 bug 修复。

**优先级：`medium` — 合理但需要论证**

- **支持 medium 的理由**（分析中已提及，但可强化）：
  - **隐私与生物特征风险**：语音属于敏感生物特征数据，未经明确告知的 STT 转写 + 自动撤回/禁言存在合规与社区争议风险（README 隐私告知段已点出）；
  - **误触发的不可逆性**：STT 误识别 + 违规词模糊匹配 = 误撤回/误禁言，比纯文本场景的误判影响更严重（语音内容不可"撤回后恢复"，用户感知强烈）；
  - **横切关注点多**：涉及配置 schema、README、帮助命令、CHANGELOG 五处同步，还涉及异步链路（§4.1 async yield 风险叠加）。
- **未充分论证的反面**：如果是"群主/管理员主动启用 + 白名单兜底 + 灰度发布"的产品定位，风险可控，可向 low 靠拢；但鉴于 Issue 描述未提及这些缓解措施，medium 是稳妥判断。

**优先级判断的反模式检查**：
- 分析中提到"误触发风险论证（≥ medium 关键理由）"——措辞不当，应为"误触发风险是 medium 优先级的关键理由之一"，避免暗示 medium 是该 issue 独有的特征。
- 没有陷入"删除功能 → low"的反模式（这是减法类 issue 的特例，本 issue 是新增功能）。

## 6. 经验教训

### 6.1 仓库特有模式

**语音/STT 类 Issue 的标准分析模板**（建议固化）：

1. **必查项**：
   - AstrBot 框架是否暴露语音 segment 转写接口（`event.message_obj.message` 中 `type='record'` 的 segment）；
   - OneBot 适配器对语音文件获取的支持（`get_record` API、消息 segment 的 `file` / `url` 字段）；
   - STT 引擎选型（AstrBot 内置 provider / 本地 Whisper / 云端 API）的成本对比；
   - 隐私告知段（语音 = 敏感生物特征）。

2. **必给标签**：`enhancement` + `stt`/`voice` + `moderation` + `group-management` + `configuration` + `documentation` + `needs-discussion` + 条件性 `breaking-change`。

3. **可行性关键风险**：
   - 异步链路（§4.1 yield 反模式）；
   - 撤回时限撞限（STT 耗时 + 2 分钟限制）；
   - 误触发（STT 误识别 × 关键词模糊匹配）；
   - 依赖体积（Whisper ~3GB）；
   - 隐私合规。

4. **强制五处同步**（与撤回类一致）：main.py + `_conf_schema.json` + README + 帮助命令 + CHANGELOG。

### 6.2 跨场景可复用经验

1. **"复用既有链路"类 Issue 的标准动作**：
   - 必查既有链路的核心函数（如本 issue 的 `_moderation_dispatch` / `_handle_violation`）；
   - 明确"扩展入口 vs 新建入口"——若可扩展既有入口（如在 `_moderation_dispatch` 中新增 `_check_voice` 分支），优先扩展；
   - 评估复用对既有行为的影响（是否构成隐性 breaking change）。

2. **异步耗时操作的强制约束**：
   - `asyncio.create_task` 包裹 + 异常不外抛；
   - helper 函数必须 `async def + await`，禁 yield；
   - 跨事件边界校验（消息 ID 时效性、操作时限）；
   - 长任务取消/超时/部分失败处理。

3. **多模态内容审核的统一框架**：
   - 文本（已有）→ 图片（已有 `_check_image`）→ 语音（本 issue 提议）→ 未来视频/文件；
   - 建议在 `_moderation_dispatch` 中建立"输入源 → 转写/标准化 → 文本违规检测 → 处置"的标准流水线，新增输入源只需补"转写/标准化"环节。
