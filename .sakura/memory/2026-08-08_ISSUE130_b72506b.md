**改动范围（五处同步，与撤回类同构）**：

2. `_conf_schema.json`：删除 `plugin_admins` 字段（必须保留迁移注释或兼容逻辑）
3. `README.md`：删除"插件管理员"说明，更新权限章节为"群管理员/群主自动拥有插件管理权限"
4. 帮助命令：同步权限说明
5. `CHANGELOG`：标注 breaking change + 配置迁移说明

**技术依赖**：
- OneBot `get_group_member_info` 必须支持 → NapCat/Lagrange/go-cqhttp 表现可能不同
- 缓存策略：是否缓存群成员角色以避免每次 API 调用？（缓存过期策略、成员变更失效）
- 调用频率：每次管理类命令都查群成员信息会显著增加 API 调用

**工作量估算**：
- 最小可用版本：~100-150 行（删旧逻辑 + 加新 helper + 修改调用点）
- 完整版本（含缓存 + 适配器兼容测试）：~200-300 行 + 1-2 天测试

**风险点**：
1. **缓存一致性**：群成员角色变更（如某人被设为管理员）需要及时失效缓存
2. **权限提升风险**：移除 `plugin_admins` 后，bot 所在所有群的管理员/群主都能执行管理命令，需审计是否有不希望被群主执行的命令
3. **配置迁移**：旧 `config.json` 中的 `plugin_admins` 字段如何处理（自动删除？保留并提示？）
4. **get_group_member_info 失败兜底**：API 调用失败时是默认拒绝还是默认放行？

### 应给出的可行性结论

**"条件性可行（中等风险）"** —— 工作量中等，但涉及权限模型横切改动 + breaking change，需要重点关注配置迁移和缓存策略。

## 6. 经验教训

### A. 致命反模式复现

本次分析是项目记忆中明令警示的所有反模式的**教科书级复现**：

1. ❌ 格式校验失败 → 整体降级为 `other`（违反"字段校验失败仅触发输出修复，不得影响实质性判断"）
2. ❌ 可行性退化为"无法评估"（违反"信息不足时也应有条件判断"）
3. ❌ 标签留空（违反"标签在不确定体系时也应给通用候选并注明需映射"）
4. ❌ 重复检测写"未检测到重复"（违反强制模板，必须写"暂未发现+检索词"）
5. ❌ 标题写"无建议"（违反明令禁止）

**根因反思**：遇到 `expected <SUGGESTED_TITLE>` 校验错误时，分析者选择"放弃所有判断"，而不是按记忆 §1 的 Pre-check 规则去**局部修复字段输出**。

### D. "权限模型重构"类 Issue 的标准模式

建议固化为项目记忆新增条目：

**触发场景**：将插件自定义权限模型改为依赖群原生权限（如移除 `plugin_admins`、移除 `title_admins` 等改为自动检测群管理员/群主）。

**必查项**：
1. 待删除的配置项及其影响范围（哪些命令/功能依赖）
2. 群原生权限获取 API 依赖（OneBot `get_group_member_info` 跨适配器差异）
3. 缓存策略（每次命令都查 vs 缓存 + 失效）
4. 权限提升风险审计（新权限模型下哪些群主能执行原不该执行的命令）
5. 配置迁移路径（旧 `config.json` 如何处理）
6. API 调用失败兜底（拒绝 vs 放行）

**应给标签**：`enhancement` + `breaking-change` + `permission` + `configuration` + `group-management` + `onebot`/`compatibility` + `needs-discussion`（中权重）

**优先级**：**`medium`**（横切权限重写但有迁移路径）而非 `high`（除非权限提升导致严重越权风险）

**五处同步清单**：main.py + `_conf_schema.json` + README + 帮助命令 + CHANGELOG
